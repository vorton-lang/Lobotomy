# Manager 动作集与信息通道

> Status: 设计决定
> 前置：[harness-adapter.md](harness-adapter.md)（进程模型、执行现场与成果、能力裁剪）

## 0. 原则

- **机械操作归运行时，判断归 Manager。** Manager 是 agent，会犯错；它只出现在需要判断的地方。
- **原文由运行时插入。** Manager 只引用 ID：用户原话、下层产出、记录条目都由运行时原样渲染，Manager 在结构上无法改写或伪造。
- **用户可以质疑系统的判断。** 下层产出全部可达，不删除；Manager 的解读与记录对用户可见、可改；下层可以绕过 Manager 指出解读错误。
- **Manager 就是下层的用户。** Manager 发给下层的消息就是普通的 user turn，Manager 声明自己的身份即可。
- **Manager 可以缺席。** 下文每个动作都对应一条运行时命令，用户在 GUI 中同样可以执行；Angela 不在时，进入她收件箱的内容直接呈现给用户（[roles-and-tasks.md](roles-and-tasks.md) §1.4）。

## 1. 向下：转发原话，解读附在后面

```text
send_to_role(
  project_id,
  role,                      // role 的名字，例如 "Malkuth"，来自 read_project
  task_id?,                  // 消息关于哪个任务；不关于任务时不填
  quote?: [msg_id, ...],     // 用户消息，运行时按时间顺序原样插入
  context?: [id, ...],       // 用户当时在回复的对象，原样插入（见下面"上下文"）
  ledger?: [entry_id, ...],  // 引用记录条目，原样插入（§3.4）
  interpretation: string,    // Manager 的解读，附在后面
)
```

派活的 `assign` 以同样的方式转达原话，参数见 roles-and-tasks.md §4。

下层收到的内容：

```text
【来自 Angela · 任务 task_…】
【用户原话】10-01 14:02
这个方向差不多，但是内存模型总觉得有点怪，先别大改。

【用户当时在回复】Angela 10-01 13:58（item_…）
……

【记录】
- [约束] ……（led_…；用户原话：「……」）

【Angela 解读】
……
```

- 转发哪些原话、发给谁，由 Manager 判断；不是每条用户消息都转给所有 role。
- 段落标题由运行时固定生成，下层始终分得清谁说了什么。没有原话、上下文和记录时，消息只有 Manager 的话，消息标题【来自 Angela】已写明发送者。
- 解读使用轻量模板，不是严格 schema：我理解的目标 / 我推断的边界 / 我不确定的地方 / 希望何时回报什么。原话以外的内容都属于 Manager 的推断。
- 下层角色指令写明：**原话优先**。原话与解读冲突时以原话为准，并调用 `flag_mismatch` 报告（见 2.3）。
- 用户的消息被转发后，GUI 在该消息下写明去向，例如"已转给 Malkuth（项目 · 任务「…」）· 附上下文：…"；派成任务时写"派成任务给 …"。用户指定的上下文标为"你指定"。点开进入那个项目，有任务时打开那个任务，用户可以核对解读。

### 1.1 上下文：用户当时在回复什么

`context` 由 Manager 从可引用的记录中选择；用户也可以在 GUI 中手动指定（用户定）。

依据：用户同时推进几件事时，一条消息不一定是在回复 Manager 最新的那条。用户常用文字指示自己在回什么，例如"导出那个可以"；这时只有 Manager 理解它，而且偶尔会理解错。

**由 Manager 选择**：

- `context` 可以引用 Manager 自己的回复或她对话中的消息，也可以引用这个项目中的任务或汇报（§2.1）。运行时按 ID 读出原文，原样插入【用户当时在回复】一段；汇报附上全文。附上的内容复制进项目的数据库，记下来源 ID 和是否由用户指定（data-model.md §10.6 跨库操作第 1 条）。
- Manager 看不到自己回复的 ID。她用 `recent_replies(limit?)` 列出最近的回复：ID、时间和第一行。她只在需要选上下文时调用，平时的输入里不加这些内容。
- 引用用完整的 ID，不用短编号。ID 带随机部分，抄错一个字符几乎不会恰好变成另一条存在的 ID，运行时会拒绝并报错。短编号抄错时常常正好是另一条存在的记录，会悄悄附上错误的上下文。
- 剩下的风险是 Manager 判断错了用户在回什么，这是判断错误，校验拦不住。它的选择对用户可见：用户的消息下写明附了什么上下文（§1）。下层收到的【用户原话】和【用户当时在回复】放在一起，对不上时可以在汇报中指出，或调用 `flag_mismatch`（§2.3）。

**用户手动指定**：

- GUI 中 Angela 的每条回复旁有"回复"，用法类似即时通讯软件：用户在文字讲不清楚时，手动选择这条消息回复的对象。发出的消息记下 `reply_to`，消息上方显示"回复：「…」"。
- 这是用户的机械覆盖，所有角色都按它执行：
  - Angela 的输入中，这条消息的标题下写明"（回复 Angela 的 item_…：「第一行」）"。其他 role 收到带 `reply_to` 的消息时也写明。
  - Manager 用 `send_to_role` 或 `assign` 转达这条消息时，运行时先附上用户选的对象，标为用户指定，再附上她用 `context` 加的。Manager 不能替换或去掉用户选的对象（用户定）。
- 只回复一条消息中的一段（子消息粒度）暂不实现（用户定）。真实使用中出现这个需求时再做，在此之前留意用户是否需要它。

## 2. 向上：正文是 Manager 的话，原文作为附件

### 2.1 附件

Manager 的回复就是对用户说的话，其中用 `[[att:<id>]]` 引用下层产出。运行时负责：

- 校验 ID 是否存在，伪造的 ID 渲染为错误引用；
- 将附件渲染为**默认收起**的一行，点开才看到内容；
- 生成附件标题行：项目、来源 role、类型、时间、长度，以及下层在汇报时自己写的标题。Manager 无法给附件写标题。

现在可以引用任务和执行者的汇报，点开是那个项目中的任务面板。引用 turn 输出、GitHub 条目未实现，列入 roadmap 待排。

```text
Worker 的实现已经完成并通过验证，检查全部通过。TL 提了一个问题，我认为值得你现在看：
分配器在并发场景下的语义还没定。
  ▸ TL 汇报 · 并发语义疑点 · 10-01 14:20 · 1.2k 字
```

**附件写明版本与当前有效性**（用户定，[#50](https://github.com/vorton-lang/Lobotomy/issues/50)）：

- 附件指向绑定版本的对象时，运行时写明它绑定的版本。界面把版本放在悬停提示中（frontend.md §7.3，P2 内部词汇降级）。
- 运行时渲染附件时，按当前状态标出它是否已过期。项目中有新事件时，GUI 重新读取附件的当前有效性。
- 现在能引用的任务与汇报不绑定版本，附件只显示它们当前的状态（[#86](https://github.com/vorton-lang/Lobotomy/issues/86)）。
- 附件的内容不变，仍是 Manager 引用时的内容。
- 依据：结论要和它的前提一起读，例如"测试通过"与"跑的是旧提交"。这两项由运行时一起渲染，Manager 无法把它们拆开。Manager 较早写的消息，也不会因为之后的变化误导用户。

**引用用户原话**（用户定）：Manager 在回复中引用用户说过的话时，写 `[[quote:<msg_id>]]`，由运行时原样渲染那条消息，并标出时间。Manager 不自己写出带引号的"用户原话"。

- 运行时校验 ID 存在，而且是用户本人的消息；否则渲染为错误引用。规则与 §3.2 中 `decision` 的依据相同。
- 依据：§0 规定原文由运行时插入。Manager 的面试中，指令明确要求"引用时原样引用"，模型仍把自己的概括放进引号，当作用户原话（[Ember manager-interviews 第三轮](https://github.com/vorton-lang/Ember/tree/main/manager-interviews/2026-10-11-official-cli-round3)）。
- 待决问题：是否支持只引用一条消息中的一段，例如按字符范围。

### 2.2 下层产出的去向

| 状态 | 怎么进入 | 用户在哪里看到 |
|---|---|---|
| 已呈现 | Manager 在回复中引用 | 对话中的附件 |
| 暂缓 | Manager 调用 `defer(ids, reason?)` | Workboard 上的"暂缓 N 条" |
| 未呈现 | 运行时自动归入（没被引用，也没被暂缓） | Inspector |

Manager 不需要逐条表态，只有"暂缓"需要显式调用。

现在只有"已呈现"：她在回复中引用的产出显示为附件。`defer` 以及"暂缓""未呈现"的归类未实现，列入 roadmap 待排。

### 2.3 `flag_mismatch`

下层认为 Manager 的解读与用户原话不一致时，在运行中的 turn 里调用 `flag_mismatch(body)`。运行时把它作为**系统提示**直接显示在对话流中，不经 Manager 过滤，因为这是在质疑 Manager 本身。内容是该 role 自己写的说明，原话与解读作为附件附上。Manager 同时收到，以便修正。这条直达通道只用于这一种情况。

- 命令写入项目的数据库，作为项目事件记下。运行时经事件游标把它送到 Manager（§6）：单独一条 Lobotomy 消息，放在用户与 Angela 的对话中，第一行写明"有角色认为 Angela 的解读与用户原话不一致"，用户直接看到。
- 它同时唤醒 Manager，不等项目停下。她的 turn 正在运行时，留到下一个 turn。
- 现在消息中只有该 role 写的说明和它所在的任务。把原话与解读作为附件附上，未实现，列入 roadmap 待排。系统通知见 §6。

## 3. 记录（ledger）

记录由 Lobotomy 保存。Manager 的长期记忆不依赖 harness 自带的记忆，也不依赖原生会话的上下文：harness 和模型会换，它们的上下文窗口和注意力也不同（用户定；方向见 [#22](https://github.com/vorton-lang/Lobotomy/issues/22)）。

### 3.1 与运行时状态分开

| 类型 | 内容 | 写入方 |
|---|---|---|
| 运行时状态（事实） | 谁正在跑 turn、成果与集成状态、会话 ID、用量 | 运行时 |
| 记录（判断） | 目标、阶段、决定、约束、待定问题、对用户状态的推测 | Manager，经 MCP 写入 |

### 3.2 结构：只追加，每条带依据

```text
ledger_add(kind, statement, evidence?: [msg_id], project_id?, task_id?, confidence?, supersedes?: entry_id)
```

| kind | 含义 | 依据 |
|---|---|---|
| `goal` / `phase` | 当前目标；阶段（探索 / 设计 / 执行 / 审查） | 可选 |
| `decision` | 已定的事，默认不再重开 | **必须引用用户消息** |
| `constraint` | 约束，标明范围（本任务 / 长期） | **必须引用用户消息** |
| `open_question` | 待定的事，以及在等谁（用户 / TL / Worker） | 可选 |
| `hypothesis` | 对用户状态的推测，附置信度 | 可选 |

- 条目不原地修改，变更时追加新条目并用 `supersedes` 指向旧条目，保留完整的理解演变过程。`supersedes` 必须指向同一作用域中最新的那一条，每条只能被取代一次。
- "必须引用用户消息"由运行时校验：ID 必须存在，且必须是用户本人的消息（会议中的发言也算）。没有用户原话作依据的判断，只能作为推测记录。
- **作用域**：不带 `project_id` 的条目是用户范围，存在 Manager 的数据库中；带 `project_id` 的是项目范围，再带 `task_id` 的是任务范围，都存在项目的数据库中（data-model.md §10.6）。依据的用户原话复制进同一个数据库，并记下来源 ID。
- 任务范围的约束在任务关闭后失效（roles-and-tasks.md §2.2）。

### 3.3 可见性

- **"共识"面板**：显示仍然有效的目标、阶段、决定、约束和待定，各附依据的原话。现在它在「全部」的右侧栏。
- 用户可以直接修改、关闭、重开共识中的条目；修改立即生效且为最终结果，由运行时直接写入，Manager 只收到通知，有异议可在之后的回复中提出。未实现：M4 中"共识"只读（用户定），修改列入 roadmap 待排。
- **待定（`open_question`）只进"共识"，不进"等你决定"**（用户定）。需要用户回答时，Manager 用 `ask_user`（§6）；问题状态只有 `question` 一个来源（data-model.md 的"问题与回复的因果关联"）。
- `hypothesis` 不在主界面显示，只能在 Inspector 中查看。Inspector 还没有做，现在界面上不显示推测。

### 3.4 读者

- **Manager**：一个会话内记录已在上下文中，不每轮重新注入。她的下一个 turn 开始新会话时，运行时把各作用域中仍然有效的条目整理后放进她的输入，作为她的可恢复状态；推测放在最后，读不到的项目写明原因。她用 `read_ledger(project_id?)` 读全部条目，每条写明是否仍然有效。用户的修改以事件形式通知她（修改共识未实现，§3.3）。
- **TL / Worker**：通过 `send_to_role` 和 `assign` 的 `ledger` 参数获得被引用的条目。Manager 按 ID 引用用户范围或这个项目的条目；运行时把它们按记下的样子插入【记录】一段，附上依据的原话，放在【用户原话】与【用户当时在回复】之后、Manager 的解读之前（§1）。被取代或已失效的条目不能引用。下层也可通过只读 MCP 查询 `decision` 和 `constraint`：未实现，列入 roadmap 待排。
- **`hypothesis` 永远不传给下层。** Manager 引用推测时，运行时拒绝。

### 3.5 下层的可恢复状态

TL / Worker 各自通过 `org_checkpoint` 写语义检查点，因为它们最清楚自己的工作状态。写入时机由运行时机械触发：换会话前、Claude 压缩前后。存储机制与 ledger 相同，内容各自独立。

`org_checkpoint` 未实现，列入 roadmap 待排。

## 4. 升级：会议

本节未实现，列入 roadmap 待排。

### 4.1 机制

会议是运行时维护的共享记录，参会者为用户、Manager 与选定的 TL / Worker。

- 每条发言原样投递给所有参会者，不经转述。
- 参会 role 继续使用自己的主会话（inline）。每轮投递上次以来的新发言，带发言人标签，开头是运行时生成的标题 `【会议】参会者：…`。
- 由 @ 决定谁回复：被 @ 的 role 回复；用户未 @ 任何人时由 Manager（主持人）回复，它可以再 @ 别人。同时被 @ 的 role 并行回复，下一轮才看到彼此的回复。
- agent 之间连续互相 @ 的轮数有上限（默认 3），到达上限后发言权回到用户。由运行时执行。
- 不参会的 role 照常工作。参会 role 如果正在跑 turn，等这一轮结束再投递。

### 4.2 发起与结束

- 用户点"拉会"并选择参会者。
- Manager 只能 `propose_meeting(participants, agenda, attachments)`，议程中写明"我卡在哪里"，由用户一键接受。下层不能直接发起会议。
- 结束由用户点击，或 Manager 提议、用户确认。结束时运行时要求 Manager 跑一轮收尾：
  1. 写入会议中的决定，依据引用用户在会上的发言；
  2. 写收尾消息，原样投递给所有参会者；
  3. 恢复分层。
- 主对话中留下一张收起的会议卡片："会议 · 14:20–14:45 · TL、Worker · 定了 3 件事"，点开可看完整记录。

### 4.3 其他形式

- **一对一**：用户与某个 role 一对一交流，走项目中的直接通路，直接给它发消息（roadmap.md"原则"）。Manager 从事件中得知变化。Inspector 中不另设一对一对话（用户定）。
- **在官方应用中接管**（待排，见 [roadmap.md](roadmap.md)）：Inspector 中点"在官方应用中打开"后，该 role 标记为"已被用户接管"，暂停投递；点"交还"后恢复。运行时只告诉 Manager 接管发生的时段。
- 如果实际使用中发现会上被否决的方案污染了主会话，再改为 fork 方案：会议在各 role 的 fork 中进行，结束后只把收尾消息带回主会话。

## 5. 对外操作

### 5.1 能力裁剪

所有 role 的对外通道（用户的连接器、会绕开 Lobotomy 的内置工具、git push、gh）在启动参数中去掉，见 harness-adapter.md 1.6。

### 5.2 push

v1 中 Lobotomy 不 push。push 与 GitHub 导出的内容范围、触发和批准单独处理（#6）。Manager 可以建议导出，但不执行。

### 5.3 外部系统由 Lobotomy 统一接入

本节未实现，列入 roadmap 待排。

Lobotomy 管理项目的全部状态，包括 GitHub 上的状态。外部系统的连接由 Lobotomy 持有，role 经 Lobotomy MCP 访问，权限集中控制。GitHub 是第一个实例，之后的外部系统沿用同一模式。

- **接入方式**：后端调用 `gh` CLI，使用用户自己的登录，Lobotomy 不读取、不保存 token。原则与 harness adapter 相同：官方 CLI、正常用法。role 进程看不到这份登录（见 5.1），凭据只在后端这一层。
- **权限**：按 role × 动作配置 allow / confirm / deny。默认值：

  | 动作 | Manager | TL | Worker |
  |---|---|---|---|
  | 读 issue、PR、review、CI 状态与日志 | allow | allow | allow |
  | 写（建 issue、评论、建 PR、打标签等） | confirm | confirm | confirm |

- **v1 开放的写操作**：只有建 issue 和评论（例如把暂缓的 TL 意见转成 issue）。v1 不 push，因此不需要建 PR。
- **confirm = 对外操作通道**：role 通过 `request_external_action(kind, draft)` 提交完整草稿。下层的申请先由 Manager 判断是否转给用户，Manager 自己的申请直接到用户。用户在 GUI 中看到草稿原文并一键确认，由运行时执行。
- **审计**：每次 GitHub 访问（读和写）都记入事件日志：哪个 role、什么动作、什么时间。
- **项目状态投影**：后端定期轮询（条件请求，304 不计入额度），关注默认分支与相关 PR 的 CI 状态、新 issue、评论、review。产生的事件机械地投影到 Workboard（如 CI 徽章、新评论数），并作为项目的变化列入 Manager 下次运行时看到的变化，由她决定是否在对话中提起。这些事件不唤醒她，与 §6"Manager 什么时候运行"的唤醒规则一致（用户定）。
- **附件快照**：GitHub 条目被引用为附件时，运行时保存引用当时的快照，确保附件内容就是 Manager 当时看到的内容。

## 6. 通知

**只有状态能触发通知。** Manager 没有通知工具：它会犯错，而且"觉得重要就通知"会让通知不断膨胀。Manager 表达紧急只能通过改变状态，即向用户提问或暂停任务；是否通知由运行时按状态机械判定。

```text
ask_user(question, kind, options?)
  → 问题列进「全部」的"等你决定"，直到用户在提问之后发来的消息送到 Manager
```

- 问题存在 Manager 的数据库中。用户可以在"等你决定"的卡片上直接回复。
- `kind` 是类别（tech-plan.md §5"要你卡"）：`confirm` 确认（授权：花钱、代表用户对外、合并碰到需要用户授权的路径），至少 1 个选项；`choice` 选择，至少 2 个选项；`open` 回答，开放问题，不带选项。选项显示成按钮，点一下就是用户发给她的一条消息，正文是选项，写明回答这个问题（data-model.md §3.5）。确认时，她把这条消息的 ID 当作授权。卡片上总留着输入框，用户可以不选而自己写（用户定）。
- Angela 的问题与执行者的提问共用问题生命周期和消息序号边界（用户授权；data-model.md 的"问题与回复的因果关联"）。用户发给她的后续消息排队时，对应问题暂时不列入"等你决定"；消息绑定到她的 turn 时，问题关闭。提问之前入队的消息只作上下文，不能关闭新问题。多个问题分别判定；她仍需要回答时，再问一次。
- 回答之前不该继续的任务，由她另外调用 `set_paused` 暂停。这是她自己的暂停，她可以恢复（roles-and-tasks.md §4）。依据：问题在她的数据库中，任务在项目的数据库中，一条命令只写一个数据库（data-model.md §10.6 跨库操作第 5 条）。
- 问题带附件（`attachments`）未实现，列入 roadmap 待排。现在她在问题里写明要用户看什么。

系统通知未实现，列入 roadmap 待排。现在窗口标题与托盘只显示"等你决定"的条数（frontend.md §2）。下面的表和规则是系统通知的设计；其中"全员在等你"和"活干完了"的判定已用于唤醒 Manager（见下面"Manager 什么时候运行"）。

运行时在以下情况发出通知：

| 情况 | 判定 |
|---|---|
| 组织离了用户就无法推进 | 每个 role 要么在等用户（决定、对外操作确认、会议提议），要么无事可做。至少一项在等用户时，是"全员在等你"；队列为空、任务全部完成时，是"活干完了" |
| 系统故障 | harness 登录失效、额度耗尽（`rate_limit_event` 被拒）、CLI 崩溃或版本不兼容、执行结果待对账 |
| `flag_mismatch` | 工作可能正沿着错误的解读推进，而且这件事不应由 Manager 决定用户是否看到 |

- 其他情况只更新 GUI，包括进度、CI 通过、部分 role 阻塞而其他 role 仍在工作。
- 用户正在看 GUI 时不弹系统通知；同一状态只通知一次，状态变化后才会再次通知；短时间内的多条通知合并。
- 组织空闲时什么都不运行：role 只在收到消息或任务时运行，Manager 只在下面"Manager 什么时候运行"的三种情况下运行。后台不会有 agent 自行扩大范围。
- **用户回来时看到的消息**（用户定，[#50](https://github.com/vorton-lang/Lobotomy/issues/50)）：
  - 组织进入"全员在等你"或"活干完了"时，运行时把这个状态放进 Manager 的收件箱。Manager 写一条合并的消息，给出可运行的入口、关键变化、同一版本的验证结果和真正待决的分叉。
  - 常规进度可以等到这时合并，不必逐条告诉用户。这一条写进 Manager 的指令。
  - 不新增触发条件。消息写完后发生的变化，由附件的当前有效性标出（§2.1）。
  - 依据：另一种做法是用户回来时再生成。它需要新增触发条件，用户回来后还要等几秒。
  - **系统通知等 Manager 写完这条消息再发**（用户定）。未实现，列入 roadmap 待排。待决问题：Manager 不在或额度受阻时怎样处理。
- **Manager 什么时候运行**（用户定）：
  - 现在只在三种情况下给她登记 turn：用户给她发了消息；某个项目进入"全员在等你"或"活干完了"；某个项目中有 role 调用了 `flag_mismatch`（§2.3）。执行者的进展这类事件不唤醒她。
  - 唤醒条件按设计由 tech-plan.md §4.2 的事件来源表给出，取代上一条的三种情况（用户定，[#86](https://github.com/vorton-lang/Lobotomy/issues/86)）。未实现，顺序见 tech-plan.md §7。
  - "在等你"按项目判定：一个项目进入这个状态就唤醒她，不等所有项目都停下。依据：一个长时间运行的项目，不应该让另一个项目的等待一直没人告诉用户。
  - 她每次运行时，运行时把各项目自她上次读到的位置以来的变化整理后放进她的输入，重点是汇报、执行者的提问，以及用户直接做的操作，例如暂停、修改完成条件。读到的位置按项目记在她的数据库中（data-model.md §10.6 跨库操作第 4 条）。
  - 依据：每次运行都消耗额度，也可能打断用户。常规进度可以等到合并的消息中再说（上一条）。
  - 项目"停下"：没有登记或运行中的 turn，调度器也没有可以启动的任务或可以投递的消息。等用户的 role 和额度受阻的 role 不算可以启动。停下时有"等你决定"的条目，是"全员在等你"；没有条目，也没有未关闭的任务，是"活干完了"。只剩用户暂停的任务时，两者都不算。
  - "进入"这个状态，按变化判断：项目停下，而且她读到的位置之后，有不是她自己造成的变化，才唤醒她。告诉她之后，位置前移，同一件事不再唤醒她。依据：运行时自己的工作会让项目短暂地不处于停下状态；按状态翻转判断，每次重启都会再唤醒她一次。她自己的操作，她已经知道。
  - 她第一次看到一个项目时，位置从这个项目当前的事件开始，不唤醒她。她的 turn 正在运行时什么都不告诉她，留到下一个 turn。
