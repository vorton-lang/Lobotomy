# 维护小组手册

> Status: 维护小组沉淀下来的共识，按"碰到什么情况"组织：什么做法好，要注意什么。它不是操作流程，也不规定谁在维护时必须做什么。

## 碰到待验收的改动

外部流程修 main 上 CI 失败开的 PR、别人的审查分支，都属于这一类。

- 看四件事：改动只做了它该做的事；符合 notes/ 中的设计；测试和文档的体量与修复相称；PR 的 CI 通过。都满足就 squash 合并。
- 看整个 diff 的构成，不只看修复本身。#91 的修复约 90 行，却带了 500 行测试、18 个文件的注释改写和一份审查报告；只看修复会误判它"克制"。
- 外部流程开的 issue，按设计问题对待。
- 审查报告里的未决项，并进对应的 notes（例如 tech-plan.md 的已知缺口），不单独留一份带日期的报告：它会随修复过时。

## 碰到要合入 main

- 自己的改动在本地通过受影响的测试后，直接推送到 main，不开 PR，也不等 PR 的 CI。合进 main 后，CI 会把同样的测试再跑一遍。
- 审查别人的分支时走 PR 合入，CI 只跑这一轮。

## 碰到要等 CI

- 不停下来等。把等待放到后台，例如 `gh run watch <run id> --exit-status`，先做下一件事；没有下一件事时，先说明 CI 正在运行。
- 连续推送时，旧的 run 会被取消，`ci-ok` 显示为失败。先看 run 的结论是不是 cancelled，再判断是不是真的失败。
- 只改文档的推送不触发 CI（`.github/workflows/ci.yml` 的 `paths-ignore`），也就不会取消正在跑的 run。

## 碰到 main 上 CI 失败

- 不用自己修。外部流程每小时检查 main 上新的 CI 失败：普通问题修好后开 PR，不简单的问题开 issue。

## 碰到罕见故障要验证

- 不靠推演和加测试。由 Dot 定期演练：频次低，单次可以昂贵；Dot 有 GUI，能直接看界面。演练项目见 tech-plan.md §7"演练"。
- 演练中发现的问题算真实出现过的问题，按 AGENTS.md"加测试前"处理。
