## 0. 目标与边界

**目标**：把界面从"开发者临时凑的"变成能长期使用的工作台。先做主路径：与 Angela 的对话、"等你决定"、任务面板。

**边界**：

- 不改业务语义、命令与后端协议。P0–P6 只改前端；P5 的自绘标题栏另改 Electron 主进程。
- 改变行为的改进不在本专项中，排进 roadmap.md 待排（§6）。
- 不改通知规则。系统通知不在本计划内（roadmap.md 待排的"通知"）。
- 性能约束不变（frontend.md §0、§4.2）。
- 与 M4 的验收并行。P0、P1 只改外观，不改变验收要看的行为。

## 1. 现状审计

方法：`e2e/screenshots.spec.ts` 用真实后端加假 Codex 截项目视图、任务面板、设置与暗色；另用模拟的 WebSocket 临时截了「全部」（Angela 的对话、四类"等你决定"、共识）。窗口 1400–1440 × 860–900。

**视觉**

- 层级平。正文、区块标题、卡片标题都在 12–14px，粗细接近。
- 间距没有设计变量，个别 padding 不在 §3 的刻度上，例如 3px、40px。字号、圆角与阴影在 P0 中已改为设计变量。
- 链接与"已转给"仍用强调色（P2）。
- 用户的消息是 85% 宽的浅蓝块，Angela 的回复是带边框的卡片。宽窗口中一行超过 80 个汉字。
- "等你决定"、Workboard、共识、附件都是同一种 1px 边框加 8px 圆角的框，分不出主次和类型。
- 设置页（Primer 式）是现在最整齐的一页。

**信息与交互**

- 主对话中露出内部词汇："turn 正常结束"、"调用 lobotomy.assign"、"（item_3）"、"基于集成版本 base0000 · 检查设置第 2 版"。其中一部分是有意的：附件写明版本是可争辩性的要求（manager-actions.md §2.1）；"turn 正常结束"是为了不与任务完成混淆（frontend.md §7.3）。要改的是层级，见 §2 原则 5。
- "等你决定"的四类条目（问题、额度、验收、受阻）长得一样，只有额度是黄色。卡片没有时间，也没有"新"的标记。
- 任务面板中「验收」「退回…」「暂停」「放弃」并排，样式相同。「放弃」点一下就执行，没有确认。交付说明、你的原话、完成条件、验证、改动、记录用同一级标题。
- 顶栏一直显示"● 已连接"，但只有断线时才需要它。
- toast 在底部正中，压在输入框上。
- 空状态只有一行居中的灰字。
- 没有键盘入口切换项目或打开任务。

## 2. 原则

1. **三种来源，三种样式。** roadmap.md 的原则"事实、权威、判断分开"在界面上要看得出来（调研 §2.5）：
   - 判断：Angela 与各 role 的话。正文样式，带角色头像。
   - 权威：你的原话。引用块，写明时间。
   - 事实：运行时写的附件、版本、"已转给"。元数据样式，带图标，可以点开；不用角色颜色。
2. **只有要你动手的东西醒目。** 运行中只有一个会动的点；"等你"用琥珀色；红色只给失败。依据：调研 §1.4 第 1、4 条，§2.2。
3. **先结论，证据一步可达。** 卡片与任务面板先写这件事对目标意味着什么、要你决定什么；证据在原处展开，不跳到别的页面。依据：调研 §2.1 的 Endsley 与 ParallelPilot，§1.5 的审查顺序。
4. **位置稳定，变化加标记。** 用户离开期间，列表不重新排序；新出现的条目加标记。依据：调研 §2.3。
5. **内部词汇降级，不删除。** turn、ID、提交号、检查设置的版本仍然可以看到，但放在次要层级：元数据行、悬停或展开。可争辩性需要它们，日常阅读不需要。范围见 §7 第 1 条。
6. **零运行时成本优先。** token、系统字体、CSS 动效。新依赖只有 lucide-react 与 Base UI 的少数组件，每加一个都记录包体积。

## 3. 视觉方向

依据调研 §3。下面是起点，具体数值在 P0 中按截图调整。

- **基调**：暖灰、低饱和，结构靠底色分层，少用线条（Linear 2026、Conductor）。
- **分层**：侧栏比主区暗一档。卡片去掉大部分边框，用底色区分。阴影只给浮层：任务面板、弹窗、菜单、toast。
- **强调色**：只用于主按钮与焦点环。选中项用中性色的底；链接用正文色加下划线。
- **颜色体系**：中性色与强调色各 12 级，直接取 Radix Colors 的色阶值（中性色 sand，强调色 indigo），按 Radix 的分工映射成语义 token（背景、元素、悬停、按下、边框、文字）。不另用 OKLCH 推导，因为 Radix 的亮暗两套已经调校过。亮色与暗色各一套；暗色不用纯黑，表层越高越亮。
- **刻度**：
  - 间距 2 / 4 / 6 / 8 / 12 / 16 / 20 / 24 / 32px。
  - 圆角 4（标签、按键提示）/ 6（按钮、输入框）/ 8（卡片）/ 12（弹窗）。
  - 阴影 2 级：面板与菜单一级，弹窗一级。列表行与卡片不用阴影。
  - 字号 12（元信息）/ 13（列表、侧栏）/ 14（正文）/ 16（区块标题）/ 20（页标题）。中文段落行高 1.6–1.7。
  - 字重只用 400 与 600。雅黑 UI 没有 600，中文会显示为粗体，接受这一点。
  - 时长 100ms（悬停、按下）/ 160ms（菜单、提示）/ 220ms（面板），一条 ease-out 曲线；减弱动效时归零。
- **字体**：系统字体，不捆绑字体文件。
  - 界面：`"Segoe UI Variable Text", "Segoe UI", "Noto Sans", "Microsoft YaHei UI", "Noto Sans CJK SC", "Source Han Sans SC", sans-serif`。雅黑 UI 排在 Noto CJK 前，避开 Windows 100% 缩放下的发虚。
  - 等宽：`"Cascadia Mono", Consolas, "DejaVu Sans Mono", "Microsoft YaHei UI", "Noto Sans Mono CJK SC", monospace`。
  - 消息正文开 `text-autospace`，代码、路径、diff 中关闭。
- **图标**：lucide-react，16px，描边 1.5，只用具名导入。只用在导航、工具栏按钮与状态标记上，正文不放装饰图标。
- **状态**：5 种外观，每种都由形状、颜色、文字共同表示（调研 §3.5）。文字沿用 `format.ts` 现有的说法，外观只是归类：

  | 外观 | 形状与颜色 | 现有状态 |
  |---|---|---|
  | 运行 | 实心点，缓慢脉冲，蓝 | 正在跑 turn、即将开始 |
  | 等你 | 空心环，琥珀 | 停下等你决定、待验收、Angela 的问题 |
  | 失败 | 三角，红 | turn 异常结束、项目打不开 |
  | 完成 | 对勾，绿 | 已完成 |
  | 静止 | 灰点 | 空闲、排队、暂停、已放弃、回复在排队 |

- **角色身份**：每个 role 一个固定颜色，从 6 个色相中选。头像是名字的首字母加色底。按名字固定分配，未知的名字按名字取色。用户不加头像。

### P2 对话

进行中。"内部词汇"一项完成（2026-10-13，在 Lobotomy-dogfood 中由 Angela 派给 Malkuth，用户验收），现状见 frontend.md §7.3。

- **版式**：

- **输入框**：
  - 高度随内容增长，有上限。
  - 显示现在的按键：Enter 发送，Shift+Enter 换行。
  - 回复的对象显示为输入框上方的一个标签，可以取消。
  - 发送按钮改为图标按钮，禁用时不再是一大块浅色。

### P3 等你决定

- **按类型区分**。每类一个图标与颜色：
  - 要你回答：Angela 的问题、执行者的问题。
  - 出了问题：turn 没能启动或异常结束、任务受阻、额度不足、没人推动的任务。
  - 等你验收。
- **卡片结构**：
  - 第一行：类型图标、项目、多久以前。
  - 第二行：一句话写要你决定什么。
  - 右侧：主操作。
  - 原始错误、路径列表等收起。
- **分组与排序**（§7 第 2 条）：「全部」与项目中都按类型分组，依次是要你回答、出了问题、等你验收。每张卡片标出项目；Angela 的问题标为"Angela"，额度受阻标为"本机"，仍只算一条（data-model.md §10.5）。同一类型中按项目排序，同一项目的卡片相邻。顺序的理由：回答问题最快就能让工作继续，验收要看证据，花的时间最长。
- **卡片上不加「验收」按钮。** 同类产品常在卡片上放"一键下一步"；验收应当发生在看得到证据的任务面板中（§8 第 3 条）。现在的「查看并验收」打开任务面板，保持。

完成标准：e2e 中关于"等你决定"的测试按新文案更新后通过。

- "离开期间发生了什么"的汇总不在本专项中，它属于 #50 的问题。

## 5. 做法

1. 每个阶段拆成几个提交，按 [maintaining.md](maintaining.md) 直接推 main。只改样式的提交，本地运行 `npm run typecheck`、`npm test` 与受影响的 e2e。
2. 改动前后用截图场景各截一组，生成本地 HTML 对照页给用户看，不发布到网上。P0 与 P1 完成后先给用户看一次，方向认可后再做 P2。这一条已满足：用户看过 P0、P1 的对照页，认可方向。之后每个阶段完成时都附对照页。
3. 无障碍名称尽量不变，因为 e2e 用它们定位。文案变了的，在同一个提交中改测试。
4. 新依赖记录 `vite build` 前后的产物大小。
5. 改了对话渲染的提交，看 CI 的 bench 摘要（AGENTS.md）。

  - 动画库（Motion 等）、Storybook 或 Ladle、捆绑 CJK 字体。
  - 数字置信度、自主度滑杆（调研 §4 第 2、3 条）。
  - 看板形态。
- **排进 roadmap.md 待排**（用户确认，2026-10-12）。它们改变行为，不在本专项中：
  - 撤回或修改排队中的消息（§8 第 9 条）。
  - 在编辑器中打开候选成果（§8 第 5 条）。
- **以后再议**：验收时记录看过哪些证据（调研 §4 第 7 条）。

## 7. 决定（用户确认，2026-10-12）

1. **内部词汇降级。** 范围见 P2"内部词汇"。异常结束、过期、被取代仍然醒目。
   **语义更新**：frontend.md §7.3 写的是正常结束的 turn 显示为"turn 正常结束"，理由是不与任务完成混淆。现在正常结束的 turn 只显示时间：不写文字，同样不会被读成任务完成。P2 实现时改 §7.3。
2. **"等你决定"按类型分组。** 「全部」与项目中都一样，排序与卡片标注见 P3。
   **语义更新**：frontend.md §2 原来写的是「全部」按项目分组。依据：
   - 两种分组的条目数相同，差别在首屏放什么。按类型时，最急的两类总在最上面；按项目时，排在后面的项目里的失败可能在首屏之外。
   - 按项目分组的好处是同一项目的事连着处理。「全部」中项目的卡片只有「前往」，处理在项目中进行，项目的右侧栏本来就只列这个项目的条目，所以这个好处不会丢。
   - "按目标组织信息"由左侧的项目列表承担：每个项目有状态与条数。
   - 同类产品都把"等你回答"与"等你验收"分开，并把需要你的排在最上（调研 §1.4 第 2、3 条）。
3. **"回来"的提示放进本专项，即 P6。** 只在前端做，不改后端，也不加 Angela 的判断。依据：这是 #50 的第一优先级"降低用户回来恢复工作现场的成本"中，运行时可以确定的那部分；标记只依据用户看过什么、什么是新的，不涉及 #50 的三组开放问题。

## 8. 同类产品的痛点在这里是否成立

开始前先检查同类产品用户的主要痛点（用户要求，2026-10-12）。证据与来源见调研 §1.6。下表按证据强度排序。

| # | 痛点 | 在 Lobotomy | 处理 |
|---|---|---|---|
| 1 | agent 谎报完成、静默卡住 | 大半已挡住：完成由用户验收决定，不由 agent 说了算（运行时的验证随 #86 退出）；没有报告就结束的 turn 进"等你决定"。没挡住：turn 卡住时没有信号；检查命令覆盖不到的地方，报错可能被压掉 | P1"多久没有新输出"（P4 的结论条随 #86 退出）。模型行为本身不归界面 |
| 2 | 额度意外耗尽 | 成立，并行会放大。现在只有"额度不足"卡片与重置时间，看不到余量 | 需要后端数据，官方 CLI 能给出多少待查。不在本专项 |

**重点关注**（与项目的价值观最一致，依次）：

1. 出处与转述（第 6 条）：对应"事实、权威、判断分开"与可争辩性。别家编排者最严重的抱怨，正是我们的结构要解决的；界面上看不出来，等于没有。
2. 审阅不走过场（第 3、10 条）：对应"保留有价值的认知摩擦"与"只发布验收过的成果"。
3. 回来时接得上（第 8 条）：对应 #50 的第一优先级。
4. 状态诚实（第 1 条）：对应"事实与判断分开"。
5. 注意力（第 4 条）：P1、P3。

对编排者的直接抱怨只有十几条，因为真正上线编排功能的产品还少。第 6 条排第一，理由是它与设计核心重合，而且这些抱怨描述的失败方式很具体，不是因为数量多。
