# Lobotomy 技术方案

本文是 [#86](https://github.com/vorton-lang/Lobotomy/issues/86) 的技术方案。已定和待决的事项都列在 §8。它不是实现规格。worker 部分的展开见 [worker-interface.md](worker-interface.md)。

依据是 2026-10-16 的五路资料调研（隔离、worker 抽象、forge 与登录、图与编排、界面）和现有代码的盘点。资料调研没有做实测；凡是"实测"的地方都要另外验证。

术语：personal agent 即 Angela；worker 指接下一件事、交回一个交付物的执行者；"事情"指一件持续推进、会转向的事；forge 指 GitHub 这类代码托管平台。

## 0. 原则（用户定）

1. 系统要灵活。由强的 personal agent 配合运行时工具约束 worker；不卡 personal agent，也不卡用户。
2. 硬关卡放在标准治理上：分支保护、必过 CI、PR。Lobotomy 不自己做快照、合并和分支。
3. Lobotomy 专注宏观编排，做事的能力放在 worker 抽象后面。
4. 用计算资源换开发上的简单。
5. "没有 Angela 也能跑"不是设计目标。没有她时，系统在逻辑上仍能运行，只是很难用。

## 1. 分层

```
人 ── 界面（会话 + 工作台 + 事情列表）
        │
     Angela（理解、拆分、判断、合并决定）
        │  图工具 / 事件 / 消息 / 资源
     编排层（Lobotomy 后端：图、事件队列、消息投递、额度与机器指标）
        │  worker 接口
     worker（环境 + 官方 CLI）── forge（PR、CI、合并） / 外部
```

- Lobotomy 自己实现：界面、编排层、worker 适配（adapter 与环境准备）。
- 借用现成的：版本管理与合并（git 加 forge）、CI、CLI 本身。

## 2. worker

### 2.1 抽象在 task 级

一个 worker 接一件交代完整的事，交回一个交付物。它内部是一个 CLI 会话，还是再分派给子 agent，Lobotomy 不依赖。

- 理由：用户说的"交代完整"有四项：要解决什么、能动什么、做到什么算交差、何时回来问。这是 task 级的契约。
- 抽象在"一个 CLI 会话"太低：Lobotomy 仍要管各 CLI 不一致的中断语义、环境和 CI 循环，而这正是要卸下的部分。
- 抽象在"能再分派的小团队"太高：它和 Angela 的拆分职责重叠，嵌套拆分会放大改动面。问题也会在层间丢失，例如 Claude Agent SDK 的 subagent 不能向用户提问。
- v1：一个 worker 就是在自己 clone 里运行的一个 Claude Code 或 Codex 会话，由 adapter 包装成 task 级契约。现有的 harness adapter、进程管理和 turn 记录可以复用。

### 2.2 接口（沿用现有 `assign` 的字段）

| 部分 | 内容 |
|---|---|
| 输入 | 用户原话与 Angela 的解读；材料（仓库与基线，或文档）；允许的动作（含"开 PR"）；`done_when`（代码任务要求 CI 通过）；`stop_when`（时间、轮数、改动规模）；`ask_when`（哪些情况停下来问）；环境引用 |
| 干预 | 只承诺两个原语。一是追加消息，回执写明它进了哪个 turn。二是停止，以进程确认退出为准。改需求 = 停止 + 新 attempt + 新的完成条件版本。暂停不做成 worker 原语 |
| 产出 | PR 地址与 head SHA，或报告的位置；自述：做了什么、没做什么、做了哪些假设；CI 链接；改动规模。`done` 只表示候选 |
| 求助 | `blocked` 是一等状态，带问题和选项，等待期间不计预算。不阻塞的猜测写进产出里的"假设"。不设"超时后自动继续" |
| 结束 | 终态：delivered、blocked、failed、stopped、budget_exhausted，各带原因。旧 attempt 迟到的结果不生效 |

- CI 结果由运行时从 forge 读取，不采信 worker 的自述。依据：worker 改测试、谎报通过是强证据的痛点。
- 审查负担是最强的痛点。dotnet/runtime 的数据：1–50 行的 PR 成功率 76–80%，101–500 行降到 64%。所以任务要拆小，这由 Angela 负责；运行时统计改动规模，交给她看。这与用户"改动面越小冲突越少"的判断一致。
- **worker 和记忆（用户定，来自 #22）**：
  - worker 不读图。必需的约束在创建任务时随任务输入带全；缺信息时，worker 报 blocked 提问，或由 Angela 补一条消息。理由：worker 是外部的、可替换的，开放查图会把图的 schema 变成对外接口；而且库是全局的，工作和生活都在里面，不应暴露给第三方 worker。
  - 代码库的知识（怎么跑、关键入口、踩过的坑）写在仓库自己的 AGENTS.md、notes 等文件里，和代码一样走 PR。图管事情和理解；需要时按「来源 + 路径 + 版本」引用仓库文档，不复制进图。
  - CLI 自带的记忆保持关闭。Lobotomy 给所有 role 设了 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`（`agent/src/capability.rs`）。Claude Code 的 auto memory 记的是用户偏好、纠正、代码推不出的项目决定和外部资料位置，正是图的内容；它按 git 仓库分目录，每个 clone 各一份，开着只会让各 worker 的记忆互相分叉。官方文档没有给开关它对效果影响的数据，本项目也没有实测。

### 2.3 环境：默认 L0 + L1

| 级 | 做法 | 解决 |
|---|---|---|
| L0 | 每个 worker 一个独立 clone。不用 git worktree：并发 `git worktree add` 会抢 `.git/config.lock` | 文件、分支、ref |
| L1 | 每个 worker 单独设 TMP/TEMP/TMPDIR、`GIT_CONFIG_GLOBAL` 和一个端口段变量（参照 Conductor，每个 workspace 10 个端口）。在现有 Job Object（Windows）或进程组（Linux，`systemd-run --user --scope -p MemoryMax=`）上加内存上限 | 临时文件、git 配置、端口（靠约定）、内存 |

- CLI 的登录目录和下载缓存（cargo registry、pnpm store）保持共享，这些缓存自带锁。构建产物放在各自的 clone 里。
- L2（OS 沙箱）在 Windows 上不可行：Claude Code 的 sandbox 不支持原生 Windows，Windows Sandbox 不能多开，也都隔离不了端口。所以 Windows 和 Linux 都能用的下一级是 L3：容器、WSL 或 VM，或者直接上独立机器。
- 什么时候升级：
  - 项目的端口、数据库或 compose 名称写死，没法参数化：这个项目用 L3。
  - 实际出现 worker 写进别的目录：上 L3。
  - 有了内存上限，内存或磁盘仍持续紧张：换服务器或 VM。
  - 凭据冲突：隔离解决不了，只能降低并发。
- Lobotomy 自己的仓库：`vite.config.ts` 设了 `strictPort`，`playwright.config.ts` 设了 `reuseExistingServer: true`。端口固定时，两个 worker 同时跑 e2e，第二个会测到第一个的前端。所以前端开发服务器与 e2e 的端口取自 `LOBOTOMY_PORT_BASE`（#89）。

### 2.4 登录与合规

- **Claude Code**：官方合规页允许"用户用自己的订阅登录原版 Claude Code，包括由平台托管运行"，同时规定开发者"不得收集、存储或中转 claude.ai 的凭据或会话 token"。所以：
  - Lobotomy 不保存、不分发 Claude 的登录 token。
  - 本机的 worker 共用用户本机 CLI 的登录，现在就是这样。
  - 在服务器上，由用户自己登录。
- 已知风险（用户报告）：多个会话并发刷新 token 时会互相顶掉；在 Windows 上并发写会损坏 `.claude.json`，2.1.61 修过。这会限制 Claude worker 的并发数，需要实测。
- **Codex**：官方明确说不要把同一份 `auth.json` 给并发任务或多台机器共用，因为 refresh token 只能使用一次。同一个 `CODEX_HOME` 下多个会话并发的表现，官方没有写明，需要实测。
- **OpenCode**：Codex 负责人在 X 上公开说正在和 OpenCode 合作，支持用户用 Codex 订阅；我没找到条款层面的文字。列为待研究项。

## 3. forge 与治理

- **身份**：用户自己的仓库用 GitHub App。
  - App 免费创建，可以装在个人账号上，只选部分仓库。
  - installation token 1 小时过期，签发时可以收窄到指定仓库和权限。
  - App 私钥是 Lobotomy 自己的凭据，不是 claude.ai 的，可以保存。后端按 worker、按仓库签发 token，经 `GH_TOKEN` 或 git credential helper 交给 worker。
  - 提交作者用 bot，提交说明里加 `Co-authored-by: 用户`。
- **对别人的仓库提 issue 或 PR**：App 做不到，只能用用户本人账号或 machine user。这属于"代表用户对外"的动作，需要单独授权（用户定）。
- **合并治理**：
  - 分支保护：required checks 加上 "Require branches to be up to date"。
  - 个人仓库没有 GitHub merge queue（只有组织名下的公开仓库有）。替代做法是由后端串行执行"更新分支 → 等 CI → 合并"。
  - 组织名下的公开仓库可以用 merge queue，Lobotomy 本身就是。用的话 CI 要加 `merge_group` 触发。
  - 需要 rebase 时，由 worker 在本地 rebase 后用 `--force-with-lease` 推送，冲突交回 worker 处理。
- **合并决定**：CI 通过后由 Angela 决定。用户随时可以否决或接管。哪些 PR 必须给用户看，列为待决问题。
- **私有仓库的成本**：分支保护需要 Pro；Actions 在 Free 计划下每月 2000 分钟。公开仓库的标准 runner 免费，包括 Windows 和 macOS。CI 的 runner 已经能验证三个平台；能交互复现问题的环境往后放。
- **自托管可替换**：Forgejo 和 Gitea 没有 GitHub App 的对等物，bot 就是一个普通用户；Actions 兼容性 Gitea 更好。接口按四个操作抽象：bot token、开 PR、读 checks、合并。先只实现 GitHub。
- **非代码的交付物不走 forge**：存进 Lobotomy 现有的文件库（按内容哈希寻址，data-model.md §7.3），图里的 artifact 节点引用它。

## 4. 编排层

### 4.1 图

- **存储**：全局一个 SQLite 数据库（用户定）。理由：仓库不是一等对象，按项目分库会让跨事情的边、附件复制和跨库操作都变复杂。未实现：现在仍按项目分库（data-model.md §10.6），全局库在第 2 步做，见 §7"第 1 步的范围"。
  - 库里加 `node` 和 `edge` 两张表，配 FTS5。
  - 不引入图数据库：Kùzu 已于 2025-10 归档，DuckPGQ 自称研究项目，SurrealDB 用的是 BSL 许可。单用户、万级节点、1–2 跳的查询，用递归 CTE 就够了。
  - 代价：一个库坏了影响全部数据，所以要定期在线备份，例如用 `VACUUM INTO`。大内容继续放在文件库里。归档只标一个状态，不移走数据目录。
- **节点 8 类**：
  - `thread`：事情。它是看问题的视角，不是边界。
  - `goal`：目标。
  - `claim`：可修改的理解，带 `firmness`，取 guess、working 或 settled。
  - `question`：待定的问题。
  - `observation`：观察到的事实，例如用户原话、worker 结果、外部变化。不可变。
  - `action`：已发生的动作。不可变。
  - `step`：具体的下一步或等待，带 `resource`，取 user、agent、external 或 time。
  - `artifact`：材料或成果，带 `adopted`。
  - 对外承诺很少，不单列一类：用一条 `action` 加一个带 `owed_to` 的 `step` 表达。
- **边 8 类**：
  - `part_of`：节点属于某件事情，可以同时属于多件，事情之间不硬切。
  - `serves`：指向目标。
  - `blocks`：唯一影响队列的边。
  - `bears_on`：证据，带 ±。
  - `answers`：理解回答问题。
  - `derived_from`：来历。
  - `supersedes`：新节点取代旧节点，写明理由。
  - `relates`：自由标签，用来放各种异质关系。
- **属性约定**：
  - 来源：user、manager、role、runtime 或 external，加上 turn ID。
  - 依据：来源 ID 加复制的原文，沿用 data-model.md §10.6 的做法。
  - 系统得知的时间；可选的现实有效期 `valid_from` / `valid_until`。
  - 失效：`retired_at` 和原因。
  - 指向项目记录的 `ref`。
- **核心存什么、什么触发执行**（用户定，#86 评论）：
  - 仓库和代码的版本管理归 worker 环境。核心保存事情、理解、关系、委派、证据和自己的材料。外部已有版本管理的材料，核心只存「来源 + 对象 ID + 版本 ID」的引用，不重复做一套 VCS。
  - 节点和边允许自由属性，由 agent 填写，用来辅助理解和记忆。
  - 会触发运行时行为的只有 step/resource、blocks、`due_at`。普通关系和自由属性不隐式触发执行。worker 的动作由显式工具发起。
- **step、阻塞与等待**（用户定）：
  - step 只存三个状态：`open`、`done`、`dropped`（带理由）。`done` 和 `dropped` 可以重开，也要写理由。"被阻塞""在做""在等"不存，每次现算。改状态的是 Angela（`step_set`）和用户。运行时只在 time 类的 step 到了 `due_at` 时把它标为 `done`。worker 任务被采用时，运行时只发事件，不改 step，因为一个 step 可能拆成了几个任务。
  - 只有 step 能被阻塞，阻塞者是 step 或 question。阻塞者 step 标为 `done`、阻塞者 question 有了答案或被 retire、这条边被 retire，这条阻塞就解除。阻塞者被 `dropped` 不算解除：运行时发事件给 Angela，由她改计划。多条阻塞全部解除才算解除。`plan` 拒绝成环。解除只唤醒 Angela，不自动派 worker。
  - 不单设 `wake_on` 字段。"等什么"用 blocks、`due_at` 和固定的事件来源表达，见 §4.2。外部等待在 v1 由 Angela 设 `due_at` 定期复查；以后可以做成一种盯住外部条件的 worker 任务。周期性的复查不做，由 Angela 处理完一个 time step 时自己建下一个。
  - 自由属性是一个限大小的 JSON 对象。`assert` 返回同类节点已在用的键，让属性名趋于一致。运行时不读自由属性。
- **读写分离（用户定）**：思路来自 #86 评论引用的帖子中"编译"的说法；记的是 Lobotomy 的引申，不是原帖验证过的方案。
  - 写入侧表达变化：新增判断、补依据、撤回关系、修订决定。读取侧按需要组织：一件事的现状、阻塞点、依据和可推进项。图是两者之间的中间表示。
  - 自然语言对应哪个对象、意味着什么变化，由 Angela 判断。意思写入之后，到读取视图的转换全部由程序机械完成：取有效版本、过滤已撤回的关系、计算阻塞、沿来源取证据。
  - Angela 默认只读编译出的视图，不拿原始的节点和边。视图的每一行都带对象 ID 和来源引用，可以回查。视图现算、不存，不另起一份单独维护的事实。
  - 界面的事情简报与 Angela 读的 `thread_brief` 由同一个编译器生成，只是渲染不同。用户看到的就是她读到的。
  - 理由：测试期 Angela 用 `deepseek-flash`（§4.5）。弱模型用通用的增删节点、连边工具，容易连错边、建重复节点；让它自己过滤失效、计算阻塞也容易出错。固定语义的写入操作加编译视图，减少模型的自由度和需要它推理的地方。这属于运行时补强，不是加关卡。
- **Angela 的工具**（用户定，#86）：不给通用的增删节点、连边工具，也不给邻居查询（`graph_neighbors`），由阻塞链和依据链代替。
  - 写入：每个操作是一条只追加的变化记录，机械地编译成节点和边。
    1. `assert`：新增判断、目标、问题或下一步，带确定程度、依据（消息 ID 或节点 ID）和作用范围，可选指向的目标、回答的问题。同时返回相似的旧对象，由她决定连接还是取代，不自动合并。编译成新节点，加 `part_of`、`derived_from`、`serves`、`answers`。
    2. `support` / `contest`：补依据，正向或反向。编译成带 ± 的 `bears_on`。
    3. `retract`：撤回判断或关系，写理由。编译成 `retired_at`。
    4. `revise`：修订，写理由。编译成新节点加 `supersedes`。
    5. `plan`：给下一步设前置条件、`resource` 和 `due_at`。编译成 `blocks` 和 step 的字段。
    6. `step_set`：推进、放弃、重开下一步，写理由。
  - 读取：编译出的视图。
    1. `thread_brief`：事情现状。按预算投影：目标、有效的判断及其为何改变、待定问题、可做的和在等的下一步、采用中的成果。根事情"关于用户"的 `thread_brief` 就是用户档案。
    2. `queue`：可推进项，按资源分组，列出没有被阻塞的下一步。
    3. `blockers`：阻塞链，一个下一步为什么卡住、卡在谁身上。
    4. `evidence`：依据链，一个判断沿来源一直追到用户原话或观察。
    5. `changes`：自某个时刻以来的变化。会话轮换后的开头和用户回来时的接续都用它。
    6. `graph_find`：按文字、类别、事情、确定程度查，返回视图行，不返回原始节点。
    7. `graph_get`：按 ID 读一个对象，用来往下钻。
- **谁来维护**：
  - Angela 显式写入，不从对话中自动抽取。依据：Graphiti 和 Mem0 的自动抽取贵，收益小。
  - 和运行时事实对应的节点（例如 worker 任务的状态），由运行时机械投影，避免状态腐烂。
  - 图是 Angela 唯一的计划面。依据：Codex 把内置的计划工具改成默认关闭，有第三方解读认为原因是两个计划面的状态会漂移。
- **账本平滑迁移**：
  - 现有的 `ledger_entry` 就是 node 表的一个子集：goal → `goal`；decision、constraint → `claim(settled)`；hypothesis → `claim(guess)`；open_question → `question`。
  - `supersedes` 和"一条只被取代一次"的规则都保留。
  - 迁移要做的是加 edge 表、扩充 kind。
  - 语义变化：默认的确定程度改为 working（暂时认定），settled 很少用。这对应"多数判断是暂时认定"（用户定）。
- **来自 #22（用户定）**：
  - **引用与"依据已变"**：
    - Angela 派任务或发消息时按 ID 引用 claim，运行时原样插入原文，沿用现有 `assign` 的 `ledger` 参数（manager-actions.md §3.4）。每次引用由运行时写成一条"任务 → claim"的边。
    - 被引用的 claim 被取代或失效时，运行时把引用它的活跃任务标为"依据已变"，并唤醒 Angela，事件里列出这些任务。沿 `derived_from` 往下游传递，深度不超过 2。
    - 这个标记现算、不存。当前的 attempt 或之后发给这个任务的消息引用了新的 claim，或者 Angela 写明理由表示"不影响"，标记就消失。用户在界面上能看到它。
    - 同一件事情里没被引用的 claim 改了，只在事件里列出可能受影响的任务，不打标记。
    - 运行时不自动给 worker 发更正。用 `revise` 还是 `send_message`，由 Angela 判断。
    - 局限：用户纠正了，而 Angela 没有改 claim，这一层管不到。
  - **作用范围**：`part_of` 的目标可以是事情或 step。只在某个任务有效的条目 `part_of` 那个 step；现有账本中项目级的条目 `part_of` 对应的事情；用户级的条目 `part_of` 初始化时建好的根事情"关于用户"。不用"没有 `part_of`"表示全局，因为那和忘了挂分不开。局部的选择不自动升级；要升级，由 Angela 在更大的范围新建一条 claim，用 `derived_from` 指回原来那条。`thread_brief` 带上这件事情和它活跃 step 上的条目；Angela 新会话的开头带上根事情的条目。
  - **幂等**：每个写图的工具都带调用方生成的请求 ID，同一个 ID 重试时返回同一个结果。迟到的旧写入由"一条只被取代一次"拒绝。
  - **历史版本**：
    - 历史由变化记录编译出来，不用 SQLite 触发器把旧值写进历史表（用户定，#86）。理由：两种做法满足同一个要求，而变化记录本来就是写入侧的形式（见上文"读写分离"）。
    - 变化记录只追加，不改、不删。节点表和边表是由变化记录编译出的当前状态，可以增量维护。Angela、用户和运行时的写入（包括运行时机械投影的事实、step 的状态、自由属性、artifact 的 `adopted`、事情的标题）都是变化记录，各带来源和 turn ID。
    - "某个时刻的图"就是把变化记录编译到那个时刻为止。"她这一轮改了什么"就是这一轮的变化记录，界面可以按 Angela 的 turn 回看。
    - 回看是只读的。"回到"某个旧版本做成用户发起的一组新写入（取代、重开、retire），历史照样保留。observation 和 action 是已经发生的事实，不回退；已经跑过的 worker 也不回退。
    - 变化记录要从建库起就有：没记下的历史，以后补不回来。
  - **证据的保留**：复制进节点的原文永久保留。托管在 forge 上的证据（例如 CI 日志）只存链接，保留期跟随 forge；GitHub Actions 的日志默认保留 90 天。文件库里的 blob，只要还有没失效的节点引用它，就一直保留。引用的东西已经拿不到时，标为"原文已不可得"，不拿摘要顶替。v1 不按时间清理；没人引用的 blob 怎样回收，以后再定。

### 4.2 事件与唤醒

- 新增一张待处理事件表，键是事情或下一步的 ID。
  - 同一个键的多次变化合并成一次，只给当前状态，做法同 k8s workqueue。
  - Angela 的 turn 开始时，运行时一次取走全部待处理事件；turn 运行中到达的事件先排队。
  - 等待用下一步表达：带 `due_at`，或被 blocks 阻塞。不单设 `wake_on`（§4.1）。
- 唤醒 Angela 与打断用户是两件事。是否打断用户，由 Angela 判断。
- 事件来源固定为下面几种，各按所列的键合并（用户定）。`due_at` 对 time 类的 step 是"等到"，对其他类是"到期提醒"，只触发一次；重启时已经过期的，也只补触发一次。

  | 事件 | 合并的键 |
  |---|---|
  | 用户的消息或界面操作 | 事情 |
  | worker 任务进入要关注的状态：delivered、blocked、failed、unknown | step 或任务 |
  | step 解除阻塞 | step |
  | 到了 `due_at`，step 仍未完成 | step |
  | 阻塞者被放弃 | 下游的 step |
  | 额度恢复 | 额度域 |

### 4.3 消息

- 区分三种状态：已保存、已投递（进了哪个 turn）、对方已按它调整。现有消息的"排队、已绑定、已投递"可以沿用。
- 对外动作的结果未知时，先查证再决定是否重试。例如开 PR 时断线：先查 PR 有没有建成。

### 4.4 资源

- **订阅额度**：把余额、重置时间和消耗速度交给 Angela，在现有额度域的基础上扩展。拿不到精确值时标为未知。
- **机器**：把指标交给 Angela，由她安排；硬保护在运行时，包括内存上限和保留的磁盘余量。
- **花钱**：必须经用户同意，见 §4.6。
- **只读**：不受限（用户定）。

### 4.5 Angela 的位置

- Angela 使用通用的 agent 驱动，和 worker 一样启动、续接、中断、确认退出、按角色选模型（用户定）。她的特殊在权限和职责，不在机制。
- 她不走 worker 协议：那是 task 级的接口，套不到一个持续的会话上。她 = agent 驱动 × 编排环境。编排环境的工具是图和任务操作，不带 clone。
- 权限和职责（提案，待细化）：
  - 只有她和用户对话，也只有她写图。worker 的结果由运行时投影成 observation。
  - 她持有编排工具：派任务、追加消息、改需求、停止、采用、回答 worker 的问题。
  - 她和用户对等：凡是她能做的，用户也能做。花钱、代表用户对外、用户指定的路径，是她必须先问用户的事。
  - 只有一个 Angela。工作、生活等领域是图里不同的事情，不是不同的 Angela。不设子 Angela。
- 用户可以直接给某个 worker 发消息（用户定）。这条消息同样走 `send_message`，Angela 收到一个事件。这沿用旧设计中用户和角色一对一的直通路径。
- 她是唯一长期存在的 agent，原生会话要轮换，记忆靠图。什么时候轮换、新会话开头放什么，见下面的"会话轮换"。现在 `recall()` 在新会话开头放账本。
- **会话轮换**：
  - 由运行时自动轮换（用户定）。依据是"上下文管理不应该手动做"，所以不采用 research/organization-runtime.md §5、§11"第一版手动"的建议。她的提示词版本变了、或换了 harness 时，下次唤醒开新会话。用户保留现有的"新会话"按钮。
  - 现状：她的原生会话只在用户点"新会话"（`NewNativeSession`）或换 harness 时更换。Claude Code 对 1M 上下文的模型默认在约 967K token 时才自动压缩（官方文档，2026-10）；压缩的摘要用户看不到，也改不了。
  - 其余部分参照市面上的 personal agent 产品，有成熟方案就照搬（用户定）。调研结果见"附：会话轮换调研"。下面的方案据此定下。
  - **方案（用户定）**：
    - **上下文大小决定换不换，空闲决定什么时候换。** 运行时在每个 turn 开始前判断：
      - 超过软上限：之后每个 turn 的输入带一句"会话已长，近期会换会话，要紧的先写进图"；到下一个空闲点再换。依据：MemGPT 的"记忆压力"提示。
      - 超过硬上限：这个 turn 作为本会话的最后一个，输入里要求她把还没写进图的东西写进去；turn 结束后换。依据：Codex 实验性上下文管理的"强制收尾并预留余量"。
      - 她的提示词版本变了、换了 harness、或她自己请求时：下次唤醒开新会话。她自己选择换会话，不加限制。
    - 空闲点一律取 1 小时，含义是"用户离开了"，不是缓存过期。
    - 上限按模型配置。DeepSeek：软上限 300K，硬上限 700K。理由：DeepSeek 的模型结构专门为长上下文优化；有人报告上下文长时表现反而更好（用户转述，未核实）。其他 provider 的上限还没定；测试期 Angela 用 DeepSeek，不急。
    - 不按钟点重置。依据：OpenClaw 和 Hermes 都在 2026 年撤掉了定时重置的默认值。
    - 不让模型写对话摘要。比对话尾部更早的内容，靠图、按 ID 读原文和全文搜索找回。依据：摘要和压缩的事故最多（编造用户指令、规则丢失、状态倒退）；Codex 的实验方案也不做摘要，而是"换窗口 + 笔记 + 可回查的历史"。
    - 不另开收尾的 turn。依据：OpenClaw 的静默收尾是这一块 bug 最多的机制。
    - CLI 自带的压缩只作兜底。
    - **新会话的开头**（在一个会话内冻结，便于缓存）：
      1. 这是一次轮换，以及上一个会话的 ID。
      2. 关于用户：根事情下的有效条目，上限 4K token。超了不截断，提示她整理。
      3. 活跃事情的 `thread_brief`，总共 15K；放不下的事情每件一行（标题、状态、ID）。
      4. 等用户的事和在跑的 worker，每件一行。
      5. 本地时间，以及距上一个会话过了多久。
      6. 对话尾部原文 20K token：在消息边界截断，只放双方的消息，不放工具过程。
      7. 本轮的待处理事件。
    - brief 和对话尾部都带消息 ID；新增的历史工具能按 ID 读原文，也能全文搜索，返回原话、时间和 ID。依据：Codex 的笔记记"条目 ID"而不是转述；Hermes 的 `session_search`。
    - 每个 turn 的输入开头写一行"已用上下文 N / 软上限 S"。依据：Codex 让模型看到剩余预算。
  - 后话（用户定）：Angela 的系统提示词。

- **测试期的模型**（用户定）：测试时 Angela 先用 DeepSeek API。理由：便宜、快；能力弱，更容易暴露运行时的问题，从而给出补强方向。Fable 或 Opus 太强，运行时有缺陷也能把活做完，问题藏起来。
  - 接法：DeepSeek 官方文档给出了 Claude Code 的接法，设 `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic`、`ANTHROPIC_AUTH_TOKEN` 和 `ANTHROPIC_MODEL` 等环境变量（官方文档，2026-10）。Claude Code 本身不改，Angela 仍用通用的 agent 驱动；角色配置要能按角色设置这几个变量，不能影响 worker。
    - 实现（第 1 步第 9 组）：变量写在 host 目录的 `role-env.toml` 里，按 role 名分节，例如 `[Angela]`。每个 turn 启动时读一次，改了从下一个 turn 起生效；别的 role 拿不到。worker 的变量写在 `workers.toml` 条目的 `agent.env` 里。Angela 在设置里另选了模型时，`--model` 会盖过 `ANTHROPIC_MODEL`，用 DeepSeek 时要把她的模型留空。
  - 型号与价格（官方价格页，2026-10）：`deepseek-flash`（V4.1-Flash）和 `deepseek-v4-pro`，上下文都是 1M。flash 每百万 token：未命中缓存的输入 0.15–0.30 美元，命中缓存 0.003–0.006 美元，输出 0.60–1.20 美元（区间为闲时与高峰）。不支持 `cache_control`，缓存由 DeepSeek 自动处理。
  - 待实测：DeepSeek 文档把"MCP servers"列为不支持，这里指的应是 API 的服务端 MCP 连接器；Claude Code 把本地 MCP 工具作为普通工具定义发送，Angela 的 MCP 工具应当可用，要实测确认。
  - API key 是用户自己的付费凭据，不是 claude.ai 的凭据，Lobotomy 可以保存。
  - 用 `deepseek-flash`（用户定）。理由（2026-10）：V4.1 的 Pro 还没出，现在的 `deepseek-v4-pro` 比 flash 笨，也更贵。
  - 缓存：据用户所知，DeepSeek 的缓存保留时间接近无限，有报道说能保留几天；官方没有写明。所以用 DeepSeek 时，"空闲后续接要按无缓存价重读"这个成本理由基本不成立，轮换主要看上下文大小和质量。
  - 失败归类（用户定）：按 #60 的格式记录失败时，加一栏"换强模型重放是否还犯"。缺信息、工具契约含糊、状态看不到、少了事件，这类运行时的缺口要补；单纯推理或判断力不足的，不为它加运行时的关卡，以免回到"为卡坏习惯把系统整僵化"。

### 4.6 授权（用户定，从 #22 吸收）

- 需要用户同意的动作是：花钱、代表用户对外、合并碰到用户指定路径的 PR，以及外部系统 adapter 的一切写操作（[external-adapter.md](external-adapter.md)，用户定）。执行这些动作的工具必须带"授权"参数，值是用户某条消息的 ID。
- 运行时检查：这条消息确实是用户发的，不是 Angela 的话，也不是外部内容。运行时检查不了语义（用户说的是"可以"还是"不行"），这一点靠事后的摘要让用户看到。
- 来源是 external 的节点，不能作为授权或"决定"的依据。外部资料里的指令进了图，也不变成用户的指令。
- 检查在编排层做，worker 看不到授权：
  - 超出本任务仓库的对外动作，worker 一律不提供，走编排层的工具（worker-interface.md §7），工具带授权参数。
  - 合并碰到用户指定路径的 PR 时，运行时先检查授权，再向 worker 发 `adopt`。
- 理由：用户说话就够，不需要额外点按钮，语音输入也能用；Angela 凭空写一条"用户同意了"过不了检查。
- 需要授权时，Angela 发一张请求卡片（用户定）。用户点选项时绑定是精确的；直接说话时，由 Angela 绑定，摘要写明"按你某时某条消息执行了 Y"。见 §5"消息的上下文"。
- 预先给的长期授权（例如"这周 20 刀以内随便花"）v1 不做，等有实际需要再说。

## 5. 界面

**骨架（用户定）**：依据是 10-15 讨论中用户的原话（[029] 只看双方的消息，内部过程除非 debug 不显示；[308] 会话加工作台，agent 一边回复一边在右边展示，用户也可以点；[136]–[138] 一个入口，加几条随时能看的进行中事项；[113] 按事情进入局部，不一打开就摆出巨大的总图；[122]、[241] 图主要在 agent 讲不清时给人看，是顶层 agent 的工具；[302] 重启后界面像以前一样）。
- 三栏，对话是主体。
  - 对话：一条连续的对话，只显示双方的消息。Angela 的消息里可以有引用（在工作台中打开）、卡片（请求授权、问题选项、带证据的完成卡）和事实行（例如"已转给 X"）。
  - 左栏（窄）：最上是"需要你 N"（单一计数源）；下面是进行中的事情，每件一行，带状态外观，用户离开期间不重排；最下是"活动"（后台在跑什么）和"资料"（全部成果的索引）。点事情，在工作台中打开它的简报，不改变对话。
  - 工作台（右）：可以收起，按需打开，重启后恢复。标签有五类：事情简报（与 Angela 读的 `thread_brief` 同源，见 §4.1"读写分离"）；材料（Markdown、图片、网页，PR 当作网页打开）；图（默认按事情显示局部）；活动；worker 详情（它的过程，以及直接给它发消息的输入框）。
- 过程不显示（用户定，依据 [029]）。Angela 干活时只有一行"正在……"；干完不留痕迹。debug 时从消息的菜单打开"查看过程"。
- Angela 回答用户当前这条消息时，可以在工作台开一个新标签并切过去；后台出的成果只加未读点；用户正在操作工作台或图时一律不切（用户定，依据 [308]）。
- 图不当首页：默认按事情显示局部，多数时候由 Angela 在讲不清时主动打开。
- 旧 UI 计划（ui-ux-plan.md）的去留：继续用 P0、P1 的视觉体系，§2 的原则，P2 的对话版式，P5 的标题栏、命令面板和 toast，P6 的"上次看到这里"；退出 P4 的任务面板、P3 的"等你决定"分类、项目列表。
- 事情简报和活动页的内容，以及停止的三档；材料编辑与 VS Code 的冲突处理；回来时的接续和通知：见下文。
- **怎样验证界面**（用户定）：看线框图看不出大问题，UX 不实际使用没有概念。所以界面的设计只求大体对，细节以实际使用为准。

**对话中的卡片（用户定）**：接续 manager-actions.md §2.1 的附件规则和 §6 的问题生命周期。
- 六种类型：

  | 类型 | 谁生成 | 进"需要你" | 内容 |
  |---|---|---|---|
  | 要你卡 | Angela 发出 | 是 | 一种卡片，标三类：确认（授权：花钱、代表用户对外、用户指定的路径，§4.6）、选择（她的问题，带选项）、回答（开放问题，直接说） |
  | 交付卡 | 运行时生成，Angela 在消息中引用 | 否 | worker 的成果（PR 或报告）：当前状态，每条要求及其证据 |
  | 停止结果卡 | 运行时生成 | 否 | 停在哪一档、作用范围、已完成与未完成的动作、还在等确认退出的进程 |
  | 系统提示行 | 运行时直接写，不经 Angela | 视情况 | 只用于四种情况：她自己的 turn 失败或没能启动；额度用完（写明恢复时间）；断线；worker 质疑她的解读（`flag_mismatch`，manager-actions.md §2.3） |
  | 事实行 | 运行时，附在 Angela 的消息中 | 否 | 已转给 X；按用户某时某条消息执行了 Y；已合并 PR #N |
  | 引用 | Angela 写，运行时渲染 | 否 | 材料、事情、PR、消息，带版本；在工作台中打开；旧版本提示"现为 vN" |

- 卡片显示对象的当前状态，不是写死的文字，沿用附件"按当前状态标出有效性"的做法。已回答、已过期、PR 已合并等变化，在原卡片上更新。
- 授权绑定对象的版本，例如"合并 PR #92"绑定当时的 head 提交。对象变了，卡片标为"已过期，需要重新确认"，由 Angela 重新发起。这与 worker 接口中 `adopt` 按版本比较并交换一致。
- 事实由运行时生成，判断由 Angela 写。交付卡上"已验证、未验证、阻塞"的标记由运行时按证据来源给出，Angela 改不了：只有环境核实过的证据（例如 forge 上的 CI）算已验证，worker 自述算未验证。她的话写在卡片外。
- 回答要你卡：
  - 每张卡片都留着输入框，用户总能不选选项而自己写（用户定）。
  - 点按钮时，绑定是精确的。
  - 直接说话时：选择和回答两类沿用现有规则，用户提问之后发来的消息送到 Angela 的 turn 时，问题关闭（manager-actions.md §6）。确认这一类由 Angela 显式绑定到那条消息，卡片写明"按你某时的「…」"。同时开着几张卡、她判断不出用户在回哪一张时，她再问一次。
  - 状态：待你 → 已答、已过期或已撤回。没回答的卡片一直留在"需要你"里，不会到时间自动继续。
- "需要你"只数要你卡（用户定）。完成了但用户没看过的事，只在左栏标"完成 · 你还没看"，不计入。理由：Angela 合并后会在对话里写摘要，把"没看过"计进去会让这个数一直偏大，用户不再把它当作"必须处理"的信号。
- 系统提示行只用于上表的四种情况，其余由 Angela 说。

**事情简报、活动页与停止（用户大体认可，细节以实际使用为准）**：
- 事情简报与 Angela 读的 `thread_brief` 由同一个编译器生成（§4.1）。从上到下：
  1. 头部：名字、状态、更新时间；操作有"看图""停止…"和"更多"（改名、合并到另一件事、归档）。
  2. 需要你：这件事上开着的要你卡，没有就不显示。
  3. 目标。
  4. 下一步：只列没完成的，带资源图标和现算的状态，被阻塞的写明卡在哪一条；已完成的折成一行。
  5. 待定的问题。
  6. 当前判断：只给"已定"和"猜测"加标签，"暂定"是默认值不标；改过的写"改过 N 次"，点开看依据链。
  7. worker：状态、最近动作，可以看详情、发消息、停止。
  8. 成果，带版本。
  9. 最近变化（`changes` 视图）。
- 每一行悬停显示依据，点开是依据链。用户可以在简报中直接用与 Angela 同一套写入操作（完成、放弃、重开、撤回、修改）；修改写成来源为"用户"的变化记录，Angela 收到事件。
- 事情的状态由程序按优先级推出：有开着的要你卡 → 等你；有没人处理的失败 → 失败；有 worker 在跑或 Angela 正为它干活 → 运行；只剩时间或外部的等待 → 在等；开着的下一步全被阻塞 → 被阻塞；否则静止。"完成"由 Angela 或用户明确关闭这件事来标记。
- 活动页分六组：Angela（当前在干什么、多久、本会话已用的上下文）、worker、在等、CI、最近一小时结束的、资源（各额度域余量、本机内存）。每一行都能单独停；顶上有"全部停下"，停掉 Angela 当前这一轮和所有 worker。
- 停止：

  | 操作 | 在哪 | 作用范围 | 怎样恢复 |
  |---|---|---|---|
  | 停止当前回复 | 输入框旁；活动页 Angela 那一行 | 只停 Angela 这一轮 | 用户再说一句话 |
  | 停止这件事情及其 worker | 事情简报的"停止…" | 打断它的 worker 当前这一轮（不取消任务，会话保留）；不再开始新的下一步 | 只有用户能恢复，沿用"用户的暂停只有用户能解除" |
  | 取消后续计划 | 同上 | 正在跑的跑完；还没开始的下一步不再开始 | 同上 |

  - 对单个 worker：打断这一轮（worker 接口的 `stop(turn)`，可以恢复）；取消这个任务（`stop(attempt)`，不能撤回，确认一次）。只有取消要确认。
  - 每次停止后，对话中出现停止结果卡。

**材料的编辑与冲突（用户定）**：
- 参照 VS Code：编辑器没有未保存的修改时，文件在磁盘上变了就直接重新载入；有未保存的修改时不打断，冲突到保存时才出现，保存时可以对比或覆盖。前两条有 vscode#53532 佐证，第三条是对现行界面的了解，实施时再核实。
- Lobotomy 的材料是文件库中带版本的对象，Angela 改材料就是存一个新版本，被覆盖的版本仍在历史中。
- 做法：
  - 用户开着材料、没有未保存的修改时，Angela 存了新版本：直接换成新版本，改动的行高亮。
  - 用户有未保存的修改时，Angela 存了新版本：不动用户的编辑，只在标签上加一个小标记。
  - 用户保存时，开始编辑之后已有新版本：以开始编辑时的版本为基准做三方合并。没有冲突就自动合并，合并进来的行高亮；有冲突才弹出对比，可以用自己的、用她的或手动合并。无论选哪个，另一版都留在历史中。没有冲突就自动合并，这一点超出 VS Code，理由是另一方是 agent，改得比人频繁。
  - Angela 要改用户正在编辑、还没保存的材料：不加锁，她的写入照常成功；工具结果告诉她"用户正在编辑这份材料"，由她决定等一等还是先说一声。
- **工作台不加文字说明的浮层**（用户定）：工作台屏幕小，文字会叠住内容。变化只用高亮和标记表示。
- 只编辑 Markdown 这类文本材料。PR 和代码在网页标签中看，不在这里编辑。每次保存是一个版本，可以看版本列表、对比任意两版。

**回来时的接续与通知（用户定）**：
- 空闲 1 小时算"离开"（§4.5）；窗口重新拿到焦点或用户发出第一句话，算"回来"。
- 回来时，"上次看到这里"的分隔线处有一块折叠的"离开期间"摘要。它由程序从 `changes` 视图生成，列出新的要你卡、交付与合并、失败、完成的事情、Angela 改动的重要判断，每条能点开。不为此唤醒 Angela：需要判断的部分，她在状态变化时已经写过合并消息（manager-actions.md §6）。
- 系统通知只在四种情况下发：全员在等你；活干完了；系统故障（登录失效、额度或余额用完、Angela 的 turn 失败）；worker 质疑 Angela 的解读（`flag_mismatch`）。用户正在看界面时不弹；同一状态只通知一次；短时间内的多条合并（沿用 manager-actions.md §6）。
- 要你卡不发系统通知，只更新"需要你"的计数和托盘。不设截止时间之类的字段（用户定）：它等于变相给 Angela 一个通知接口，她总能把时间设成 1 秒。要么不通知，要么正式设立接口；目前看这是假需求。
- "已看"存在后端，不存在浏览器本地，也不按 ui-ux-plan.md P6 存在 localStorage（用户定）。理由：左栏要显示"完成 · 你还没看"，重启或换设备后要一致。

下面是从调研中挑出的借鉴，括号里注明是纯展示还是需要后端支持：

1. **过程折叠**：调研中的做法是每条回复的过程折成一行"最新动作"，可以展开，展开偏好要记住。依据：最强的痛点是"过程被隐藏又难展开，导致不信任"，而不是默认折叠本身。Lobotomy 的做法不同：过程不显示，debug 时从消息的菜单打开，见上文骨架（用户定）。（纯展示）
2. **后台成果不替换工作台**：agent 在后台产出新对象时，只在标签上加未读点；对象头部能跳回来源消息。Angela 回答用户当前这条消息时可以切过去，见上文骨架。依据：反例是 ChatGPT Canvas，自动打开、改错对象，后来被撤回。（纯展示）
3. **成果用稳定 ID 加版本**：引用绑定到（ID，版本）；打开旧引用时提示"现为 vN"；全局有成果索引；每个版本都可达。（需后端）
4. **事情级状态**：运行、等你、阻塞、完成、失败、取消。"需要你"只数要你卡，见上文"对话中的卡片"；"已看"要持久保存。（需后端）
5. **单一计数源**：侧栏、托盘、提示共用一个集合计数。依据：Cursor 的两处计数不一致，官方承认是"两套说法"。（纯展示）
6. **停止分三档**：停止当前回复、停止这件事情及其 worker、取消后续计划，每档写明作用范围；停止后列出已完成和未完成的动作。依据：调研中没有产品把停止的范围分清。（需后端）
7. **引用 chip**：选中的片段、成果或事情变成输入框里的 chip，发送后可以跳回原处。（展示加后端：turn 要携带引用 ID）
8. **重启恢复**：草稿、以消息 ID 为锚点的滚动位置、工作台对象、展开状态存在本地；事情的状态以后端为准重建，不从界面缓存恢复。依据：Codex 重启后线程消失、未读标记清空、顺序错乱。（主要是展示）
9. **完成卡带证据**：每条要求标为已验证、未验证或阻塞，并附证据。（需后端）

**补充设计**（用户定，#86 评论）：
- 重启后恢复当前事情、会话位置和工作台现场。
- 独占保护只针对图界面：用户正在聚焦、操作图时，agent 不竞争操作，不抢选中项和视角。
  - 保护的是视图，不锁数据（用户定）。Angela 的写入照常进库。暂不应用只为防止和用户的操作并发，保护的是"正在操作"，不是"正在看"：
    - 图在后台，或用户切走了：直接应用；用户回来时，变化过的节点短暂高亮。
    - 图开着、用户在看但没有操作：直接应用，用动画标出哪里变了（对应 [235]"agent 一边改一边显示动画"）。
    - 用户正在操作（拖动、选中、编辑）：视图不跳动，先攒着，在角上提示"Angela 有 N 处修改"；用户停手几秒或切走后自动应用，也可以点一下提前应用。
  - 用户正选中或编辑的节点被取代或 retire 时，用户眼前的节点保留，标为"已被取代"。
- 材料多开标签页，主要看 Markdown、图片和网页，不需要控制权锁。Markdown 的并发编辑参考 VS Code；外部更新、未保存的修改和冲突怎样处理，见上文"材料的编辑与冲突"。
- 消息、材料和图中的选中项之间要能双向引用和定位。
- 关闭材料标签只关闭视图，不删除成果，也不停止 worker。
- 后台出了新成果先提示，不自动抢焦点，不自动打开一堆标签。

**消息的上下文**（用户定）：
- 约束：
  - 强制用户手选上下文不可接受。上下文管理不应该手动做。
  - 实际使用中，agent 大多数时候能自己猜出上下文。用户愿意时，可以指定回复某条消息。
  - 理由：自然语言是流变的；而且计划支持语音输入，那时没有输入框可以选。
  - 打开、切换材料不应悄悄改变上下文（#86 评论）。
- 和 Dot、ChatGPT 的区别：它们猜的上下文只影响这一次怎么回，猜错了用户下一句就能纠正。Lobotomy 中 Angela 猜的归属写进图，被以下几处使用：界面的事情视图、轮换后开头的 `thread_brief`、作用范围、"依据已变"的候选列表、把用户的话转给 worker、授权。前四处出错是显示问题，或是延迟出现的记忆错误；后两处会执行动作，有实际效果。
- **做法（用户定）**：
  - 输入时没有上下文状态。用户只管说话，指定回复某条消息是可选的。Angela 读完后自己归属，可以同时挂到多件事情上。归属是图里的普通边，可以猜错，改起来代价低。
  - 记忆不只靠归属：新会话开头的对话尾部原文和全文搜索都不依赖归属。
  - 动作发生时显式绑定，并且让用户看得见：转给 worker 时，对话里显示"已转给 X"；用到授权时，摘要写明"按你某时某条消息执行了 Y"。高危的错误当场暴露。
  - 需要授权的动作，由 Angela 发一张请求卡片。用户可以点选项，也可以直接说话；点选时绑定是精确的。
  - 对话里不显示 Angela 的归属，跟 Dot 一样不暴露内部过程。记忆上的错误由对话尾部原文和搜索兜底，也能在事情视图里看到。
  - 剩下的靠 Angela 自己的素养，即她的系统提示词（后话）。

**会话节奏**（#86 评论；用户定）：
- 想法：用提示词和接口让 agent 可以选择不回话。觉得用户没说完时静默等待，新消息来了合起来看；没什么值得补充时不回复；有自然的联想可以聊别的。先验证这种交互是否自然，不为此改模型结构。
- 等重构时再做，不在现在的 M4 Angela 上试。
- 不设"过一段时间再唤醒"：她误判时，用户补一句简单的话就能叫醒她。定时再唤醒有死循环的风险，也容易被利用。

   - 冷 clone 与冷构建要多久；
   - 端口冲突；
   - 整机内存。
   结果决定并发上限，以及要不要上服务器。
1. **worker 层替换**：任务阶段改为 PR 流程，删除第 6 节"退出"一行，放开 push 和 gh。这一步卸下的维护面最大，也是并行 worker 的前提。实施计划与实际验收见本节末尾。
2. **图与事件**：账本迁移，Angela 的图工具，待处理事件表。动工前的图工具实验见本节末尾。验收由 #22 的最小验收改写（用户定）：

   2. 用户把 A 改成 B 后，旧 turn 迟到的取代被拒，重试不重复写入；引用 A 的活跃任务出现"依据已变"，Angela 被唤醒。
   3. 历史经验（某个测试曾经失败）和当前结果（CI 通过）能分开回答；图不覆盖运行时的事实。

   5. 验证新会话的开头确实放进了 brief，不凭模型自己说"记住了"。
   6. 记录读写的开销，以及漏记、漏召回的实际案例。
3. **界面**：会话、工作台和事情列表，接上 UI 计划 P2 剩下的项目。

### 第 1 步的实施计划（用户定）

**完成的标志**：Angela（`deepseek-flash`）向 Lobotomy 仓库派出 2–3 件真实任务。每件任务走完这条链：

1. worker 在自己的 clone 里工作。
2. agent 退出后，环境用 bot 身份推送并开 PR。
3. CI 失败时，环境在预算内交回 agent 修。
4. Angela 按版本合并。

中途重启后端或 worker 宿主、停止任务，之后都能接着走。这相当于把第 0 步的实验搬进 Lobotomy 里跑一遍。

**演练**（用户定）：罕见的故障不靠测试推演，由 Dot 定期演练，像航空的模拟机复训：频次低，单次可以昂贵。Dot 有 GUI，能直接看界面。每项都看两件事：界面上能不能看懂现在由谁负责、在等什么；之后能不能接着走。

1. worker 正在跑 turn 时，结束后端进程，再启动。worker 宿主随后端重新启动；任务的状态与 worker 的一致，之后能接着走。
2. worker 正在跑 turn 时，结束 worker 宿主进程。后端约 5 秒后重启它；任务的状态对得上，之后能接着走。
3. 在任务面板打断一个正在跑的任务，再在"等你决定"的卡片中发消息，让它接着做。
4. 让一件任务的 CI 失败一次。worker 在预算内修好；预算用完时 attempt 记为失败，交给 Angela 和用户决定。
5. 让一件任务改到需要授权的路径（`workers.toml` 的 `authorization.paths`）。Angela 合并前先问用户，没有授权时合并被拒绝。
6. 任务执行中修改完成条件。旧 attempt 停下，新 attempt 按新版本开始。

演练中发现的问题算真实出现过的问题，按 AGENTS.md"加测试前"处理。

**第 7 组的做法**：
- 项目库保留 `task` 行，存标题、原话、解读和阶段。新加 worker 任务、交付物和证据三张表。worker 的每个事件由一条运行时命令写进这些表，同时推进任务阶段，并写进项目的事件日志：delivered 对应等验收；其余状态都对应执行中，包括 failed 和 canceled。任务只在编排层关闭时才变成完成或放弃（`close`），这样失败或被停的任务还能改需求重来（实现时的选择）。所以 GUI、Angela 的读取工具和"全员在等你"的判断大体照旧。
- worker 写在 host 目录的 `workers.toml` 里，格式沿用 worker-interface.md §8。每个 worker 条目显式写明所属的项目名（用户定）。后端为每个条目启动一个 worker 宿主。
- 后端不运行项目里非 remote 的 role，Angela 按名字指派 worker。
- 唤醒 Angela：worker 进入 `delivered`、`blocked`、`failed`、`unknown`，或报了 `mismatch_flagged`。`working` 和证据变化不唤醒她。
- 授权（§4.6）：`workers.toml` 里列出需要用户授权的路径。交付物带上改动的路径；改动碰到这些路径时，采用的工具必须带用户消息的 ID 作为授权。
- worker 的采用沿用验收对未投递消息的检查（用户定）。用户发给 worker、没有送到的消息，只有用户能明确放下；Angela 采用时遇到这类消息会被拒绝（data-model.md §4.2，#14）。交给过 worker 的任务关闭后不能重开（data-model.md §4.6）。
- worker 的过程（agent 做了什么、跑了哪些命令），第 1 步不在界面上显示，留给第 3 步的"查看过程"和协议的 `read_log`（用户定）。
- **实现**（`lobotomyd/src/workers.rs`）：后端为 `workers.toml` 的每个条目启动一个 worker 宿主，宿主退出 5 秒后重启。重启后按项目库里已应用的 seq 续订。项目打开时，worker 名写成 remote 的 role。项目调度器把 remote role 的排队任务交给 worker。Angela 的 send_to_role、accept、send_back、abandon、set_paused 遇到 worker 的任务时，走 worker 协议，其中 accept 带授权检查。配置格式见 `workers.rs` 开头的注释。
  - `workers.toml` 只在后端启动时读一次。读不出来时，后端照常启动，但不启动任何 worker，也不改项目里 worker 的 role；host 快照带上原因，界面在「全部」和每个项目的右侧栏最上面写明（实现时的选择）。
- 后端只运行 Angela 的 turn，不直接运行执行者（用户定）；项目调度器只把排队任务交给 worker。项目打开时，后端删除没有被任何记录引用的非 remote role，例如初始的 Malkuth。runner 的回归测试在 worker 宿主中（`worker/tests/runner.rs`）。e2e 和性能基线中的长对话由 Angela 在假 Codex 上的 turn 生成。

**第 1 步的范围**：

**第 1 步的已知缺口**（重构审查，[#91](https://github.com/vorton-lang/Lobotomy/pull/91)）：

## 8. 已定与待决

**已定（用户定）**
- **合并**：CI 通过后由 Angela 合并，用户看摘要；用户指定的路径必须由用户确认。
- **数据库**：全局一个，见 §4.1。
- **测试**：只保留回归测试，没有拦住过问题的测试已经退役。理由：加上后端的删减，预计能缩短 CI。长期方案以后再定。
  - 回归测试指两类：修 bug 的提交新增或实质改过的测试；在 CI 上失败过、随后由不只改测试的提交修好的测试。真实 CLI 测试与 MCP 契约测试也已退役；怎样对照真实 CLI 检查 adapter，随 worker 层的替换再定。
  - 测试追求杠杆，不追求召回率。值得加测试的主要是主路径、真实出现过的问题和反复跑进的弯路；不为推演出来的场景加测试，罕见但代价大的风险靠设计和权限分工防。依据是 1972 年东方航空 401 号航班的教训：机组全盯着一个坏掉的指示灯，没人在开飞机。规则写在 AGENTS.md 的原则第 7 条和"加测试前"。
- **隔离**：便宜的就够，"一人一个文件夹也能跑"。
- **身份**：worker 用 bot 身份开 PR。
- **"没有 Angela 也能跑"不是设计目标。**
- **审查返工**：审查意见通过"续接原会话、追加消息"交给 worker 返工；"停止 + 新 attempt"只用于需求变化。依据：第 9 节的实验。
- **Angela**：使用通用的 agent 驱动；她的特殊在权限和职责，见 §4.5。
- **会话节奏**：等重构时再做，不设"过一段时间再唤醒"，见 §5。
- **图语义**：step 的状态、blocks 的解除与组合、不单设 `wake_on`，见 §4.1。唤醒条件（定时和"等待解除"）由 §4.2 的事件来源表回答，取代 manager-actions.md §6 的三种唤醒条件。
- **图界面**：保护视图，不锁数据，见 §5。
- **用户直接给 worker 发消息**：可以，Angela 收到事件，见 §4.5。
- **Angela 的会话轮换**：运行时自动轮换，大小决定换不换、空闲决定什么时候换，不写对话摘要，开头的配方见 §4.5。
- **测试期 Angela 用 `deepseek-flash`**，见 §4.5。
- **消息的上下文**：输入时没有上下文状态，归属由 Angela 猜、可以错；动作发生时显式绑定并让用户看得见；对话里不显示归属。见 §5。
- **事情简报、活动页与停止**：大体认可，细节以实际使用为准，见 §5。
- **材料冲突、回来与通知**：没有冲突就自动合并，工作台不加文字浮层；回来时由程序生成"离开期间"摘要；通知只在四种情况下发，要你卡不通知；"已看"存在后端。见 §5。
- **对话中的卡片**：六种类型，卡片显示当前状态，授权绑定版本，事实由运行时生成，"需要你"只数要你卡，见 §5。
- **图的读写分离**：写入侧是一组表达变化的操作，读取侧是编译出的视图，历史由变化记录编译出来，见 §4.1。
- **来自 #22**：引用与"依据已变"、作用范围、幂等、历史版本、证据保留见 §4.1；worker 不读图、代码库知识写在仓库里、CLI 自带记忆保持关闭见 §2.2；授权见 §4.6；第 2 步的验收见 §7。
- **第 1 步的实施计划**：抽出 Angela 与 worker 宿主共用的 agent 驱动；先保留按项目分库；协议补 `mismatch_flagged` 事件；远端传输、非代码交付物等推后。见 §7 末尾。

## 9. 第 0 步实验结果（2026-10-16 01:05–01:45，本机 Windows）

**设置**
- 3 个 worker：w1、w2 用 Claude Code（opus），w3 用 Codex（gpt-6-astra，medium）。
- 隔离按 L0 加 L1：每个 worker 一个独立 clone，单独的 TMP、git 全局配置、空的 gh 配置，各自一个端口段。
- CLI 登录共用用户本机的登录。
- 推送身份是 GitHub App bot：git 每次需要凭据时现场签发 token，PR 由驱动脚本用 bot 身份开。
- main 的规则：bot 必须走 PR，且 `ci-ok` 必须通过；用户的账号豁免。

**结果**

| worker | 结果 | 用时 | 折合 API 成本 |
|---|---|---|---|
| w1 端口变量 | 交付 → #89，CI 通过后由 bot 合并 | 7.4 分钟，含 `npm ci`、冷编译后端、Electron e2e | $0.63 |

- **登录**：约 15 分钟的并发使用中，没有出现认证错误。这段时间太短，没有覆盖 token 刷新，"互相顶掉"的风险仍待更长的实验验证。

**对设计的影响**
1. 第 2.2 节的接口在实验中可用：worker 遇到要改语义时停下；先复现、再修复、保留回归测试；按 AGENTS.md 跑了相关测试。
2. 合并前的审查有实际价值。#90 的漏洞是 worker 对后端数据的前提理解错了（以为历史页带最新的 turn 状态），而它自己的测试全部通过。审查者需要能读后端的契约和代码。
3. 审查意见用"续接原会话、追加消息"返工，又快又便宜（48 秒）。第 2.2 节的"改需求 = 停止 + 新 attempt"适用于需求变化；审查返工走"追加消息"（用户定，见 §8"审查返工"）。

5. 规则没有要求"分支必须是最新的"。#90 基于旧的 main 合并，因为和 #89 改动不重叠，所以没有问题；main 的 CI 作为兜底。
6. 已知缺口得到实证：合并用的就是 worker 手里同一种 token，所以 worker 技术上能自己合并自己的 PR。

## 附：会话轮换调研（2026-10-17）

三路资料调研：消费级的 personal agent 与陪伴产品；开源与开发者框架；评测证据与缓存成本。没有实测。标注"官方"的出自官方文档、论文或维护者的说法；"逆向"出自泄露的提示词或第三方逆向。

**市面上的做法**
- 消费级产品里，"一条对话"只是界面，不是一个模型会话。产品要么每轮重新拼上下文（Tolan：近期消息摘要 + 人设卡 + 检索到的记忆 + 应用状态，官方案例 2026-01），要么保留一个滚动窗口，接近上限时压缩（Claude.ai，官方 2025-11；Poke，逆向）。没有一家公开按时间轮换。
- 按钟点重置只在开源框架里出现过，而且两家都在 2026 年撤掉了默认值：OpenClaw 把 `session.reset.mode` 的默认改为 `none`（PR #111140，2026-07-19），起因是用户抱怨每天 4 点的重置毁掉上下文；Hermes Agent 在 v2026.9.11 去掉了重置计时器。Hermes 的文档仍建议在自然的节点（一件事做完、换话题、一天开始）手动开新会话，理由是长会话贵，而且记忆整理"几乎没机会运行"。
- 拼进上下文的部分各家相同：一段短而稳定的用户档案（约 1–4K token：ChatGPT 的档案约 4K，Claude.ai 的综合约 1K，Hermes 约 1.3K）、之前对话的摘要、检索到的记忆、时间等元数据、一段按 token 计的近期原文。
- 近期原文的长度没有对照实验，常见的默认值是 20K token：OpenClaw 的 `keepRecentTokens` 是 20,000；Codex 压缩后保留最近 20K token 的用户消息（源码 `compact.rs`）；Hermes 保留最近 20 条消息，精简模式 10–25K。
- 轮换或压缩之后，全部历史仍可搜索：Hermes 用 SQLite FTS5 的 `session_search` 返回原始消息；Claude.ai 压缩后保留完整历史供模型引用；Letta 有 recall 存储。
- 开头的内容在一个会话内冻结，便于缓存：Hermes 在会话开始时冻结记忆快照，会话中的新记忆要到下一个会话才看得到；Claude Code 每个会话读一次 CLAUDE.md。
- 整理记忆多在后台、按空闲或压缩触发，而不是在重置前：Codex 的 memories 在线程空闲 6 小时后抽取；Letta 在每次压缩时触发反思；ChatGPT 的 "Dreaming" 在后台综合（2026-06）；Tolan 每晚压缩。

**证据**
- 长上下文仍会变差，各模型差别很大。Chroma "Context Rot"（2025-07）测了 18 个模型，全部历史（约 113K）都比只给相关的约 300 token 差。2026 年的 MRCR v2 8-needle：GPT-5.5 在 128–256K 为 87.5%，Opus 4.7 为 59.2%，Opus 4.6 在 1M 为 78.3%。没有找到 DeepSeek V4.1 Flash 的长度曲线。
- 多轮对话本身就会变差："LLMs Get Lost in Multi-Turn Conversation"（ICLR 2026）测了 15 个模型，任务分散到多轮后平均下降 39%；作者建议带着整合过的摘要开新对话。
- 记忆策略：历史超过约 100K 后，"摘要或观察 + 近期原文 + 检索"的组合优于全量上下文，也优于单纯检索（BEAM、LongMemEval、Mastra 的自报结果）。事实更新和矛盾消解，所有方法都做不好（MemoryAgentBench 中多跳更新不超过 7%）。
- 摘要和压缩会出错：编造用户指令并执行（claude-code #46602）、压缩后 CLAUDE.md 的规则被忽略（#6354）、状态倒退到旧步骤（#24792）、Codex 忘了自己刚做的 23 处修改（codex #5957）、OpenClaw 的"先确认再动手"在压缩中丢失后删了 200 多封邮件（AIID #1542）。逐条从原文抽取的事实，比保留原始片段差（arXiv 2601.00821，单作者）。
- 压缩前的静默收尾（OpenClaw 的 memory flush）是这一块 bug 最多的机制：不触发（#4836、#19488、#47143）、死循环（#66058）、和 Codex 原生压缩冲突（#126171）。重置时它只保存最近 15 条消息，不做收尾；要求加收尾的 #45608 仍开着。
- MemGPT（2023）在上下文约 70% 时给模型一个"记忆压力"提示，让它先保存。

**缓存成本**（官方，2026-10）
- Claude Code：订阅额度内主对话的缓存有效期 1 小时，API key 下 5 分钟。Pro 和 Max 上，空闲超过约 1 小时、且超过 100K 的会话，恢复时会弹出"从摘要恢复"。缓存读取按 API 计价约为原价的 0.1 倍（Opus 5.5 为 0.05 倍）。订阅额度里缓存怎样折算，没有公开。
- OpenAI：缓存空闲 5–10 分钟到 1 小时失效，可选 24 小时保留。
- 推算：缓存失效后续接一个 200K 的会话，此后每一轮的成本约是 30K 开头的 6.7 倍；500K 约 17 倍。

**Codex 的实验性上下文管理**（读源码与本机模型目录，codex-cli 0.162.0-alpha.17.2，2026-10-17）
- 开关是 `[features.context_management] experimental_mode`，阶段为 under development，默认关闭。只对 ChatGPT 登录的 Plus / Pro 账户、OpenAI 自家后端、模型目录里标了 `supports_experimental_context` 的模型生效。本机目录中 gpt-6-astra、gpt-6-sol、gpt-6-luna、gpt-5.6-sol 支持；各模型的 `token_budget.enabled` 目前都是 false。
- 机制（`codex-rs/core/src/session/token_budget.rs`、`codex-rs/ext/history-notes`）：
  - 不做摘要式压缩，而是换一个全新的上下文窗口。新窗口"不会自动包含当前对话"。
  - 模型有私有笔记 `notes`（读、写、追加、搜索；每个文件不超过 1MB），跨窗口保留。
  - 模型有只读的 `history` 工具，可列出各个窗口、按窗口和条目 ID 读原文、按字面子串搜索。每个非助手条目后面带 `[id: ...]`。
  - 新窗口开头注入一段不超过 4KB 的 "thread hint"，由后端生成；`<context_window>` 里写明上一个窗口的 ID。
  - 模型能看到剩余的上下文预算，并有 `get_context_remaining` 工具。
  - 换窗口由模型自己调用 `functions.new_context` 触发。剩余不到 6,144 token 时，提示它先记笔记再换；预算用尽时，强制它"只写一次笔记，然后换窗口"，为此在阈值之外预留 16,384 token。
  - 笔记要写：目标、决定、进展、学到的东西、下一步，以及每个仍在处理的用户请求和重要动作的窗口 ID 与条目 ID，以便之后按 ID 读回原文。
  - 笔记和历史是"私有的、仅模型可见的状态"，提示词要求模型不向用户提及。
- 推断（未证实）：OpenAI 的 dots（2026-09-29 发布，GPT-6 Astra）对外说它不拿"dot 给自己记的笔记"训练，界面也隐藏内部过程。这与 Codex 的私有笔记和历史恢复很像，可能是同一套机制。dots 的记忆机制没有公开细节；New Computer 的 Dot 是另一个产品，已于 2025-10-05 关停。
