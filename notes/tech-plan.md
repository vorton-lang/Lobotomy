# Lobotomy 技术方案

本文是 [#86](https://github.com/vorton-lang/Lobotomy/issues/86) 的技术方案。它在 2026-10-16 作为草稿写成，2026-10-17 收进 notes/。已定和待决的事项都列在 §8。它不是实现规格。worker 部分的展开见 [worker-interface.md](worker-interface.md)。

依据是 2026-10-16 的五路资料调研（隔离、worker 抽象、forge 与登录、图与编排、界面）和现有代码的盘点。资料调研没有做实测；凡是"实测"的地方都要另外验证。

术语：personal agent 即 Angela；worker 指接下一件事、交回一个交付物的执行者；"事情"指一件持续推进、会转向的事；forge 指 GitHub 这类代码托管平台。

## 0. 原则（用户确认，2026-10-15/16）

1. 系统要灵活。由强的 personal agent 配合运行时工具约束 worker；不卡 personal agent，也不卡用户。
2. 硬关卡放在标准治理上：分支保护、必过 CI、PR。Lobotomy 不再自己做快照、合并和分支。
3. Lobotomy 专注宏观编排，做事的能力放在 worker 抽象后面。
4. 用计算资源换开发上的简单。
5. 不再把"没有 Angela 也能跑"作为设计目标。没有她时，系统在逻辑上仍能运行，只是很难用。

## 1. 分层

```
人 ── 界面（会话 + 工作台 + 事情列表）
        │
     Angela（理解、拆分、判断、合并决定）
        │  图工具 / 事件 / 消息 / 资源
     编排层（Lobotomy 后端：图、事件队列、消息投递、额度与机器指标）
        │  worker 接口
     worker（环境 + 官方 CLI）── forge（PR、CI、合并） / 外部
```

- Lobotomy 自己实现：界面、编排层、worker 适配（adapter 与环境准备）。
- 借用现成的：版本管理与合并（git 加 forge）、CI、CLI 本身。

## 2. worker

### 2.1 抽象在 task 级

一个 worker 接一件交代完整的事，交回一个交付物。它内部是一个 CLI 会话，还是再分派给子 agent，Lobotomy 不依赖。

- 理由：用户说的"交代完整"有四项：要解决什么、能动什么、做到什么算交差、何时回来问。这是 task 级的契约。
- 抽象在"一个 CLI 会话"太低：Lobotomy 仍要管各 CLI 不一致的中断语义、环境和 CI 循环，而这正是要卸下的部分。
- 抽象在"能再分派的小团队"太高：它和 Angela 的拆分职责重叠，嵌套拆分会放大改动面。问题也会在层间丢失，例如 Claude Agent SDK 的 subagent 不能向用户提问。
- v1：一个 worker 就是在自己 clone 里运行的一个 Claude Code 或 Codex 会话，由 adapter 包装成 task 级契约。现有的 harness adapter、进程管理和 turn 记录可以复用。

### 2.2 接口（沿用现有 `assign` 的字段）

| 部分 | 内容 |
|---|---|
| 输入 | 用户原话与 Angela 的解读；材料（仓库与基线，或文档）；允许的动作（含"开 PR"）；`done_when`（代码任务要求 CI 通过）；`stop_when`（时间、轮数、改动规模）；`ask_when`（哪些情况停下来问）；环境引用 |
| 干预 | 只承诺两个原语。一是追加消息，回执写明它进了哪个 turn。二是停止，以进程确认退出为准。改需求 = 停止 + 新 attempt + 新的完成条件版本。暂停不做成 worker 原语 |
| 产出 | PR 地址与 head SHA，或报告的位置；自述：做了什么、没做什么、做了哪些假设；CI 链接；改动规模。`done` 只表示候选 |
| 求助 | `blocked` 是一等状态，带问题和选项，等待期间不计预算。不阻塞的猜测写进产出里的"假设"。不设"超时后自动继续" |
| 结束 | 终态：delivered、blocked、failed、stopped、budget_exhausted，各带原因。旧 attempt 迟到的结果不生效 |

- CI 结果由运行时从 forge 读取，不采信 worker 的自述。依据：worker 改测试、谎报通过是强证据的痛点。
- 审查负担是最强的痛点。dotnet/runtime 的数据：1–50 行的 PR 成功率 76–80%，101–500 行降到 64%。所以任务要拆小，这由 Angela 负责；运行时统计改动规模，交给她看。这与用户"改动面越小冲突越少"的判断一致。
- **worker 和记忆（用户，2026-10-17，从 #22 吸收）**：
  - worker 不读图。必需的约束在创建任务时随任务输入带全；缺信息时，worker 报 blocked 提问，或由 Angela 补一条消息。理由：worker 是外部的、可替换的，开放查图会把图的 schema 变成对外接口；而且库是全局的，工作和生活都在里面，不应暴露给第三方 worker。
  - 代码库的知识（怎么跑、关键入口、踩过的坑）写在仓库自己的 AGENTS.md、notes 等文件里，和代码一样走 PR。图管事情和理解；需要时按「来源 + 路径 + 版本」引用仓库文档，不复制进图。
  - CLI 自带的记忆保持关闭。现在 Lobotomy 已给所有角色设了 `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`（`lobotomyd/src/capability.rs`）。Claude Code 的 auto memory 记的是用户偏好、纠正、代码推不出的项目决定和外部资料位置，正是图的内容；它按 git 仓库分目录，每个 clone 各一份，开着只会让各 worker 的记忆互相分叉。官方文档没有给开关它对效果影响的数据，本项目也没有实测。

### 2.3 环境：默认 L0 + L1

| 级 | 做法 | 解决 |
|---|---|---|
| L0 | 每个 worker 一个独立 clone。不用 git worktree：并发 `git worktree add` 会抢 `.git/config.lock` | 文件、分支、ref |
| L1 | 每个 worker 单独设 TMP/TEMP/TMPDIR、`GIT_CONFIG_GLOBAL` 和一个端口段变量（参照 Conductor，每个 workspace 10 个端口）。在现有 Job Object（Windows）或进程组（Linux，`systemd-run --user --scope -p MemoryMax=`）上加内存上限 | 临时文件、git 配置、端口（靠约定）、内存 |

- CLI 的登录目录和下载缓存（cargo registry、pnpm store）保持共享，这些缓存自带锁。构建产物放在各自的 clone 里。
- L2（OS 沙箱）在 Windows 上不可行：Claude Code 的 sandbox 不支持原生 Windows，Windows Sandbox 不能多开，也都隔离不了端口。所以 Windows 和 Linux 都能用的下一级是 L3：容器、WSL 或 VM，或者直接上独立机器。
- 什么时候升级：
  - 项目的端口、数据库或 compose 名称写死，没法参数化：这个项目用 L3。
  - 实际出现 worker 写进别的目录：上 L3。
  - 有了内存上限，内存或磁盘仍持续紧张：换服务器或 VM。
  - 凭据冲突：隔离解决不了，只能降低并发。
- Lobotomy 自己的仓库就会撞端口：`vite.config.ts` 固定使用 5173 并设了 `strictPort`，`playwright.config.ts` 设了 `reuseExistingServer: true`。两个 worker 同时跑 e2e 时，第二个会测到第一个的前端。以后用 worker 开发 Lobotomy 自己，要先把端口改成读变量。#89 已经做了这一步：前端开发服务器与 e2e 的端口取自 `LOBOTOMY_PORT_BASE`（2026-10-16）。

### 2.4 登录与合规

- **Claude Code**：官方合规页允许"用户用自己的订阅登录原版 Claude Code，包括由平台托管运行"，同时规定开发者"不得收集、存储或中转 claude.ai 的凭据或会话 token"。所以：
  - Lobotomy 不保存、不分发 Claude 的登录 token。
  - 本机的 worker 共用用户本机 CLI 的登录，现在就是这样。
  - 在服务器上，由用户自己登录。
- 已知风险（用户报告）：多个会话并发刷新 token 时会互相顶掉；在 Windows 上并发写会损坏 `.claude.json`，2.1.61 修过。这会限制 Claude worker 的并发数，需要实测。
- **Codex**：官方明确说不要把同一份 `auth.json` 给并发任务或多台机器共用，因为 refresh token 只能使用一次。同一个 `CODEX_HOME` 下多个会话并发的表现，官方没有写明，需要实测。
- **OpenCode**：Codex 负责人在 X 上公开说正在和 OpenCode 合作，支持用户用 Codex 订阅；我没找到条款层面的文字。列为待研究项。

## 3. forge 与治理

- **身份**：用户自己的仓库用 GitHub App。
  - App 免费创建，可以装在个人账号上，只选部分仓库。
  - installation token 1 小时过期，签发时可以收窄到指定仓库和权限。
  - App 私钥是 Lobotomy 自己的凭据，不是 claude.ai 的，可以保存。后端按 worker、按仓库签发 token，经 `GH_TOKEN` 或 git credential helper 交给 worker。
  - 提交作者用 bot，提交说明里加 `Co-authored-by: 用户`。
- **对别人的仓库提 issue 或 PR**：App 做不到，只能用用户本人账号或 machine user。这属于"代表用户对外"的动作，需要单独授权（用户，2026-10-15）。
- **合并治理**：
  - 分支保护：required checks 加上 "Require branches to be up to date"。
  - 个人仓库没有 GitHub merge queue（只有组织名下的公开仓库有）。替代做法是由后端串行执行"更新分支 → 等 CI → 合并"。
  - 组织名下的公开仓库可以用 merge queue，Lobotomy 本身就是。用的话 CI 要加 `merge_group` 触发。
  - 需要 rebase 时，由 worker 在本地 rebase 后用 `--force-with-lease` 推送，冲突交回 worker 处理。
- **合并决定**：CI 通过后由 Angela 决定。用户随时可以否决或接管。哪些 PR 必须给用户看，列为待决问题。
- **私有仓库的成本**：分支保护需要 Pro；Actions 在 Free 计划下每月 2000 分钟。公开仓库的标准 runner 免费，包括 Windows 和 macOS。CI 的 runner 已经能验证三个平台；能交互复现问题的环境往后放。
- **自托管可替换**：Forgejo 和 Gitea 没有 GitHub App 的对等物，bot 就是一个普通用户；Actions 兼容性 Gitea 更好。接口按四个操作抽象：bot token、开 PR、读 checks、合并。先只实现 GitHub。
- **非代码的交付物不走 forge**：存进 Lobotomy 现有的文件库（按内容哈希寻址，data-model.md §7.3），图里的 artifact 节点引用它。

## 4. 编排层

### 4.1 图

- **存储**：全局一个 SQLite 数据库（用户，2026-10-16）。理由：仓库不再是一等对象，按项目分库会让跨事情的边、附件复制和跨库操作都变复杂。这推翻了 M3 定下的按项目分库（data-model.md §10.6）。
  - 库里加 `node` 和 `edge` 两张表，配 FTS5。
  - 不引入图数据库：Kùzu 已于 2025-10 归档，DuckPGQ 自称研究项目，SurrealDB 用的是 BSL 许可。单用户、万级节点、1–2 跳的查询，用递归 CTE 就够了。
  - 代价：一个库坏了影响全部数据，所以要定期在线备份，例如用 `VACUUM INTO`。大内容继续放在文件库里。归档从"移走数据目录"变成"标一个状态"。
- **节点 8 类**：
  - `thread`：事情。它是看问题的视角，不是边界。
  - `goal`：目标。
  - `claim`：可修改的理解，带 `firmness`，取 guess、working 或 settled。
  - `question`：待定的问题。
  - `observation`：观察到的事实，例如用户原话、worker 结果、外部变化。不可变。
  - `action`：已发生的动作。不可变。
  - `step`：具体的下一步或等待，带 `resource`，取 user、agent、external 或 time。
  - `artifact`：材料或成果，带 `adopted`。
  - 对外承诺很少，不单列一类：用一条 `action` 加一个带 `owed_to` 的 `step` 表达。
- **边 8 类**：
  - `part_of`：节点属于某件事情，可以同时属于多件，事情之间不硬切。
  - `serves`：指向目标。
  - `blocks`：唯一影响队列的边。
  - `bears_on`：证据，带 ±。
  - `answers`：理解回答问题。
  - `derived_from`：来历。
  - `supersedes`：新节点取代旧节点，写明理由。
  - `relates`：自由标签，用来放各种异质关系。
- **属性约定**：
  - 来源：user、manager、role、runtime 或 external，加上 turn ID。
  - 依据：来源 ID 加复制的原文，沿用 data-model.md §10.6 的做法。
  - 系统得知的时间；可选的现实有效期 `valid_from` / `valid_until`。
  - 失效：`retired_at` 和原因。
  - 指向项目记录的 `ref`。
- **语义更新**（用户，#86 评论，2026-10-16）：
  - 仓库和代码的版本管理归 worker 环境。核心保存事情、理解、关系、委派、证据和自己的材料。外部已有版本管理的材料，核心只存「来源 + 对象 ID + 版本 ID」的引用，不再重复做一套 VCS。
  - 节点和边允许自由属性，由 agent 填写，用来辅助理解和记忆。
  - 会触发运行时行为的只有 step/resource、blocks、`due_at`/`wake_on`。普通关系和自由属性不隐式触发执行。worker 的动作仍由显式工具发起。
  - 落地前要补清三点：step 的状态及转换；blocks 怎样解除、多条阻塞怎样组合；`wake_on` 的表达方式和触发条件。答案见下。
- **已定（用户，2026-10-17）**：
  - step 只存三个状态：`open`、`done`、`dropped`（带理由）。`done` 和 `dropped` 可以重开，也要写理由。"被阻塞""在做""在等"不存，每次现算。改状态的是 Angela（`step_set`）和用户。运行时只在 time 类的 step 到了 `due_at` 时把它标为 `done`。worker 任务被采用时，运行时只发事件，不改 step，因为一个 step 可能拆成了几个任务。
  - 只有 step 能被阻塞，阻塞者是 step 或 question。阻塞者 step 标为 `done`、阻塞者 question 有了答案或被 retire、这条边被 retire，这条阻塞就解除。阻塞者被 `dropped` 不算解除：运行时发事件给 Angela，由她改计划。多条阻塞全部解除才算解除。`graph_link` 拒绝成环。解除只唤醒 Angela，不自动派 worker。
  - 不单设 `wake_on` 字段。"等什么"用 blocks、`due_at` 和固定的事件来源表达，见 §4.2。外部等待在 v1 由 Angela 设 `due_at` 定期复查；以后可以做成一种盯住外部条件的 worker 任务。周期性的复查不做，由 Angela 处理完一个 time step 时自己建下一个。
  - 自由属性是一个限大小的 JSON 对象。`graph_add` 返回同类节点已在用的键，让属性名趋于一致。运行时不读自由属性。
- **Angela 的工具（10 个）**：
  1. `graph_add`：批量新建，同时返回相似的旧节点，由她决定连接还是取代，不自动合并。
  2. `graph_revise`：取代旧节点。
  3. `graph_retire`：让节点或边失效。
  4. `graph_link`：加边。
  5. `graph_get`：按 ID 读。
  6. `graph_neighbors`：查关联，深度不超过 2。
  7. `graph_find`：按文字、类别、事情、确定程度查。
  8. `queue`：按资源分组，列出没有被阻塞的下一步。
  9. `step_set`：改下一步的状态。
  10. `thread_brief`：按预算投影一件事情：目标、有效的判断及其为何改变、待定问题、可做的和在等的下一步、采用中的成果。
- **谁来维护**：
  - Angela 显式写入，不从对话中自动抽取。依据：Graphiti 和 Mem0 的自动抽取贵，收益小。
  - 和运行时事实对应的节点（例如 worker 任务的状态），由运行时机械投影，避免状态腐烂。
  - 图是 Angela 唯一的计划面。依据：Codex 把内置的计划工具改成默认关闭，有第三方解读认为原因是两个计划面的状态会漂移。
- **账本平滑迁移**：
  - 现有的 `ledger_entry` 就是 node 表的一个子集：goal → `goal`；decision、constraint → `claim(settled)`；hypothesis → `claim(guess)`；open_question → `question`。
  - `supersedes` 和"一条只被取代一次"的规则都保留。
  - 迁移要做的是加 edge 表、扩充 kind。
  - 语义变化：默认的确定程度改为 working（暂时认定），settled 很少用。这对应"多数判断是暂时认定"（用户，2026-10-15）。
- **从 #22 吸收（用户，2026-10-17）**：
  - **引用与"依据已变"**：
    - Angela 派任务或发消息时按 ID 引用 claim，运行时原样插入原文，沿用现有 `assign` 的 `ledger` 参数（manager-actions.md §3.4）。每次引用由运行时写成一条"任务 → claim"的边。
    - 被引用的 claim 被取代或失效时，运行时把引用它的活跃任务标为"依据已变"，并唤醒 Angela，事件里列出这些任务。沿 `derived_from` 往下游传递，深度不超过 2。
    - 这个标记现算、不存。当前的 attempt 或之后发给这个任务的消息引用了新的 claim，或者 Angela 写明理由表示"不影响"，标记就消失。用户在界面上能看到它。
    - 同一件事情里没被引用的 claim 改了，只在事件里列出可能受影响的任务，不打标记。
    - 运行时不自动给 worker 发更正。用 `revise` 还是 `send_message`，由 Angela 判断。
    - 局限：用户纠正了，而 Angela 没有改 claim，这一层管不到。
  - **作用范围**：**语义更新**：`part_of` 的目标可以是事情或 step。只在某个任务有效的条目 `part_of` 那个 step；原来项目级的条目 `part_of` 对应的事情；用户级的条目 `part_of` 初始化时建好的根事情"关于用户"。不用"没有 `part_of`"表示全局，因为那和忘了挂分不开。局部的选择不自动升级；要升级，由 Angela 在更大的范围新建一条 claim，用 `derived_from` 指回原来那条。`thread_brief` 带上这件事情和它活跃 step 上的条目；Angela 新会话的开头带上根事情的条目。
  - **幂等**：每个写图的工具都带调用方生成的请求 ID，同一个 ID 重试时返回同一个结果。迟到的旧写入由"一条只被取代一次"拒绝。
  - **历史版本**：
    - node 和 edge 表不允许 DELETE，只能 retire。
    - 可变字段（step 的状态、自由属性、artifact 的 `adopted`、事情的标题等）每改一次，由 SQLite 触发器把旧值连同有效期写进历史表，不依赖各个工具自己记历史。
    - "某个时刻的图"是当时已存在、还没失效的节点和边，加上它们当时的字段值。界面可以按 Angela 的 turn 回看"她这一轮改了什么"。
    - 回看是只读的。"回到"某个旧版本做成用户发起的一组新写入（取代、重开、retire），历史照样保留。observation 和 action 是已经发生的事实，不回退；已经跑过的 worker 也不回退。
    - 这两条约束要在建表时就定下来：没记下的历史，以后补不回来。
  - **证据的保留**：复制进节点的原文永久保留。托管在 forge 上的证据（例如 CI 日志）只存链接，保留期跟随 forge；GitHub Actions 的日志默认保留 90 天。文件库里的 blob，只要还有没失效的节点引用它，就一直保留。引用的东西已经拿不到时，标为"原文已不可得"，不拿摘要顶替。v1 不按时间清理；没人引用的 blob 怎样回收，以后再定。

### 4.2 事件与唤醒

- 新增一张待处理事件表，键是事情或下一步的 ID。
  - 同一个键的多次变化合并成一次，只给当前状态，做法同 k8s workqueue。
  - Angela 的 turn 开始时，运行时一次取走全部待处理事件；turn 运行中到达的事件先排队。
  - 等待就是带 `due_at` 或 `wake_on` 的下一步。
- 唤醒 Angela 与打断用户是两件事。是否打断用户，由 Angela 判断。
- **已定（用户，2026-10-17）**：事件来源固定为下面几种，各按所列的键合并。`due_at` 对 time 类的 step 是"等到"，对其他类是"到期提醒"，只触发一次；重启时已经过期的，也只补触发一次。

  | 事件 | 合并的键 |
  |---|---|
  | 用户的消息或界面操作 | 事情 |
  | worker 任务进入要关注的状态：delivered、blocked、failed、unknown | step 或任务 |
  | step 解除阻塞 | step |
  | 到了 `due_at`，step 仍未完成 | step |
  | 阻塞者被放弃 | 下游的 step |
  | 额度恢复 | 额度域 |

### 4.3 消息

- 区分三种状态：已保存、已投递（进了哪个 turn）、对方已按它调整。现有消息的"排队、已绑定、已投递"可以沿用。
- 对外动作的结果未知时，先查证再决定是否重试。例如开 PR 时断线：先查 PR 有没有建成。

### 4.4 资源

- **订阅额度**：把余额、重置时间和消耗速度交给 Angela，在现有额度域的基础上扩展。拿不到精确值时标为未知。
- **机器**：把指标交给 Angela，由她安排；硬保护在运行时，包括内存上限和保留的磁盘余量。
- **花钱**：必须经用户同意，见 §4.6。
- **只读**：不受限（用户，2026-10-15）。

### 4.5 Angela 的位置

- **已定（用户，2026-10-17）**：Angela 使用通用的 agent 驱动，和 worker 一样启动、续接、中断、确认退出、按角色选模型。她的特殊在权限和职责，不在机制。
- 她不走 worker 协议：那是 task 级的接口，套不到一个持续的会话上。她 = agent 驱动 × 编排环境。编排环境的工具是图和任务操作，不带 clone。
- 权限和职责（提案，待细化）：
  - 只有她和用户对话，也只有她写图。worker 的结果由运行时投影成 observation。
  - 她持有编排工具：派任务、追加消息、改需求、停止、采用、回答 worker 的问题。
  - 她和用户对等：凡是她能做的，用户也能做。花钱、代表用户对外、用户指定的路径，是她必须先问用户的事。
  - 只有一个 Angela。工作、生活等领域是图里不同的事情，不是不同的 Angela。不设子 Angela。
- **已定（用户，2026-10-17）**：用户可以直接给某个 worker 发消息。这条消息同样走 `send_message`，Angela 收到一个事件。这沿用旧设计中用户和角色一对一的直通路径。
- 她是唯一长期存在的 agent，原生会话要轮换，记忆靠图。要单独设计：什么时候轮换；新会话开头放什么，例如活跃事情的 `thread_brief`、对话尾部和本地时间。现在 `recall()` 在新会话开头放账本。
- **会话轮换**：
  - **已定（用户，2026-10-17）**：由运行时自动轮换。这推翻了 research/organization-runtime.md §5、§11"第一版手动"的建议，依据是"上下文管理不应该手动做"。她的提示词版本变了、或换了 harness 时，下次唤醒开新会话。用户保留现有的"新会话"按钮。
  - 现状：她的原生会话只在用户点"新会话"（`NewNativeSession`）或换 harness 时更换。Claude Code 对 1M 上下文的模型默认在约 967K token 时才自动压缩（官方文档，2026-10）；压缩的摘要用户看不到，也改不了。
  - 其余部分先调研市面上的 personal agent 产品再定，有成熟方案就照搬（用户，2026-10-17）。调研结果见"附：会话轮换调研"。下面是据此定下的方案。
  - **已定（用户，2026-10-17）**：
    - **上下文大小决定换不换，空闲决定什么时候换。** 运行时在每个 turn 开始前判断：
      - 超过软上限：之后每个 turn 的输入带一句"会话已长，近期会换会话，要紧的先写进图"；到下一个空闲点再换。依据：MemGPT 的"记忆压力"提示。
      - 超过硬上限：这个 turn 作为本会话的最后一个，输入里要求她把还没写进图的东西写进去；turn 结束后换。依据：Codex 实验性上下文管理的"强制收尾并预留余量"。
      - 她的提示词版本变了、换了 harness、或她自己请求时：下次唤醒开新会话。她自己选择换会话，不加限制。
    - 空闲点一律取 1 小时，含义是"用户离开了"，不是缓存过期。
    - 上限按模型配置。DeepSeek：软上限 300K，硬上限 700K。理由：DeepSeek 的模型结构专门为长上下文优化；有人报告上下文长时表现反而更好（用户转述，未核实）。其他 provider 的上限还没定；测试期 Angela 用 DeepSeek，不急。
    - 不按钟点重置。依据：OpenClaw 和 Hermes 都在 2026 年撤掉了定时重置的默认值。
    - 不让模型写对话摘要。比对话尾部更早的内容，靠图、按 ID 读原文和全文搜索找回。依据：摘要和压缩的事故最多（编造用户指令、规则丢失、状态倒退）；Codex 的实验方案也不做摘要，而是"换窗口 + 笔记 + 可回查的历史"。
    - 不另开收尾的 turn。依据：OpenClaw 的静默收尾是这一块 bug 最多的机制。
    - CLI 自带的压缩只作兜底。
    - **新会话的开头**（在一个会话内冻结，便于缓存）：
      1. 这是一次轮换，以及上一个会话的 ID。
      2. 关于用户：根事情下的有效条目，上限 4K token。超了不截断，提示她整理。
      3. 活跃事情的 `thread_brief`，总共 15K；放不下的事情每件一行（标题、状态、ID）。
      4. 等用户的事和在跑的 worker，每件一行。
      5. 本地时间，以及距上一个会话过了多久。
      6. 对话尾部原文 20K token：在消息边界截断，只放双方的消息，不放工具过程。
      7. 本轮的待处理事件。
    - brief 和对话尾部都带消息 ID；新增的历史工具能按 ID 读原文，也能全文搜索，返回原话、时间和 ID。依据：Codex 的笔记记"条目 ID"而不是转述；Hermes 的 `session_search`。
    - 每个 turn 的输入开头写一行"已用上下文 N / 软上限 S"。依据：Codex 让模型看到剩余预算。
  - 后话（用户，2026-10-17）：Angela 的系统提示词。

- **测试期的模型**（用户，2026-10-17）：测试时 Angela 先用 DeepSeek API。理由：便宜、快；能力弱，更容易暴露运行时的问题，从而给出补强方向。Fable 或 Opus 太强，运行时有缺陷也能把活做完，问题藏起来。
  - 接法：DeepSeek 官方文档给出了 Claude Code 的接法，设 `ANTHROPIC_BASE_URL=https://api.deepseek.com/anthropic`、`ANTHROPIC_AUTH_TOKEN` 和 `ANTHROPIC_MODEL` 等环境变量（官方文档，2026-10）。Claude Code 本身不改，Angela 仍用通用的 agent 驱动；角色配置要能按角色设置这几个变量，不能影响 worker。
  - 型号与价格（官方价格页，2026-10）：`deepseek-flash`（V4.1-Flash）和 `deepseek-v4-pro`，上下文都是 1M。flash 每百万 token：未命中缓存的输入 0.15–0.30 美元，命中缓存 0.003–0.006 美元，输出 0.60–1.20 美元（区间为闲时与高峰）。不支持 `cache_control`，缓存由 DeepSeek 自动处理。
  - 待实测：DeepSeek 文档把"MCP servers"列为不支持，这里指的应是 API 的服务端 MCP 连接器；Claude Code 把本地 MCP 工具作为普通工具定义发送，Angela 的 MCP 工具应当可用，要实测确认。
  - API key 是用户自己的付费凭据，不是 claude.ai 的凭据，Lobotomy 可以保存。
  - **已定（用户，2026-10-17）**：用 `deepseek-flash`。V4.1 的 Pro 还没出，现在的 `deepseek-v4-pro` 比 flash 笨，也更贵。
  - 缓存：据用户所知，DeepSeek 的缓存保留时间接近无限，有报道说能保留几天；官方没有写明。所以用 DeepSeek 时，"空闲后续接要按无缓存价重读"这个成本理由基本不成立，轮换主要看上下文大小和质量。
  - 失败归类（用户同意，2026-10-17）：按 #60 的格式记录失败时，加一栏"换强模型重放是否还犯"。缺信息、工具契约含糊、状态看不到、少了事件，这类运行时的缺口要补；单纯推理或判断力不足的，不为它加运行时的关卡，以免回到"为卡坏习惯把系统整僵化"。

### 4.6 授权（用户，2026-10-17，从 #22 吸收）

- 需要用户同意的动作是：花钱、代表用户对外、合并碰到用户指定路径的 PR。执行这些动作的工具必须带"授权"参数，值是用户某条消息的 ID。
- 运行时检查：这条消息确实是用户发的，不是 Angela 的话，也不是外部内容。运行时检查不了语义（用户说的是"可以"还是"不行"），这一点靠事后的摘要让用户看到。
- 来源是 external 的节点，不能作为授权或"决定"的依据。外部资料里的指令进了图，也不变成用户的指令。
- 检查在编排层做，worker 看不到授权：
  - 超出本任务仓库的对外动作，worker 一律不提供，走编排层的工具（worker-interface.md §7），工具带授权参数。
  - 合并碰到用户指定路径的 PR 时，运行时先检查授权，再向 worker 发 `adopt`。
- 理由：用户说话就够，不需要额外点按钮，语音输入也能用；Angela 凭空写一条"用户同意了"过不了检查。
- **补充（用户，2026-10-17）**：需要授权时，Angela 发一张请求卡片。用户点选项时绑定是精确的；直接说话时，由 Angela 绑定，摘要写明"按你某时某条消息执行了 Y"。见 §5"消息的上下文"。
- 预先给的长期授权（例如"这周 20 刀以内随便花"）v1 不做，等有实际需要再说。

## 5. 界面

**骨架（用户，2026-10-17）**：依据是 10-15 讨论中用户的原话（[029] 只看双方的消息，内部过程除非 debug 不显示；[308] 会话加工作台，agent 一边回复一边在右边展示，用户也可以点；[136]–[138] 一个入口，加几条随时能看的进行中事项；[113] 按事情进入局部，不一打开就摆出巨大的总图；[122]、[241] 图主要在 agent 讲不清时给人看，是顶层 agent 的工具；[302] 重启后界面像以前一样）。
- 三栏，对话是主体。
  - 对话：一条连续的对话，只显示双方的消息。Angela 的消息里可以有引用（在工作台中打开）、卡片（请求授权、问题选项、带证据的完成卡）和事实行（例如"已转给 X"）。
  - 左栏（窄）：最上是"需要你 N"（单一计数源）；下面是进行中的事情，每件一行，带状态外观，用户离开期间不重排；最下是"活动"（后台在跑什么）和"资料"（全部成果的索引）。点事情，在工作台中打开它的简报，不改变对话。
  - 工作台（右）：可以收起，按需打开，重启后恢复。标签有五类：事情简报；材料（Markdown、图片、网页，PR 当作网页打开）；图（默认按事情显示局部）；活动；worker 详情（它的过程，以及直接给它发消息的输入框）。

下面是从调研中挑出的借鉴，括号里注明是纯展示还是需要后端支持：

1. **过程折叠**：每条回复的过程折成一行"最新动作"，可以展开，展开偏好要记住。依据：最强的痛点是"过程被隐藏又难展开，导致不信任"，而不是默认折叠本身。（纯展示）
2. **工作台只由用户替换**：agent 产出新对象时，只在标签上加未读点；对象头部能跳回来源消息。依据：反例是 ChatGPT Canvas，自动打开、改错对象，后来被撤回。（纯展示）
3. **成果用稳定 ID 加版本**：引用绑定到（ID，版本）；打开旧引用时提示"现为 vN"；全局有成果索引；每个版本都可达。（需后端）
4. **事情级状态**：运行、等你、阻塞、完成、失败、取消。"需要你"= 等你 + 完成了但没看过；"已看"要持久保存。（需后端）
5. **单一计数源**：侧栏、托盘、提示共用一个集合计数。依据：Cursor 的两处计数不一致，官方承认是"两套说法"。（纯展示）
6. **停止分三档**：停止当前回复、停止这件事情及其 worker、取消后续计划，每档写明作用范围；停止后列出已完成和未完成的动作。依据：调研中没有产品把停止的范围分清。（需后端）
7. **引用 chip**：选中的片段、成果或事情变成输入框里的 chip，发送后可以跳回原处。（展示加后端：turn 要携带引用 ID）
8. **重启恢复**：草稿、以消息 ID 为锚点的滚动位置、工作台对象、展开状态存在本地；事情的状态以后端为准重建，不从界面缓存恢复。依据：Codex 重启后线程消失、未读标记清空、顺序错乱。（主要是展示）
9. **完成卡带证据**：每条要求标为已验证、未验证或阻塞，并附证据。（需后端）

## 附：会话轮换调研（2026-10-17）

三路资料调研：消费级的 personal agent 与陪伴产品；开源与开发者框架；评测证据与缓存成本。没有实测。标注"官方"的出自官方文档、论文或维护者的说法；"逆向"出自泄露的提示词或第三方逆向。

**市面上的做法**
- 消费级产品里，"一条对话"只是界面，不是一个模型会话。产品要么每轮重新拼上下文（Tolan：近期消息摘要 + 人设卡 + 检索到的记忆 + 应用状态，官方案例 2026-01），要么保留一个滚动窗口，接近上限时压缩（Claude.ai，官方 2025-11；Poke，逆向）。没有一家公开按时间轮换。
- 按钟点重置只在开源框架里出现过，而且两家都在 2026 年撤掉了默认值：OpenClaw 把 `session.reset.mode` 的默认改为 `none`（PR #111140，2026-07-19），起因是用户抱怨每天 4 点的重置毁掉上下文；Hermes Agent 在 v2026.9.11 去掉了重置计时器。Hermes 的文档仍建议在自然的节点（一件事做完、换话题、一天开始）手动开新会话，理由是长会话贵，而且记忆整理"几乎没机会运行"。
- 拼进上下文的部分各家相同：一段短而稳定的用户档案（约 1–4K token：ChatGPT 的档案约 4K，Claude.ai 的综合约 1K，Hermes 约 1.3K）、之前对话的摘要、检索到的记忆、时间等元数据、一段按 token 计的近期原文。
- 近期原文的长度没有对照实验，常见的默认值是 20K token：OpenClaw 的 `keepRecentTokens` 是 20,000；Codex 压缩后保留最近 20K token 的用户消息（源码 `compact.rs`）；Hermes 保留最近 20 条消息，精简模式 10–25K。
- 轮换或压缩之后，全部历史仍可搜索：Hermes 用 SQLite FTS5 的 `session_search` 返回原始消息；Claude.ai 压缩后保留完整历史供模型引用；Letta 有 recall 存储。
- 开头的内容在一个会话内冻结，便于缓存：Hermes 在会话开始时冻结记忆快照，会话中的新记忆要到下一个会话才看得到；Claude Code 每个会话读一次 CLAUDE.md。
- 整理记忆多在后台、按空闲或压缩触发，而不是在重置前：Codex 的 memories 在线程空闲 6 小时后抽取；Letta 在每次压缩时触发反思；ChatGPT 的 "Dreaming" 在后台综合（2026-06）；Tolan 每晚压缩。

**证据**
- 长上下文仍会变差，各模型差别很大。Chroma "Context Rot"（2025-07）测了 18 个模型，全部历史（约 113K）都比只给相关的约 300 token 差。2026 年的 MRCR v2 8-needle：GPT-5.5 在 128–256K 为 87.5%，Opus 4.7 为 59.2%，Opus 4.6 在 1M 为 78.3%。没有找到 DeepSeek V4.1 Flash 的长度曲线。
- 多轮对话本身就会变差："LLMs Get Lost in Multi-Turn Conversation"（ICLR 2026）测了 15 个模型，任务分散到多轮后平均下降 39%；作者建议带着整合过的摘要开新对话。
- 记忆策略：历史超过约 100K 后，"摘要或观察 + 近期原文 + 检索"的组合优于全量上下文，也优于单纯检索（BEAM、LongMemEval、Mastra 的自报结果）。事实更新和矛盾消解，所有方法都做不好（MemoryAgentBench 中多跳更新不超过 7%）。
- 摘要和压缩会出错：编造用户指令并执行（claude-code #46602）、压缩后 CLAUDE.md 的规则被忽略（#6354）、状态倒退到旧步骤（#24792）、Codex 忘了自己刚做的 23 处修改（codex #5957）、OpenClaw 的"先确认再动手"在压缩中丢失后删了 200 多封邮件（AIID #1542）。逐条从原文抽取的事实，比保留原始片段差（arXiv 2601.00821，单作者）。
- 压缩前的静默收尾（OpenClaw 的 memory flush）是这一块 bug 最多的机制：不触发（#4836、#19488、#47143）、死循环（#66058）、和 Codex 原生压缩冲突（#126171）。重置时它只保存最近 15 条消息，不做收尾；要求加收尾的 #45608 仍开着。
- MemGPT（2023）在上下文约 70% 时给模型一个"记忆压力"提示，让它先保存。

**缓存成本**（官方，2026-10）
- Claude Code：订阅额度内主对话的缓存有效期 1 小时，API key 下 5 分钟。Pro 和 Max 上，空闲超过约 1 小时、且超过 100K 的会话，恢复时会弹出"从摘要恢复"。缓存读取按 API 计价约为原价的 0.1 倍（Opus 5.5 为 0.05 倍）。订阅额度里缓存怎样折算，没有公开。
- OpenAI：缓存空闲 5–10 分钟到 1 小时失效，可选 24 小时保留。
- 推算：缓存失效后续接一个 200K 的会话，此后每一轮的成本约是 30K 开头的 6.7 倍；500K 约 17 倍。

**Codex 的实验性上下文管理**（读源码与本机模型目录，codex-cli 0.162.0-alpha.17.2，2026-10-17）
- 开关是 `[features.context_management] experimental_mode`，阶段为 under development，默认关闭。只对 ChatGPT 登录的 Plus / Pro 账户、OpenAI 自家后端、模型目录里标了 `supports_experimental_context` 的模型生效。本机目录中 gpt-6-astra、gpt-6-sol、gpt-6-luna、gpt-5.6-sol 支持；各模型的 `token_budget.enabled` 目前都是 false。
- 机制（`codex-rs/core/src/session/token_budget.rs`、`codex-rs/ext/history-notes`）：
  - 不做摘要式压缩，而是换一个全新的上下文窗口。新窗口"不会自动包含当前对话"。
  - 模型有私有笔记 `notes`（读、写、追加、搜索；每个文件不超过 1MB），跨窗口保留。
  - 模型有只读的 `history` 工具，可列出各个窗口、按窗口和条目 ID 读原文、按字面子串搜索。每个非助手条目后面带 `[id: ...]`。
  - 新窗口开头注入一段不超过 4KB 的 "thread hint"，由后端生成；`<context_window>` 里写明上一个窗口的 ID。
  - 模型能看到剩余的上下文预算，并有 `get_context_remaining` 工具。
  - 换窗口由模型自己调用 `functions.new_context` 触发。剩余不到 6,144 token 时，提示它先记笔记再换；预算用尽时，强制它"只写一次笔记，然后换窗口"，为此在阈值之外预留 16,384 token。
