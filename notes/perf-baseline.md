# 性能基线

> Status: 第一份基线（2026-10-04，M1 第 5 个增量）
> 依据：[frontend.md](frontend.md) §5；[#6](https://github.com/vorton-lang/Lobotomy/issues/6) §5"先建立基线，再据结果确定预算"。

本文记录 GUI 性能基线的测法与参考数据。预算还没有定，要等有了不同机器、不同平台的数据之后再定。

## 1. 怎么跑

```powershell
cd frontend
npm run bench
```

脚本会先编译 release 版后端和前端的生产构建，再运行场景。

- **被测对象**：前端用生产构建，由 `vite preview` 提供；后端是 release 构建，接假 Codex（`backend/crates/lobotomyd/tests/fixtures/fake-bench.mjs`）和假 Claude（`fake-claude.mjs`）。数据都是合成的，内容固定，所以不同次运行的结果可以比较。
- **浏览器**：Windows 上用本机 Edge，其他平台用 Playwright 自带的 Chromium（需要先运行 `npx playwright install chromium`）。两者都基于 Chromium，内存数据取自 DevTools 协议。默认无头运行。
- **结果**：写入 `frontend/bench-results/`，不提交。参考数据记在本文 §3。
- **CI**：每次推送到 main，在 Windows 和 Ubuntu 的 GitHub 托管机器上各运行一次（`.github/workflows/ci.yml`）。结果写在 job 的摘要里，并作为 artifact 保留；只记录，不设门槛。共享机器的数据波动大，所以 §3 的本机数据仍是参考。

## 2. 场景与指标

**数据**：一个任务，共 5 个 turn。前 4 个 turn 各 600 个 item，内容混合：带代码块和表格的 Markdown 回复、几行到几百行输出的命令、reasoning、文件改动、todo。最后一个 turn 包含一条 100,000 行的命令输出，以及一条没有闭合的 Markdown（代码围栏、强调、列表）。数据走真实的 runner 写入，共 2418 个 item。

| 场景 | 测什么 |
|---|---|
| 打开 | 从导航开始，到最新一条出现在屏幕上的时间；期间的长任务；快照和首页请求的往返时间；内存与 DOM 节点数。再刷新一次，测热启动 |
| 滚回开头 | 每帧向上滚 1500 像素，一路加载更早的分页，直到第一个 turn 出现。测总耗时、各页请求的往返时间、帧间隔、长任务；滚完后的内存与 DOM 节点数 |
| 搜索到开头 | 按 Ctrl+F，输入只在第一个 turn 出现的词。测从开始输入到那一行出现在屏幕上的时间，含 200 ms 的输入防抖、搜索请求和沿途加载的分页 |
| 空闲时打字 | 在输入框以每 30 ms 一个字符的速度打字，测每次按键从 keydown 到下一帧开始的时间 |
| 十万行输出 | 在查看器中打开全文，测到第一行出现的时间；再按 Ctrl+End，测到最后一行出现的时间 |
| 流式更新 | 一条命令运行 8 秒，每 20 ms 更新一次输出。每行带有写入时间，测屏幕比输出落后多少；同时测帧间隔、长任务，以及期间打字的输入延迟 |
| 后端重启 | 杀掉后端，在同一端口重启。测后端开始监听后，GUI 多久重新连上、对话多久恢复 |
| Claude 的流式回复 | 在设置中把 Malkuth 切换到 Claude。一条回复流式输出 8 秒，每 20 ms 一行，每行带有写入时间。测屏幕比回复落后多少，同时测帧间隔、长任务和期间打字的输入延迟。测完切回 Codex。放在最后，因为它让对话末尾多出很长一条回复 |

没有闭合的 Markdown 只检查一件事：它要按 Markdown 渲染出来，而不是退回纯文本。

## 3. 参考数据

机器：AMD Ryzen AI 9 H 365（20 线程）、31 GB 内存、Windows 11 26200、Edge 154、120 Hz 屏幕。提交 6e508ca，2418 个 item。下表取同一天连续两次运行的数据，两次结果相近。

| 场景 | 结果 |
|---|---|
| 打开 | 最新一条在 182–190 ms 时可见；没有长任务；快照请求 3–8 ms，首页请求 6–8 ms；堆 3.2 MB，DOM 节点 266 |
| 刷新后再打开 | 92–101 ms |
| 滚回开头 | 2.2 s，加载 19 页；分页请求中位数 5.6 ms；帧间隔最大 8.8 ms，没有长任务；滚完后堆 7.2 MB，DOM 节点 720。这是修复滚动 bug 之后单独运行一次的数据；修复前是 9.4 s，见 §4 |
| 搜索到开头 | 438 ms，其中搜索请求 18 ms，加载 19 页，每页中位数 9.5 ms；没有长任务（这一项在加入搜索后单独运行一次，提交 2808bbe 之后） |
| 空闲时打字 | 中位数 1.7 ms，p95 2.2–6.4 ms |
| 十万行输出 | 查看器 88–112 ms 显示第一行；Ctrl+End 后 160 ms 显示最后一行；没有长任务；堆 12.9 MB |
| 流式更新 | 屏幕落后输出：中位数 18–19 ms，p95 28–34 ms，最大 41–137 ms；帧间隔最大 9.7 ms；没有长任务；期间打字中位数 5.5–5.9 ms |
| 后端重启 | 后端 180 ms 内开始监听，GUI 再过约 330 ms 重新连上，对话随即恢复 |
| Claude 的流式回复 | 屏幕落后回复：中位数 14–20 ms，p95 28–29 ms，最大 31–42 ms；帧间隔最大 10.4 ms；没有长任务；期间打字中位数 5.5–6.4 ms。同一台机器，2026-10-10 连续两次运行，M2 加入 |

## 4. 测量中弄清的两件事

**输入延迟只测到下一帧开始。**
- Chromium 的 Event Timing 能测到画面呈现，但在自动化浏览器里不可靠。
  - 流式更新期间，它报告按键要 300–980 ms 才呈现，有窗口模式也一样。
  - 但同一时段主线程空闲，下一帧在 10 ms 内开始。
  - 用 DevTools 录屏，每次按键都有一帧画面，间隔约 45 ms，正好是"30 ms 打字间隔加上处理时间"。一开录屏，Event Timing 的最大值也降到 32 ms。
  - 浏览器刚启动后的第一次测量也有同样的现象，与页面在做什么无关。
- 结论：这是自动化浏览器在没有其他出帧需求时推迟出帧造成的，不是界面的延迟。
- 所以基线只用"keydown 到下一帧开始"，它衡量的是主线程对输入的响应。真实窗口中按键到画面呈现的时间，目前没有测。

**"滚回开头"原先慢，是因为一个 bug。**
- **原先的判断**：第一次测得 9.4 s，当时认为时间花在虚拟列表第一次测量条目的真实高度上。这个判断不对。
- **发现过程**：CI 的机器更慢，这个场景在 120 s 内滚不到顶。在本机把 CPU 降速 4 倍可以复现：对话停在顶部，不再加载更早的分页。
- **原因**：加载更早的一页时，列表应保持眼前的行不动，新内容从上方插入；这个"正在插入"的状态在新的一页到达之前就被清除了。新的一页于是不补偿滚动位置，列表停在顶部；在顶部继续往上滚不产生滚动事件，也就不再触发加载。机器越慢越必然发生。在快的机器上也常发生，所以滚动被拖慢。
- **修复与回归测试**：现在只在最早的一条记录变化（更早的一页真正插入）之后才清除这个状态。修复后本机 2.2 s，CPU 降速 4 倍时 10.7 s、8 倍时 24 s，都能滚到顶。端到端测试加了 CPU 降速 4 倍的回归测试。
- **这个数字的含义**：这个场景每帧滚 1500 像素，衡量的是遍历全部内容的吞吐量，不代表用户等待的时间。

## 5. 还没有覆盖

| 内容 | 原因 |
|---|---|
| 多个 agent 同时流式输出 | 现在只有 Malkuth；M3 的多项目或 M4 加入 Angela 后补上 |
| 会话切换 | 现在只有一个 Thread；M3 的项目切换或 Inspector 做出来后补上 |
| 窗口中的按键到呈现 | 见 §4 |
| 客户端读得慢时的重新同步 | 后端测试已覆盖：落后超过推送缓冲的客户端会收到 `resync`（`backend/crates/lobotomyd/tests/gui.rs`）。GUI 收到后重新取快照的耗时，与"刷新后再打开"相近，没有单独测 |
| macOS 上的数据 | CI 只在 Windows 和 Ubuntu 上运行 |
