# 数据模型：业务对象、命令与对话记录

> Status: 设计决定 v0.1（2026-10-04）；§9 的汇总是草案
> 按 [#7](https://github.com/vorton-lang/Lobotomy/issues/7) 逐项讨论；§1–§8 是已确认的决定，§9 是 M1 的对象与命令汇总，§10 是项目边界，未定事项列在 §11。
> 依据：[#6](https://github.com/vorton-lang/Lobotomy/issues/6) §1（SQLite 是业务事实的唯一权威）、#7 及其[讨论补充](https://github.com/vorton-lang/Lobotomy/issues/7#issuecomment-5953401457)、[harness-adapter.md](harness-adapter.md)、[roles-and-tasks.md](roles-and-tasks.md)、[frontend.md](frontend.md) §3。

## 1. 命令

所有状态变化都经后端的命令完成。GUI、调度器和 role（经 MCP）调用同一组命令（#6 §1）。

- 命令按领域命名，例如建任务、启动 turn、报告 `done`、验收。`admit / claim / finish` 不作为 API 名称。
- 每条命令写明五项：
  1. 调用者与权限；
  2. 前置条件；
  3. 同一事务内写入的内容；
  4. 幂等键；
  5. 经 outbox 执行的副作用。
- 命令清单见 §9.2（草案）。
- **拒绝与不变式错误分开**（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)，2026-10-05）。
  - 前置条件不满足时，命令被拒绝，带一个代码，什么也不写。调度器把拒绝当作"现在没有事可做"。
  - 存储的状态违反了代码依赖的规则时，例如读到不认识的阶段，报不变式错误。等待不会让它消失，所以调度器把它当作错误记录，不当作拒绝。
- **读操作使用单独的只读连接**（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)，2026-10-09）。
  - 写操作仍只经过唯一的写连接，命令的事务不会交错。
  - 数据库是 WAL 模式：读不等写，写也不等读。GUI 每 100 ms 查看事件日志，不再占用写连接。
  - 每次读在一个读事务里完成。其中的所有查询看到同一时刻已提交的状态，即使期间有命令提交。
- **一个数据目录只运行一个后端。** 后端在数据目录下的 `lock` 文件上持有独占锁；第二个后端打开同一目录时报错退出。进程结束时，操作系统释放锁。
- **迁移在关闭外键的情况下执行**，每个迁移提交前检查外键。迁移因此可以按 SQLite 的"十二步"重建被其他表引用的表，例如修改 CHECK 约束。

## 2. 占用

占用分两层。每层的资源在同一个事务中一次取得。

| 层 | 持有者 | 资源 | 取得 | 释放 |
|---|---|---|---|---|
| 任务层 | 任务 | role 及其槽位 | 任务开始执行时 | 任务完成或放弃时 |
| turn 层 | turn | role 的运行权 | 登记 turn 时 | turn 结束时。结果为 unknown 时，对账结束后才释放 |

v1 中 role 与槽位一一固定，因此任务层不会出现"取得了 role，却没有取得工作目录"的半占用（[#1](https://github.com/vorton-lang/Lobotomy/issues/1)）。Reviewer 没有固定槽位，审查现场在固定的候选成果上单独物化（harness-adapter.md §3）。

**语义更新**（[#11](https://github.com/vorton-lang/Lobotomy/issues/11)，2026-10-04）：turn 层原来是"native session 的运行权"。native session 改为按任务划分（§4.1）后，按 session 的屏障挡不住这种情况：放弃 A 时 A 的 CLI 仍在运行，B 用新 session 在同一个槽位里启动第二个 CLI。因此改为 role 的运行权。

### 唯一约束

以下约束由数据库强制，不依赖调用方自行检查：

- 每个 task 最多一个未关闭的 attempt。
- 每个 role 最多被一个任务占用。
- 每个 role 最多一个未结束的 turn，无论在哪个 native session 中。已登记、运行中、unknown 都算未结束。

## 3. turn 与消息投递

### 3.1 turn

- 一个 turn 就是一次 CLI 进程运行（harness-adapter.md §1.1）。
- 运行时在启动 CLI 前登记 turn，生成 turn_id（harness-adapter.md §1.3 第 8 条）。
- GUI 的 Thread → Turn → Item 中，Turn 使用同一个 turn_id，不另设编号（frontend.md §3）。
- **MCP token 按 turn 发放。**
  - 每个 turn 本来就要重新传 MCP 配置（harness-adapter.md §1.3 第 2 条），按 turn 发放 token 没有额外的调用成本。
  - token 与发放它的 turn 永久对应。`done` 等调用因此直接绑定到 turn，不按"角色当前任务"反查归属。
  - turn 结束后，如果旧进程仍用该 token 调用，后端把调用记为迟到。迟到的调用不能推进状态。
  - 更换 URL 不影响 prompt cache：Codex 已实测，第二个 turn 的缓存命中与不更换相同（harness-adapter.md §1.4）。Claude 待 M3 实测。

### 3.2 turn 的状态

| 状态 | 进入条件 |
|---|---|
| 已登记 | 运行时在同一个事务中写入 turn 记录、MCP token 和绑定的输入消息。CLI 尚未启动 |
| 运行中 | CLI 已启动。运行时记下 pid 与进程启动时间，用于在 pid 被复用时区分进程 |
| 已结束 · completed | 运行时收到 harness 的 turn 结束事件（Claude `result`，Codex `turn.completed`），且 CLI 已退出 |
| 已结束 · failed | harness 报告错误，例如额度被拒、登录失效、参数错误；或者 CLI 自行退出，没有 turn 结束事件，例如启动时拒绝参数或权限模式、崩溃。失败信息取 harness 的错误事件；没有错误事件时，取退出状态与 stderr 的开头。环境不允许权限模式时，失败种类为"权限模式不被允许"（harness-adapter.md §1.9）。CLI 在 stdout 上没有任何输出时，记为"harness 没有开始这个 turn"（§3.4）。按系统故障通知（manager-actions.md §6） |
| 已结束 · interrupted | CLI 已退出，没有 turn 结束事件，且是 Lobotomy 让它停下的：用户中断、停止组织，以及对账结果 |
| unknown | 后端重启时，处于"已登记"或"运行中"的 turn 都改为 unknown |

completed 只表示 turn 正常结束，不表示任务完成。任务完成取决于 `done` 与验收（harness-adapter.md §4.1）。

CLI 自行退出原先记为 interrupted，现在记为 failed（**语义更新**，#13，2026-10-04）。实测中，受管 Codex 不允许无沙箱模式，启动时只在 stderr 写出原因就退出；记为 interrupted 时，GUI 只显示"被中断"，用户以为继续即可恢复。两种结果之后可做的事相同：继续、新建 native session 或放弃。失败信息中的 stderr 去掉了本 turn 的 MCP token；stderr 全文保留在原始输出中。

### 3.3 对账

"待对账"只核对一件事：CLI 进程是否已经退出。

只核对这一件事的理由：

- `done` 等业务命令在发生时已写入 SQLite；对话 item 在完成时已落库。
- Lobotomy 不恢复执行现场（harness-adapter.md §1.7），因此不需要从 harness 的会话文件重建业务事实。

核对方法：

1. 运行时按记下的 pid 与进程启动时间检查进程。
2. 如果后端在记下 pid 之前已崩溃：
   - Windows：进程以挂起方式创建，记下 pid 之后才运行（harness-adapter.md §1.8）。没有 pid 就表示 CLI 从未运行，turn 记为 interrupted（**语义更新**，2026-10-04）。
   - Linux：运行时按命令行中的 turn 标识查找进程。Codex 的 MCP URL 在命令行参数中；Claude 的 MCP 配置文件按 turn_id 命名。尚未实现，Linux 适配时补上。

核对结果：

- **CLI 已退出**：turn 记为 interrupted，运行时释放 native session 的运行权。
  - 已有 `done` 的采集意图时，运行时照常采集（harness-adapter.md §4.1）。
  - 没有采集意图时，槽位保持原样，等用户选择继续、新建 native session 或放弃（harness-adapter.md §3）。
- **CLI 仍在运行**（例如 Linux 上 harness 没有响应 SIGTERM）：turn 保持 unknown，运行时定期检查进程是否退出。GUI 显示"上一个 turn 的进程仍在运行"，并提供"终止"。运行时不自动终止进程。

### 3.4 消息投递

| 状态 | 判断依据 |
|---|---|
| 排队 | 消息在 role 的收件箱中，尚未绑定到 turn |
| 已绑定 | 与 turn 登记在同一个事务中写入 |
| 已投递 | CLI 已启动，stdin 写入并关闭成功 |

- 登记 turn 时，运行时按到达顺序绑定收件箱中全部排队的消息。
- 消息投递后，跟随所在 turn 的结果：completed、failed、interrupted 或 unknown。
- "已处理"不作为机器状态。模型是否按消息行事属于语义判断；机器能确认的只有"投递它的 turn 是否正常结束"。
- 输入是否已进入 harness 自己的会话记录：Claude 额度被拒时，输入在报错前已写入（§8.3）；其他中断时刻仍需实测（harness-adapter.md §6）。
- **所在 turn 未正常结束时，消息不自动重投。** resume 接续的是原来的 native session，其记录中可能已有这条消息；自动重投可能造成重复。GUI 把这些消息标为"所在 turn 未正常结束"，由用户决定继续还是重发。
- **harness 没有开始的 turn，继续时原样重发**（**语义更新**，2026-10-04）。CLI 在 stdout 上没有任何输出就退出时，例如启动时拒绝参数或权限模式，输入没有进入任何会话。原来的"继续"只发一段"上一个 turn 失败"的说明，那次的输入因此丢失：受管环境中第一个 turn 被拒时，执行者从没见过任务说明。现在用户选择继续时，运行时把那次的输入原样作为新 turn 的输入，不加说明；绑定的消息改绑到新 turn，投递状态清空。这不会造成重复，因为 harness 从没收到过这些内容。
- 因额度失败的 turn 如何处理，见 §8.5。

## 4. 任务流（M1）

### 4.1 attempt

- 每次进入执行阶段，运行时开一个新的 attempt。进入执行的情况有四种：任务开始、验证失败、退回、重开。
- attempt 内每次运行 CLI 是一个 turn。同一个 attempt 内接续时，运行时只新建 turn，不新建 attempt。例如：执行者提问后用户回答，turn 被中断后用户选择继续，更换 native session 后的第一个 turn。
- 执行者的 `done` 被采集为候选成果时，或任务被放弃时，attempt 结束。之后的验证与验收针对这个 attempt 产出的候选成果。`done` 的采集被体积护栏挡下时，attempt 继续（harness-adapter.md §4.1）。

turn 是执行单位：一个进程、一个 MCP token，对账按 turn 进行。attempt 是业务单位：一次执行交出一份候选成果，证据与验收针对它。

**native session 按任务划分**（[#11](https://github.com/vorton-lang/Lobotomy/issues/11)，用户确认，2026-10-04）：

- 执行者在任务的第一个 turn 时新开 native session，任务关闭（完成或放弃）时结束它。任务有明确的边界，上一个任务的上下文对下一个任务基本没有帮助。
- 同一任务的多个 attempt（验证失败、退回）沿用同一个 session。上一轮做了什么、为什么被打回，对修改有用。
- 重开的任务新开 session（§4.6）。
- 不属于任何任务的消息（role 空闲时用户直接发送）使用 role 的一个独立 session。
- 用户随时可以手动新建 native session。新 session 开始时，运行时重发这一轮的完整开工说明：任务说明，加上"初始改动"的提示和开工时有冲突标记的文件。冲突文件记在 attempt 上。原来只重发任务说明，新 session 不知道工作目录里有冲突标记（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)）。
- 采集被挡下时，role 同样停下，等用户放行、丢弃或继续（harness-adapter.md §4.1）。
- 异常后停下（harness-adapter.md §1.7）只针对当前 attempt 内的异常 turn。上一个 attempt 已经结束时，采集或用户已经推进了工作，它的异常 turn 不再挡住新 attempt；"继续"也只能作用于当前 attempt。这样新任务、重开和新 attempt 都不会被旧的异常状态阻塞。

### 4.2 离开执行阶段后的消息

任务离开执行阶段后（验证、审查、验收），发给执行者的消息进入收件箱排队，任务回到执行时运行时再投递。

- 理由：候选成果已经固定。执行者此时如果运行 turn，可能修改槽位，使槽位与候选成果不一致；4.3 的重新物化也可能覆盖这些修改。
- 代价：验收期间不能与执行者对话。用户需要提问时，退回任务并附上问题。

**任务关闭时，它的排队消息不再投递**（**语义更新**，#14，用户确认，2026-10-04）。原来写的是"任务回到执行或关闭时再投递"。

- 实测中出了问题：
  1. 用户在执行者的 turn 运行时发了补充要求，那个 turn 随后报告了 done，补充要求就排在了候选成果之后；
  2. 验收关闭任务后，补充要求被投递到一个不属于任何任务的 turn。执行者照做并报告 done，但报告不能推进任何任务；
  3. 修改没有进入验收结果。下一个任务开始时，槽位被重写，修改从工作目录中消失，只留在采集记录里。
- 现在的规则：
  - 验收时，如果用户发给这个任务的消息还没投递，用户必须二选一：
    - **退回**：消息随退回进入新的 attempt，产出的修改会成为候选成果，照常验证、验收；
    - **验收，不再投递**：验收请求列出这些消息，后端核对列出的就是全部未投递的消息，然后把它们标为"未投递"，并记在验收决定里。
  - 放弃任务时，它的排队消息标为未投递，并记在放弃决定里。
  - 运行时发给任务的排队消息（例如"完成条件已更新"）在任务关闭时一并作废，不需要用户决定。

### 4.3 回到执行时的槽位

- 默认：槽位保持原样，执行者接着修改。HEAD 仍是槽位物化时的集成版本，`git diff` 显示整个任务的改动。
- 例外：候选成果在验证时被 rebase 到新的集成版本时，运行时把槽位重新物化为 rebase 后的候选成果。有冲突时，冲突标记写入文件。HEAD 设为新的集成版本。
- 4.2 保证此时槽位内容等于候选成果，因此重新物化不会丢失修改。
- v1 只有一个 Worker，任务进行期间集成版本一般不前进，这个例外很少出现。

### 4.4 修改完成条件

- 用户随时可以修改完成条件。每次修改生成一个新版本，不打断正在运行的 turn。
- 任务在执行阶段时，运行时把新版本作为一条消息投递给执行者。
- 任务在验证或验收阶段时，运行时不自动退回任务，更新消息按 4.2 排队。验收请求带完成条件版本；版本不符时，验收被拒绝。用户按新版本重新判断，再决定验收或退回。
- 已有的证据仍绑定旧版本。

### 4.5 证据何时作废

| 证据 | 绑定 | 作废条件 |
|---|---|---|
| 检查结果 | 成果内容、基线、检查配置 | 三者任一变化。完成条件的文字变化不使其作废 |
| 验收 | 成果、完成条件版本、集成版本头 | 提交时任一项与当前值不符（CAS） |
| 审查结论（M2） | 成果、完成条件版本 | 完成条件版本变化。基线变化后能否沿用，M2 再定 |

以下变化不使证据作废：role 下线后再上线、更换 native session、展示字段变化。

### 4.6 重开

- 只能重开已关闭的任务，即已完成或已放弃的任务。重开建立新的 attempt，任务进入排队。
- 代码起点：最后一份候选成果 rebase 到当前集成版本；没有候选成果时，从当前集成版本开始。对已完成的任务，两者相同。组合的结果按"任务、候选成果、集成版本"三者固定，三者相同时重用（#12）。
- 用任务之外的改动建成的任务，在还没有候选成果时，以那份改动代替候选成果，代码起点的算法相同（#14）。
- 继承：任务 ID、当前完成条件版本、审查预算（不重置，roles-and-tasks.md §2.2）。
- 不继承：检查结果、审查结论。
- **语义更新**：原来写的是"native session 按 role 管理，重开时不更换"。现在任务关闭时它的 session 已经结束，重开时新开 session（§4.1）。新 session 收到任务说明，槽位物化为上面的代码起点，agent 从代码状态接手。

## 5. 副作用与回执

每个副作用都按同一顺序进行：

1. 运行时把意图写入 SQLite，与引起它的业务变化在同一个事务中提交。
2. 运行时执行副作用。
3. 运行时记录回执。

回执丢失时：能安全重做的副作用，运行时重做；不能重做的，运行时核对实际状态。

| 副作用 | 意图记录 | 回执 | 回执丢失时 |
|---|---|---|---|
| 启动 CLI | turn 记录（已登记） | pid；turn 结束事件 | 按 §3.3 对账。运行时不自动重启 CLI |
| 物化槽位或验证现场 | 物化记录：现场、generation、目标提交 | 检出完成后记为"就绪" | 运行时原地重做：先快照、再检出，中断的检出因此被补完。目标文件被未跟踪的文件挡住时，运行时隔离旧目录，以新 generation 重做（§6）。**语义更新**（2026-10-04）：原来先核对目录是否等于目标（harness-adapter.md §3） |
| 采集与 pin | 每个 turn 结束时的采集意图；报告 `done` 的 turn 标为候选成果（harness-adapter.md §4.1） | pin 的 commit_id | 按 #6 §2 的发布协议处理 |
| 运行检查 | 检查记录：成果、基线、检查配置 | 检查结果 | 重跑 |
| 物化预览 | 验收事务中的 outbox 记录 | 预览已到达的集成版本 | 比较主仓库与目标版本后重做。只物化最新的集成版本，跳过中间版本：写入一个版本后，只有更早版本的预览记录被视为已覆盖；写入期间新验收的版本仍会被写入（#12） |
| 系统通知 | 通知意图 | 显示确认 | 不补发系统通知，GUI 内照常显示。宁可漏发一次，也不重复 |

- 启动 CLI 不能重做：重做意味着模型再运行一次。turn 记录本身就是意图与回执，不另进通用 outbox。
- **物化预览前先检查，不一致就停。** 写入前，运行时确认主仓库的工作区仍等于上次物化的版本。不一致时（例如用户手动改过文件，或文件被其他程序锁住），运行时停止物化，按系统故障通知（manager-actions.md §6），不覆盖文件。"用户不手工修改项目文件"只是前提假设，运行时不依赖它覆盖文件。
- **检查在固定的验证现场运行**，不在执行者的槽位中运行。每次验证时，运行时把验证现场物化为 rebase 后的候选成果，被忽略的构建缓存保留。理由：槽位内容不一定等于 rebase 后的结果；检查可能生成或修改文件。M2 的审查现场复用同一套物化机制。
- `done` 与采集的顺序、验收的原子边界已确认，见 harness-adapter.md §4.1、§4.2。
- **执行出错时停下，等用户重试**（用户确认，2026-10-04）。物化、采集或验证在执行时出错（例如文件被占用、磁盘已满）时，运行时停下这项工作，记下原因并在 GUI 中显示，不自动重试。用户选择"重试"后再执行。
  - 失败状态只保存在后端进程中。后端重启后，未完成的意图会再执行一次；重启被视为用户的操作。
  - 理由：常见原因多是持续的，自动重试只会反复失败；失败若只写进日志，role 看上去只是卡住；验证重试会重跑全部检查命令。
  - 物化预览出错时同样停止，等用户"重试预览"（上文）。

## 6. 磁盘占用与回收

Lobotomy 在磁盘上创建的每个目录或文件，在 SQLite 中都有归属记录和回收条件。不允许产生没有回收条件的内容。"隔离""保留现场"都是中间状态，不是处理完毕。

| 内容 | 回收条件 |
|---|---|
| 隔离的旧现场 | 新 generation 就绪后删除。物化的前提是旧内容已采集，因此其中没有需要保留的内容 |
| 采集未覆盖而保留的现场 | 不额外占用磁盘，但槽位不能复用，直到问题解决（harness-adapter.md §4.1） |
| 验证现场 | 数量固定，复用 |
| 审查现场（M2） | 任务关闭时删除 |
| 每个 turn 的 MCP 配置文件 | turn 结束时删除 |
| 大输出与原始输出文件 | 见 §7.5 |
| jj 中的采集与 pin | 每个 pin 都有归属（task、attempt、turn）。保留期与回收策略待定，定下之前不删除 |

- 删除失败时（例如 Windows 上文件被占用），运行时定期重试。持续失败时，GUI 显示占用的空间和原因。
- 运行时启动时清扫 Lobotomy 的数据目录：删除没有归属记录、或已满足回收条件的内容。清扫只在 Lobotomy 的数据目录内进行。运行时先写归属记录、再创建内容，因此正常运行不会产生没有记录的内容。

## 7. 对话记录

### 7.1 Thread

- Thread 按 role 划分，跨 native session 连续。native session 记为 turn 的属性。
- 按任务查看的记录，是把 turn 按 task 筛选出的视图。
- 理由：模型实际的上下文是 role 的 native session，它跨多个任务。
- 会议、一对一与 Thread 的关系留到 M3。

### 7.2 Item

- 业务事实只存一份。`org_report`、`done`、`flag_mismatch` 等调用经命令入口写成命令记录；Thread 中对应的工具调用 item 只引用该命令记录，不重复保存内容。
- 其他 item 是展示类：agent 文本、思考、工具调用及其输出、文件改动。每个 item 在完成时落库（frontend.md §3）。

### 7.3 存储

- SQLite 保存 item 的元数据和小内容。
- 任何字段超过存储阈值时，内容存入本地文件库。数据库保存哈希、大小、头尾预览和稀疏行索引；稀疏行索引用于按行范围读取。
- 本地文件库：文件按内容哈希命名，写入后不再修改；相同内容只存一份；没有引用时删除。不使用外部对象存储服务，也不复用 jj 的对象库。
- 存储阈值的起始值为 100KB。依据：[SQLite 官方测量](https://www.sqlite.org/intern-v-extern-blob.html)中，BLOB 小于约 100KB 时存在库内读取更快，大于时存为独立文件更快；交叉点随页大小在 50–200KB 之间变化，测量所用硬件较早。最终值在性能基线实测后确定。
- 存储阈值按字节计算，与对话中折叠显示的阈值（按行计算，frontend.md §6）分开。
- 写入文件库失败时，该字段留在 SQLite 中，item 照常按顺序落库，只是读取这个字段较慢。运行时不重试、不补录（[#10](https://github.com/vorton-lang/Lobotomy/issues/10)，用户确认，2026-10-04）。
- 图片等二进制内容一律存入文件库。
- 两家 CLI 的工具输出都在工具结束后一次到达，不在运行中流式到达（harness-adapter.md §1.4）。后端收到后整块写入文件库。

### 7.4 原始输出

- 运行时把每个 turn 的 CLI 原始输出完整写入文件。
- turn 正常结束、没有无法解析的事件、所有事件都已记录时，item 落库后运行时删除原始输出。
- 其他情况保留原始输出，用于排查和改进解析（harness-adapter.md §1.3 第 7 条），按 7.5 回收。
- 没能记下 harness 的会话 ID 时，这个 turn 记为 failed，role 停下等用户（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)）。否则下一个 turn 不带 resume，悄悄开一个新会话，role 失去上下文。

### 7.5 保留与回收

| 内容 | 保留与回收 |
|---|---|
| 消息、汇报、agent 文本等小内容 | 永久保留，落实"下层产出全部可达，不删除"（manager-actions.md §0） |
| 大工具输出的全文；7.4 保留的原始输出 | 所属任务关闭 30 天后回收，天数可配置；没有任务的 turn 从 turn 结束时计算。回收后保留头尾预览与大小，GUI 标为"全文已回收" |
| 文件库中的文件 | 没有引用时删除 |

工具输出是执行过程的记录，不属于下层产出，回收全文不违反上述原则。

### 7.6 序号

- 每个 Thread 一个单调递增的序号，用于对话的"快照加增量"（frontend.md §3 第 4 条）。
- 另设一个全局事件序号，记录业务状态的变化，供 Workboard 等投影使用。

### 7.7 引用

- `[[att:id]]`、ledger 的依据、退回时引用的意见，都指向持久记录的稳定 ID：item、命令记录、消息、成果或检查结果。
- 引用不指向事件，也不指向 partial。
- ID 全局唯一并带类型前缀。运行时校验 ID 是否存在、类型是否允许（manager-actions.md §2.1）。
- 后端生成的 ID 按生成顺序排序，同一毫秒内也是如此。查询在时间戳相同时按 ID 排序，依赖这一点（2026-10-09）。

## 8. 额度（M1 的最小行为）

依据 [#4](https://github.com/vorton-lang/Lobotomy/issues/4)。

### 8.1 额度域

- 额度域按"harness × 登录账户"划分。v1 中每个 harness 只使用用户的一个登录，因此只有两个域：Claude 域（Angela、Binah）和 Codex 域（Malkuth、Yesod）。
- 额度域属于项目外层，以后多个项目共用同一账户时共享额度状态（§10）。
- v1 不支持多账户。

### 8.2 观测

- Claude：每个 turn 的 stdout 中有 `rate_limit_event`，包含 5 小时与 7 天窗口的利用率和重置时间（harness-adapter.md §1.3 第 5 条）。
- Codex：`--json` 输出中没有额度信息。运行时尽力从 rollout 文件的 `rate_limits` 读取已用百分比、窗口长度和重置时间；读不到时不显示。
- 每次观测都带时间，GUI 显示观测的新旧。
- 观测只用于显示。只有真正被拒绝才阻塞调度，过期的观测不造成阻塞。v1 不按利用率提前限流。

### 8.3 被拒绝时

- 被拒的 turn 记为 failed（额度）。该额度域进入"受阻"：域内所有 role 都不再启动新 turn，运行时不按 role 各自重试。
- 已在运行的 turn 不打断，由它们自行结束。
- 另一个额度域照常工作。需要受阻域判断的环节停下等待。
- 同一状态只通知一次，按系统故障通知（manager-actions.md §6）。
- 识别不出原因的失败记为普通 failed，不阻塞额度域。

实测记录（Claude Code 2.1.283，交互式 CLI，2026-10-01，一次）。被拒时，会话文件中写入一条合成的 assistant 消息：

- `isApiErrorMessage: true`、`error: "rate_limit"`、`apiErrorStatus: 429`；
- `quotaLimits` 中有 `status: "rejected"`、`rateLimitType: "five_hour"` 和 `resetsAt`（Unix 秒）；
- 显示文本为 "You've hit your session limit · resets 12:20am (Asia/Tokyo)"；
- 用户的输入在报错之前已写入会话文件。

`-p` 的 stream-json 模式下被拒的形式尚未确认，预期是 `status` 为 `rejected` 的 `rate_limit_event`，字段与上面的 `quotaLimits` 相同。Codex 被拒时的形式未知，暂不处理。

### 8.4 恢复检查

**语义更新**（[#11](https://github.com/vorton-lang/Lobotomy/issues/11) 讨论，用户确认，2026-10-04）：恢复统一由用户手动触发。原来的"重置时间过后 1 分钟自动检查"已删除，以减少维护面。

- 运行时不计划、不进行自动检查。受阻的额度域只在用户手动重试时检查。
- 用户重试时，运行时立即检查一次。通过则额度域回到正常；仍被拒则保持受阻，并记下新的重置时间用于显示。同一额度域同时最多进行一次检查。
- 检查使用一次最小的独立调用，带不保存会话的参数（Claude `--no-session-persistence`，Codex `exec --ephemeral`）。检查不经过任何 role 的 native session，也不在用户的会话历史中留下记录。
- 检查调用有超时，默认 2 分钟，可配置。超时按"仍被拒"处理，额度域保持受阻（[#10](https://github.com/vorton-lang/Lobotomy/issues/10)，用户确认，2026-10-04）。

### 8.5 恢复后

- 检查通过后，额度域回到正常，同域 role 的排队工作照常调度。
- **语义更新**：原来"上一个 turn 因额度失败的 role，运行时自动开始继续 turn"已删除（用户确认，2026-10-04）。因额度失败的 role 与其他失败一样停下，由用户选择"继续"。继续时，输入以一段说明开头（上一个 turn 因额度不足而失败，请先检查工作目录），其后是排队的消息。
- 失败 turn 的输入不重发（§3.4）。8.3 的实测中，Claude 在报错前已把输入写入会话文件，resume 后模型可以看到它。

### 8.6 不自动换用

运行时不自动更换模型、harness 或账户，也不绕过额度限制。换用方案由用户决定。

### 8.7 GUI

- 受影响的 role 在 Workboard 上显示额度状态，例如"额度不足（Claude）· 14:00 重置 · 等待手动重试"，或"额度不足（Claude）· 重置时间未知 · 等待手动重试"。
- 额度状态与"等你决定"分开显示。
- 确定性的 GUI 控制照常可用（roles-and-tasks.md §1.4）。

| 额度重试 | 额度域受阻；没有正在进行的检查 | 检查结果；通过时额度域回到正常（§8.4） | 立即进行一次检查调用 |
| 重试预览 | 预览物化已停止 | 物化意图 | 物化预览（先检查主仓库是否与上次预览一致） |

**role（经 MCP，按 turn 的 token 识别）**

| 命令 | 前置条件 | 同一事务写入 | 幂等 | 副作用 |
|---|---|---|---|---|
| `org_report(progress)` | turn 未结束 | 命令记录 | — | — |
| `org_report(blocked)` | turn 未结束；任务在执行阶段 | 阻塞原因 | 同一原因重复报告不再写入 | 卡在等用户时进入"等你决定"；用户的回复绑定到下一个 turn 时清除（见下） |
| `org_report(done)` | turn 未结束；任务在执行阶段 | 把本 turn 的采集标为候选成果；保持占用 | 同一 turn 重复报告不再写入 | CLI 退出后采集 |

`blocked` 与 `done` 不满足前置条件时，命令记录下来但不生效，结果分两种：
- `late`：turn 已结束，或它所属的 attempt 已经结束；
- `no_task`：turn 不属于任何任务（#14）。

回给 agent 的说明，以及 GUI 中的报告卡片，都按实际结果写明"未生效"及原因，不按报告参数显示为完成。

**用户的回复绑定到 turn 时，阻塞原因清除**（**语义更新**，[#17](https://github.com/vorton-lang/Lobotomy/issues/17)，2026-10-09）。原来只有执行者报告 progress 或 done 时才清除。实测中，用户回答后，执行者已经在处理回复，"等你决定"却仍显示问题和空白回复框，直到执行者报告 done。现在的规则：

- 用户回复后，回复先在收件箱排队。这时用户不需要再做什么，所以问题不列入"等你决定"。阻塞原因保留。
- 登记 turn 时，如果绑定的消息中有用户的消息，运行时在同一事务中清除阻塞原因。执行者已经拿到回复。它仍需要回答时，再报告一次 blocked，问题重新列入"等你决定"。
- 运行时自己的消息（例如"完成条件已更新"）不是回复，不清除阻塞原因。
- 绑定后的 turn 没能启动或失败时，role 停下等用户（harness-adapter.md §1.7）。turn 正常结束，但执行者既没有提问也没有报告 done 时，任务按"没有人推动"列入"等你决定"（frontend.md §7）。

## 10. 项目边界

- v1 中一个实例只管理一个项目。每个项目有独立的数据目录：SQLite、jj 存储、文件库、槽位与验证现场。
- 以后会扩展为多项目（多仓库）管理。项目内的管理方式不变，外面加一层多项目隔离（用户确认，2026-10-04）。
- **后端实现约束：不使用全局单例。** 项目范围内的状态都挂在项目实例上，通过参数传递，不放进全局单例或进程级静态变量。这些状态包括数据库连接、调度器、MCP 路由、运行中的 turn、项目配置。以后在同一个后端进程中开多个项目实例时，不需要重写。
- **跨项目共享的状态放在项目外层**，v1 也一样：
  - 额度域：按"harness × 账户"划分，多个项目共用同一账户时额度是共享的（§8）；
  - CLI 二进制的探测与版本记录；
  - 每个 harness 的权限模式：限制来自本机环境，不来自项目（harness-adapter.md §1.9）；
  - 系统通知的投递；
  - 后端的监听端口与 GUI 连接。
- 多项目时，role（含 Manager）不跨项目共享，每个项目一套（用户确认，2026-10-04）。role 的 native session、Thread、槽位都属于项目实例。
- **实现**（2026-10-04）：外层是 `Host` 对象，项目实例持有它的引用。外层状态存在独立的 `host.db` 中，目录默认为 `%LOCALAPPDATA%\Lobotomy`（Linux 为 `$XDG_STATE_HOME/lobotomy` 或 `~/.local/state/lobotomy`），可用 `--host-dir` 指定。目前存放额度域、每个 harness 的权限模式（harness-adapter.md §1.9）与 CLI 配置。`host.db` 与项目数据库一样按编号迁移（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)）；第一个迁移只建缺少的表，迁移出现之前建的库照常升级。"同一额度域同时最多一次检查"目前在进程内保证，多实例时再改为跨进程。
