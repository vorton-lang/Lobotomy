# 数据模型：业务对象、命令与对话记录

> Status: 设计决定 v0.2（2026-10-10）
> 按 [#7](https://github.com/vorton-lang/Lobotomy/issues/7) 逐项讨论；§1–§8 是已确认的决定，§9 汇总对象与命令，§10 是项目与 host，未定事项列在 §11。
> 标「未实现」的设计还没有实现，列入 [roadmap.md](roadmap.md) 待排。
> 依据：[#6](https://github.com/vorton-lang/Lobotomy/issues/6) §1（SQLite 是业务事实的唯一权威）、#7 及其[讨论补充](https://github.com/vorton-lang/Lobotomy/issues/7#issuecomment-5953401457)、[harness-adapter.md](harness-adapter.md)、[roles-and-tasks.md](roles-and-tasks.md)、[frontend.md](frontend.md) §3。

## 1. 命令

所有状态变化都经后端的命令完成。GUI、调度器和 role（经 MCP）调用同一组命令（#6 §1）。

- 命令按领域命名，例如建任务、启动 turn、报告 `done`、验收。`admit / claim / finish` 不作为 API 名称。
- 每条命令写明五项：
  1. 调用者与权限；
  2. 前置条件；
  3. 同一事务内写入的内容；
  4. 幂等键；
  5. 副作用。
- 命令清单见 §9.2。
- **拒绝与不变式错误分开**（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)，2026-10-05）。
  - 前置条件不满足时，命令被拒绝，带一个代码，什么也不写。调度器把拒绝当作"现在没有事可做"。
  - 存储的状态违反了代码依赖的规则时，例如读到不认识的阶段，报不变式错误。等待不会让它消失，所以调度器把它当作错误记录，不当作拒绝。
- **读操作使用单独的只读连接**（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)，2026-10-09）。
  - 写操作仍只经过唯一的写连接，命令的事务不会交错。
  - 数据库是 WAL 模式：读不等写，写也不等读。GUI 每 100 ms 查看事件日志，不再占用写连接。
  - 每次读在一个读事务里完成。其中的所有查询看到同一时刻已提交的状态，即使期间有命令提交。
- **一个数据目录只由一个后端打开。** 后端打开项目时，在项目数据目录下的 `lock` 文件上取得独占锁。锁被别的进程占用时，这个项目打不开，只影响它自己，其他项目照常运行（§10.3）。进程结束时，操作系统释放锁。host 目录另有一把锁，见 §10.3。
- **迁移在关闭外键的情况下执行**，每个迁移提交前检查外键。迁移因此可以按 SQLite 的"十二步"重建被其他表引用的表，例如修改 CHECK 约束。

## 2. 占用

占用分两层。每层的资源在同一个事务中一次取得。

| 层 | 持有者 | 资源 | 取得 | 释放 |
|---|---|---|---|---|
| 任务层 | 任务 | role | 任务开始执行时 | 任务完成或放弃时 |
| turn 层 | turn | role 的运行权 | 登记 turn 时 | turn 结束时。结果为 unknown 时，对账结束后才释放 |

每个 role 有自己的工作目录（harness-adapter.md §3），因此任务层不会出现"取得了 role，却没有取得工作目录"的半占用（[#1](https://github.com/vorton-lang/Lobotomy/issues/1)）。

turn 层的资源是 role 的运行权，不是 native session 的运行权（**语义更新**，[#11](https://github.com/vorton-lang/Lobotomy/issues/11)，2026-10-04）。依据：native session 按任务划分（§4.1），按 session 的屏障挡不住这种情况：放弃任务 A 时 A 的 CLI 仍在运行，任务 B 用新 session 在同一个工作目录里启动第二个 CLI。

### 唯一约束

以下约束由数据库强制，不依赖调用方自行检查：

- 每个 task 最多一个未关闭的 attempt。
- 每个 role 最多被一个任务占用。
- 每个 role 最多一个未结束的 turn，无论在哪个 native session 中。已登记、运行中、unknown 都算未结束。

## 3. turn 与消息投递

### 3.1 turn

- 一个 turn 就是一次 CLI 进程运行（harness-adapter.md §1.1）。
- 运行时在启动 CLI 前登记 turn，生成 turn_id（harness-adapter.md §1.3 第 8 条）。
- GUI 的 Thread → Turn → Item 中，Turn 使用同一个 turn_id，不另设编号（frontend.md §3）。
- **MCP token 按 turn 发放。**
  - 每个 turn 本来就要重新传 MCP 配置（harness-adapter.md §1.3 第 2 条），按 turn 发放 token 没有额外的调用成本。
  - token 与发放它的 turn 永久对应。`done` 等调用因此直接绑定到 turn，不按"角色当前任务"反查归属。
  - turn 结束后，如果旧进程仍用该 token 调用，后端把调用记为迟到。迟到的调用不能推进状态。
  - 更换 URL 不影响 prompt cache：Codex 已实测，第二个 turn 的缓存命中与不更换相同（harness-adapter.md §1.4）。Claude 还没有实测。

### 3.2 turn 的状态

| 状态 | 进入条件 |
|---|---|
| 已登记 | 运行时在同一个事务中写入 turn 记录、MCP token 和绑定的输入消息。CLI 尚未启动 |
| 运行中 | CLI 已启动。运行时记下 pid 与进程启动时间，用于在 pid 被复用时区分进程 |
| 已结束 · completed | 运行时收到 harness 的 turn 结束事件（Claude `result`，Codex `turn.completed`），且 CLI 已退出 |
| 已结束 · failed | harness 报告错误，例如额度被拒、登录失效、参数错误；或者 CLI 自行退出，没有 turn 结束事件，例如启动时拒绝参数或权限模式、崩溃。失败信息取 harness 的错误事件；没有错误事件时，取退出状态与 stderr 的开头。环境不允许权限模式时，失败种类为"权限模式不被允许"（harness-adapter.md §1.9）。CLI 在 stdout 上没有任何输出时，记为"harness 没有开始这个 turn"（§3.4）。按系统故障通知（manager-actions.md §6） |
| 已结束 · interrupted | CLI 已退出，没有 turn 结束事件，且是 Lobotomy 让它停下的：用户中断、停止组织，以及对账结果 |
| unknown | 后端重启时，处于"已登记"或"运行中"的 turn 都改为 unknown |

completed 只表示 turn 正常结束，不表示任务完成。任务完成取决于 `done` 与验收（§4.1）。

CLI 自行退出时记为 failed，不记为 interrupted（**语义更新**，#13，2026-10-04）。依据：受管环境中的 Codex 不允许无沙箱模式，启动时只在 stderr 写出原因就退出（#13 实测）；这种情况记为"被中断"，用户会以为继续即可恢复。两种结果之后可做的事相同：继续、新建 native session 或放弃。

失败信息中的 stderr 去掉了本 turn 的 MCP token；stderr 全文保留在原始输出中。

### 3.3 对账

"待对账"只核对一件事：CLI 进程是否已经退出。

只核对这一件事的理由：

- `done` 等业务命令在发生时已写入 SQLite；对话 item 在完成时已落库。
- Lobotomy 不恢复执行现场（harness-adapter.md §1.7），因此不需要从 harness 的会话文件重建业务事实。

核对方法：

1. 运行时按记下的 pid 与进程启动时间检查进程。
2. 如果后端在记下 pid 之前已崩溃：
   - Windows：进程以挂起方式创建，记下 pid 之后才运行（harness-adapter.md §1.8）。没有 pid 就表示 CLI 从未运行，turn 记为 interrupted（**语义更新**，2026-10-04）。
   - Linux：运行时按命令行中的 turn 标识查找进程。Codex 的 MCP URL 在命令行参数中；Claude 的 MCP 配置文件按 turn_id 命名。未实现，列入 roadmap 待排（Linux 适配时补上）。

核对结果：

- **CLI 已退出**：turn 记为 interrupted，运行时释放 role 的运行权（§2）。
  - 这个 turn 报告过 `done` 时，任务照常进入验收（§4.1）。
  - 没有报告 `done` 时，工作目录保持原样，等用户选择继续、新建 native session 或放弃（harness-adapter.md §1.7）。
- **CLI 仍在运行**（例如 Linux 上 harness 没有响应 SIGTERM）：turn 保持 unknown，运行时定期检查进程是否退出。GUI 显示"上一个 turn 的进程仍在运行"，并提供"终止"。运行时不自动终止进程。

### 3.4 消息投递

| 状态 | 判断依据 |
|---|---|
| 排队 | 消息在 role 的收件箱中，尚未绑定到 turn |
| 已绑定 | 与 turn 登记在同一个事务中写入 |
| 已投递 | CLI 已启动，stdin 写入并关闭成功 |

- 登记 turn 时，运行时按到达顺序绑定收件箱中全部排队的消息。
- 消息投递后，跟随所在 turn 的结果：completed、failed、interrupted 或 unknown。
- "已处理"不作为机器状态。模型是否按消息行事属于语义判断；机器能确认的只有"投递它的 turn 是否正常结束"。
- 输入是否已进入 harness 自己的会话记录：Claude 额度被拒时，输入在报错前已写入（§8.3）；其他中断时刻仍需实测（harness-adapter.md §6）。
- **所在 turn 未正常结束时，消息不自动重投。** resume 接续的是原来的 native session，其记录中可能已有这条消息；自动重投可能造成重复。GUI 把这些消息标为"所在 turn 未正常结束"，由用户决定继续还是重发。
- **harness 没有开始的 turn，继续时原样重发**（**语义更新**，#13，2026-10-04）。CLI 在 stdout 上没有任何输出就退出时，例如启动时拒绝参数或权限模式，输入没有进入任何会话。用户选择继续时，运行时把那次的输入原样作为新 turn 的输入，不加说明；绑定的消息改绑到新 turn，投递状态清空。这不会造成重复，因为 harness 从没收到过这些内容。依据：只发一段失败说明时，那次的输入会丢失；受管环境中第一个 turn 被拒时，执行者就从没见过任务说明。
- 因额度失败的 turn 如何处理，见 §8.5。

### 3.5 问题与回复的因果关联

**语义更新**（用户授权根因修复，2026-10-12；收紧 [#17](https://github.com/vorton-lang/Lobotomy/issues/17) 的回复规则）。

执行者的 `org_report(blocked)` 与 Angela 的 `ask_user` 共用 `question` 记录。执行者每个任务最多保留一个当前问题；Angela 可以同时等待多个问题的回答。`question` 是问题状态的唯一事实来源，task 表不存阻塞原因。对外的 Task DTO 仍有 `blocked_reason` 字段，从该任务的开放问题读取，界面协议不变。

- 提问事务保存问题 ID、role、task（Angela 的问题为空）、提问 turn，以及当时数据库中最大的 `message.seq`，作为 `after_message_seq`。消息入队和提问在同一个数据库的写事务中串行提交。关联使用 `message.seq > after_message_seq`，不比较时间戳；同毫秒、时钟回拨、投递乱序与后端重启都不改变边界。
- 后续消息还必须发给提问的 role。任务问题接受用户或 Angela 的消息，消息指向该任务或未指定任务；Angela 的问题只接受用户发给她的消息。其他任务、其他 role 与运行时的消息均不算回复。Angela 转达消息时，以该消息进入项目收件箱的事务为边界，不用引用原话的时间跨库比较。
- 有关联的回复排队时，问题暂时不列入"等你决定"，问题记录仍保持开放，DTO 的 `blocked_reason` 仍由它派生。绑定到 turn 时，运行时在同一事务中关闭这些问题，并记录交付 turn 与消息 ID；对应的 `blocked_reason` 随后读出为空。展示、绑定及输入构造使用同一关联规则。
- 关联只表示时序与来源、接收范围合格的候选回复已交付，不表示运行时判断了内容是否真正解决问题。无关的新消息也可能符合这些条件并关闭问题；role 仍需回答时再次提问。关联不授予动作权限。
- 旧消息仍按入队顺序交付。输入列出当前问题，并逐条标明消息关联的问题；没有关联的消息仅作上下文。新问题仍未收到回复时，输入明确说明不能把本 turn 的旧消息当成其回复或授权。
- 同一 turn 对仍开放的问题重复提交相同文本，保留原问题和边界。执行者改变问题、在新 turn 再次报告 blocked，或在问题关闭后重新报告时，创建新问题；旧回复不能关闭新问题。progress、done、关闭任务或进入新 attempt 会撤下旧任务问题。Angela 的不同问题各自记录边界。
- `blocked` 仍是问题状态，不是执行禁令。"继续"控制命令本身不回答问题。暂停、权限与异常后继续保持独立；收到关联回复也不能解除用户的暂停。绑定后的 turn 未启动或失败时，仍按原规则等待用户；未启动 turn 的输入重发（§3.4；harness-adapter.md §1.9）保留已有的问题关联。
- 运行时读取当前问题，不从历史事件重建当前状态。

## 4. 任务流（M1）

### 4.1 attempt

- 每次进入执行阶段，运行时开一个新的 attempt。进入执行的情况有三种：任务开始、退回、重开。
- attempt 内每次运行 CLI 是一个 turn。同一个 attempt 内接续时，运行时只新建 turn，不新建 attempt。例如：执行者提问后用户回答，turn 被中断后用户选择继续，更换 native session 后的第一个 turn。
- **语义更新**（[#86](https://github.com/vorton-lang/Lobotomy/issues/86)，2026-10-17）：报告 `done` 的 turn 结束时，不论结果，attempt 以候选成果结束，任务进入验收。任务被放弃时，attempt 也结束。之后的验收针对这个 attempt 报告的 `done`。依据：采集与验证随 worker 层的替换退出，运行时不再固定文件成果。

turn 是执行单位：一个进程、一个 MCP token，对账按 turn 进行。attempt 是业务单位：一次执行交出一份候选成果，证据与验收针对它。

**native session 按任务划分**（[#11](https://github.com/vorton-lang/Lobotomy/issues/11)，用户确认，2026-10-04）：

- 执行者在任务的第一个 turn 时新开 native session，任务关闭（完成或放弃）时结束它。任务有明确的边界，上一个任务的上下文对下一个任务基本没有帮助。
- 同一任务的多个 attempt（退回）沿用同一个 session。上一轮做了什么、为什么被打回，对修改有用。
- 重开的任务新开 session（§4.6）。
- 不属于任何任务的消息（role 空闲时用户直接发送）使用 role 的一个独立 session。
- 用户随时可以手动新建 native session。新 session 开始时，运行时重发这一轮的开工说明（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)）。
- 异常后停下（harness-adapter.md §1.7）只针对当前 attempt 内的异常 turn。上一个 attempt 已经结束时，工作已经推进，它的异常 turn 不再挡住新 attempt；"继续"也只能作用于当前 attempt。这样新任务、重开和新 attempt 都不会被旧的异常状态阻塞。

### 4.2 离开执行阶段后的消息

任务离开执行阶段后（验收），发给执行者的消息进入收件箱排队，任务回到执行时运行时再投递。

- 理由：执行者已交出候选成果。此时运行 turn，交出的内容可能在验收期间改变。
- 代价：验收期间不能与执行者对话。用户需要提问时，退回任务并附上问题。

**任务关闭时，它的排队消息不再投递**（**语义更新**，#14，用户确认，2026-10-04）。依据：实测中，任务关闭后才投递的补充要求进入了不属于任何任务的 turn，产出的修改没有进入验收结果，下一个任务开始时又从工作目录中消失（#14）。

- 验收时，如果用户发给这个任务的消息还没投递，用户必须二选一：
  - **退回**：消息随退回进入新的 attempt，照常验收；
  - **验收，不再投递**：验收请求列出这些消息，后端核对列出的就是全部未投递的消息，然后把它们标为"未投递"，并记在验收决定里。
- 放弃任务时，它的排队消息标为未投递，并记在放弃决定里。
- 运行时发给任务的排队消息（例如"完成条件已更新"）在任务关闭时一并作废，不需要用户决定。

### 4.3 回到执行时的工作目录

- 工作目录保持原样，执行者接着工作。运行时不改写它（**语义更新**，#86，2026-10-17；harness-adapter.md §3）。

### 4.4 修改完成条件

- 用户随时可以修改完成条件。每次修改生成一个新版本，不打断正在运行的 turn。
- 任务在执行阶段时，运行时把新版本作为一条消息投递给执行者。
- 任务在验收阶段时，运行时不自动退回任务，更新消息按 4.2 排队。验收请求带完成条件版本；版本不符时，验收被拒绝。用户按新版本重新判断，再决定验收或退回。
- 已有的证据仍绑定旧版本。

### 4.5 证据何时作废

| 证据 | 绑定 | 作废条件 |
|---|---|---|
| 验收 | 完成条件版本 | 提交时与当前值不符 |
| 审查结论（审查阶段） | 成果、完成条件版本 | 完成条件版本变化。基线变化后能否沿用，做审查时再定 |

以下变化不使证据作废：role 下线后再上线、更换 native session、展示字段变化。

**语义更新**（#86，用户确认，2026-10-17）：检查结果随验证退出，验收不再绑定成果与集成版本头。

### 4.6 重开

- 只能重开已关闭的任务，即已完成或已放弃的任务。重开建立新的 attempt，任务进入排队。
- **语义更新**（#86，2026-10-17）：重开只让任务重新排队，运行时不为它准备代码起点。
- **语义更新**（#86，用户，2026-10-17）：交给过 worker 的任务关闭后不能重开，要做就新建一个任务。依据：worker 那边的 attempt 关闭后不再执行，重开只会让任务停在排队。失败或被停的 worker 任务不关闭，可以改完成条件重来（tech-plan.md §7 第 7 组）。
- 继承：任务 ID、当前完成条件版本、审查预算（不重置，roles-and-tasks.md §2.2）。
- 不继承：审查结论。
- 重开时新开 native session（**语义更新**，#11，2026-10-04；§4.1）：任务关闭时它的 session 已经结束。新 session 收到任务说明。

## 5. 副作用与回执

每个副作用都按同一顺序进行：

1. 运行时把意图写入 SQLite，与引起它的业务变化在同一个事务中提交。
2. 运行时执行副作用。
3. 运行时记录回执。

回执丢失时：能安全重做的副作用，运行时重做；不能重做的，运行时核对实际状态。

| 副作用 | 意图记录 | 回执 | 回执丢失时 |
|---|---|---|---|
| 启动 CLI | turn 记录（已登记） | pid；turn 结束事件 | 按 §3.3 对账。运行时不自动重启 CLI |
| 系统通知（未实现，见 manager-actions.md §6） | 通知意图 | 显示确认 | 不补发系统通知，GUI 内照常显示。宁可漏发一次，也不重复 |

- 启动 CLI 不能重做：重做意味着模型再运行一次。turn 记录本身就是意图与回执。
- **语义更新**（#86，用户确认，2026-10-17）：物化、采集、检查、预览与采用展示分支这些副作用随 worker 层的替换退出，`outbox` 表随预览删除。

## 6. 磁盘占用与回收

Lobotomy 在磁盘上创建的每个目录或文件，在 SQLite 中都有归属记录和回收条件。不允许产生没有回收条件的内容。

- 现在记在 SQLite 中的：文件库中的文件（blob 记录）、turn 的原始输出（按 turn_id 命名，归属于 turn 记录）。
- role 的工作目录（harness-adapter.md §3）还没有归属记录与回收条件，按所在目录确定，现在一直保留。待决，见 §11。
- 旧版本在项目数据目录中留下的私有存储与现场目录（`store/`、`slots/`、`workspaces/`、`verify/`、`quarantine/`、`trials/`）没有归属记录。运行时不读，也不删除它们（#86）。怎样处理见 §11。

| 内容 | 回收条件 |
|---|---|
| 审查现场（审查阶段） | 任务关闭时删除 |
| 每个 turn 的 MCP 配置文件 | turn 结束时删除 |
| 大输出与原始输出文件 | 见 §7.5 |

- 删除失败时（例如 Windows 上文件被占用），运行时定期重试。持续失败时，GUI 显示占用的空间和原因。未实现，列入 roadmap 待排。现在删除失败时运行时不重试。
- 运行时启动时清扫 Lobotomy 的数据目录：删除没有归属记录、或已满足回收条件的内容。清扫只在 Lobotomy 的数据目录内进行。运行时一般先写归属记录、再创建内容（§5）。文件库是例外：先写文件、再写 blob 记录。写入中途崩溃只会留下没有记录的文件，由清扫删除，不会出现指向不存在文件的记录（**语义更新**，按实现，用户确认，2026-10-13）。
- 清扫的现状：后端打开项目时不删除任何内容（#86）。以下部分未实现，列入 roadmap 待排：
  - 删除没有 blob 记录的文件库文件；
  - 删除后端崩溃后留下的 MCP 配置文件；
  - 按 §7.5 回收原始输出与大输出的全文。

## 7. 对话记录

### 7.1 Thread

- Thread 按 role 划分，跨 native session 连续。native session 记为 turn 的属性。
- 按任务查看的记录，是把 turn 按 task 筛选出的视图。
- 理由：模型实际的上下文是 role 的 native session，它跨多个任务。
- 会议与 Thread 的关系留到会议阶段（roadmap.md 待排）。

### 7.2 Item

- 业务事实只存一份。`org_report`、`done`、`flag_mismatch` 等调用经命令入口写成命令记录；Thread 中对应的工具调用 item 只引用该命令记录，不重复保存内容。只读的工具调用（例如 Angela 读取项目）不写命令记录，item 保存完整的回复。回复中提到别的数据库的命令记录时，item 也不引用它。
- 其他 item 是展示类：agent 文本、思考、工具调用及其输出、文件改动。每个 item 在完成时落库（frontend.md §3）。

### 7.3 存储

- SQLite 保存 item 的元数据和小内容。
- 任何字段超过存储阈值时，内容存入本地文件库。数据库保存哈希、大小、头尾预览和稀疏行索引；稀疏行索引用于按行范围读取。稀疏行索引未实现，列入 roadmap 待排；现在只能按哈希读取全文。
- 本地文件库：文件按内容哈希命名，写入后不再修改；相同内容只存一份；没有引用时删除（未实现，见 §7.5）。不使用外部对象存储服务。
- 存储阈值的起始值为 100KB。依据：[SQLite 官方测量](https://www.sqlite.org/intern-v-extern-blob.html)中，BLOB 小于约 100KB 时存在库内读取更快，大于时存为独立文件更快；交叉点随页大小在 50–200KB 之间变化，测量所用硬件较早。最终值在性能基线实测后确定。
- 存储阈值按字节计算，与对话中折叠显示的阈值（按行计算，frontend.md §7.3）分开。
- 写入文件库失败时，该字段留在 SQLite 中，item 照常按顺序落库，只是读取这个字段较慢。运行时不重试、不补录（[#10](https://github.com/vorton-lang/Lobotomy/issues/10)，用户确认，2026-10-04）。
- 图片等二进制内容一律存入文件库。
- 两家 CLI 的工具输出都在工具结束后一次到达，不在运行中流式到达（harness-adapter.md §1.4）。后端收到后整块写入文件库。

### 7.4 原始输出

- 运行时把每个 turn 的 CLI 原始输出完整写入文件。
- turn 正常结束、没有无法解析的事件、所有事件都已记录时，item 落库后运行时删除原始输出。
- 其他情况保留原始输出，用于排查和改进解析（harness-adapter.md §1.3 第 7 条），按 7.5 回收。
- 没能记下 harness 的会话 ID 时，这个 turn 记为 failed，role 停下等用户（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)）。否则下一个 turn 不带 resume，悄悄开一个新会话，role 失去上下文。

### 7.5 保留与回收

| 内容 | 保留与回收 |
|---|---|
| 消息、汇报、agent 文本等小内容 | 永久保留，落实"下层产出全部可达，不删除"（manager-actions.md §0） |
| 大工具输出的全文；7.4 保留的原始输出 | 所属任务关闭 30 天后回收，天数可配置；没有任务的 turn 从 turn 结束时计算。回收后保留头尾预览与大小，GUI 标为"全文已回收" |
| 文件库中的文件 | 没有引用时删除 |

工具输出是执行过程的记录，不属于下层产出，回收全文不违反上述原则。

后两行的回收都未实现，列入 roadmap 待排。现在运行时不删除文件库中的文件，也不删除 7.4 保留的原始输出；GUI 在设置中显示保留的原始输出占用的空间（#16）。

### 7.6 序号

- 每个 Thread 一个单调递增的序号，用于对话的"快照加增量"（frontend.md §3 第 4 条）。
- 另设一个全局事件序号，记录业务状态的变化，供 Workboard 等投影使用。
- 每个事件记下写入它的命令记录。事件只由命令在自己的事务中写入，一条命令可以写入多个事件。
- 后端读出事件时，从命令记录中一并给出调用者：`user`、`runtime`、`role:<名字>` 或 `manager`。role 的命令还给出它所在的 turn；`manager` 的命令给出她在自己数据库中的 turn。依据见 §10.6 跨库操作第 3 条。
- 加入这一项之前写入的事件不带命令记录引用。读出时，它们的调用者为空。

### 7.7 引用

- 引用都指向持久记录的稳定 ID，不指向事件，也不指向 partial。
- `[[att:id]]` 现在可以指向任务和执行者的汇报（`org_report` 的命令记录，`cmd_`）。设计中可以引用的其他产出见 manager-actions.md §2.1。
- `[[quote:id]]` 和 ledger 的依据指向用户本人的消息（manager-actions.md §2.1、§3.2）。
- ID 全局唯一并带类型前缀。运行时校验 ID 是否存在、类型是否允许（manager-actions.md §2.1）。
- 后端生成的 ID 按生成顺序排序，同一毫秒内也是如此。查询在时间戳相同时按 ID 排序，依赖这一点（2026-10-09）。

## 8. 额度（M1 的最小行为）

依据 [#4](https://github.com/vorton-lang/Lobotomy/issues/4)。

### 8.1 额度域

- 额度域按"harness × 登录账户"划分。v1 中每个 harness 只使用用户的一个登录，因此只有两个域：Claude 域和 Codex 域。role 的 turn 属于它所在会话的 harness 的域；role 可以切换 harness（§9.2）。
- 额度域属于 host，所有项目共享（§10）。
- v1 不支持多账户。

### 8.2 观测

- Claude：每个 turn 的 stdout 中有 `rate_limit_event`，包含 5 小时与 7 天窗口的利用率和重置时间（harness-adapter.md §1.3 第 5 条）。
- Codex：`--json` 输出中没有额度信息。运行时尽力从 rollout 文件的 `rate_limits` 读取已用百分比、窗口长度和重置时间；读不到时不显示。
- 每次观测都带时间，GUI 显示观测的新旧。
- 观测只用于显示。只有真正被拒绝才阻塞调度，过期的观测不造成阻塞。v1 不按利用率提前限流。

观测未实现，列入 roadmap 待排。现在运行时只识别被拒（§8.3）：不记录 `rate_limit_event` 中的利用率，也不读 Codex 的 rollout 文件。

### 8.3 被拒绝时

- 被拒的 turn 记为 failed（额度）。该额度域进入"受阻"：域内所有 role 都不再启动新 turn，运行时不按 role 各自重试。
- 已在运行的 turn 不打断，由它们自行结束。
- 另一个额度域照常工作。需要受阻域判断的环节停下等待。
- 同一状态只通知一次，按系统故障通知（manager-actions.md §6）。
- 识别不出原因的失败记为普通 failed，不阻塞额度域。

实测记录（Claude Code 2.1.283，交互式 CLI，2026-10-01，一次）。被拒时，会话文件中写入一条合成的 assistant 消息：

- `isApiErrorMessage: true`、`error: "rate_limit"`、`apiErrorStatus: 429`；
- `quotaLimits` 中有 `status: "rejected"`、`rateLimitType: "five_hour"` 和 `resetsAt`（Unix 秒）；
- 显示文本为 "You've hit your session limit · resets 12:20am (Asia/Tokyo)"；
- 用户的输入在报错之前已写入会话文件。

`-p` 的 stream-json 模式下被拒的形式尚未确认。Claude adapter 认三种信号，按上面的记录推定（harness-adapter.md §1.4，2026-10-09）：
- `status` 为 `rejected` 的 `rate_limit_event`，字段预期与上面的 `quotaLimits` 相同，重置时间取自这里；
- 顶层 `error` 为 `rate_limit` 的 assistant 消息；
- `api_error_status` 为 429 的 `result`。

Codex 被拒时的形式未知，暂不处理。

### 8.4 恢复检查

- **恢复只由用户手动触发**（**语义更新**，[#11](https://github.com/vorton-lang/Lobotomy/issues/11) 讨论，用户确认，2026-10-04）。运行时不计划、不进行自动检查。受阻的额度域只在用户手动重试时检查。
- 用户重试时，运行时立即检查一次。通过则额度域回到正常；仍被拒则保持受阻，并记下新的重置时间用于显示。同一额度域同时最多进行一次检查。
- 检查使用一次最小的独立调用，带不保存会话的参数（Claude `--no-session-persistence`，Codex `exec --ephemeral`）。检查不经过任何 role 的 native session，也不在用户的会话历史中留下记录。
- 检查调用的超时默认 2 分钟，可配置（配置未实现，现在固定 2 分钟，列入 roadmap 待排）。超时按"仍被拒"处理，额度域保持受阻（[#10](https://github.com/vorton-lang/Lobotomy/issues/10)，用户确认，2026-10-04）。

### 8.5 恢复后

- 检查通过后，额度域回到正常，同域 role 的排队工作照常调度。
- 运行时不自动继续因额度失败的 role（**语义更新**，用户确认，2026-10-04）。它与其他失败一样停下，由用户选择"继续"。继续时，输入以一段说明开头（上一个 turn 因额度不足而失败，请先检查工作目录），其后是排队的消息。
- 失败 turn 的输入不重发（§3.4）。8.3 的实测中，Claude 在报错前已把输入写入会话文件，resume 后模型可以看到它。

### 8.6 不自动换用

运行时不自动更换模型、harness 或账户，也不绕过额度限制。换用方案由用户决定。

### 8.7 GUI

- 受影响的 role 在 Workboard 上显示额度状态，例如"额度不足（Claude）· 14:00 重置 · 等待手动重试"，或"额度不足（Claude）· 重置时间未知 · 等待手动重试"。
- 额度状态与"等你决定"分开显示。
- 确定性的 GUI 控制照常可用（roles-and-tasks.md §1.4）。

## 10. 项目与 host

一个后端进程管理所有项目，项目的外层是 host（**语义更新**，用户确认，2026-10-10）。依据：全局只有一个 Angela，她的数据位置、工具参数和界面都取决于多项目的结构。

**语义更新**（[#86](https://github.com/vorton-lang/Lobotomy/issues/86)，用户，2026-10-16）：新方向改为全局一个数据库，不再按项目分库，见 tech-plan.md §4.1。未实现，顺序见 tech-plan.md §7。

### 10.1 项目实例与执行者

**语义更新**（[#86](https://github.com/vorton-lang/Lobotomy/issues/86)，第 1 步，用户确认，2026-10-17）：第 1 步保留按项目分库，全局库在第 2 步做（tech-plan.md §7）。执行者已移到 worker 宿主，后端只运行 Angela 的 turn。

- 每个项目仍有独立的 SQLite 与文件库，保存编排任务及 worker 的状态、交付物与证据。
- 执行者的 native session、Thread 与工作目录属于 worker 宿主的 task 实例；每个 attempt 有自己的 clone。项目实例不再运行本地执行者。
- **后端实现约束：不使用全局单例。** 项目范围内的状态都挂在项目实例上，通过参数传递，不放进全局单例或进程级静态变量。这些状态包括数据库连接、调度器、MCP 路由、运行中的 turn、项目配置。

### 10.2 host

host 是项目的外层，一个用户一个。它的状态存在 host 目录的 `host.db` 中，按编号迁移（[#16](https://github.com/vorton-lang/Lobotomy/issues/16)）。host 目录默认为 `%LOCALAPPDATA%\Lobotomy`（Linux 为 `$XDG_STATE_HOME/lobotomy` 或 `~/.local/state/lobotomy`），可用 `--host-dir` 指定。

host 持有跨项目共享的状态：

- 项目登记（§10.3）；
- 额度域：按"harness × 账户"划分，所有项目共享（§8）；
- CLI 二进制的探测与版本记录（版本记录未实现，列入 roadmap 待排；harness-adapter.md §1.5）；
- 每个 harness 的权限模式：限制来自本机环境，不来自项目（harness-adapter.md §1.9）；
- 系统通知的投递（未实现，见 manager-actions.md §6）；
- 后端的监听端口、GUI 连接与 GUI token（frontend.md §1）；
- Angela（§10.6）。

### 10.3 进程与登记

- **一个 host 目录只运行一个后端。** 后端在 host 目录的 `lock` 文件上持有独占锁，并在 host 目录写入 `backend.json`（端口与 pid）。锁被占用时，第二个后端报错退出。每个项目的数据目录另有一把锁（§1），别的进程不能再打开同一个项目。
- **项目登记在 `host.db` 中**：项目 ID、名称、数据目录、仓库路径、状态（接入中、运行、归档）、登记时间。
  - 项目 ID 与项目数据库中 project 行的 ID 相同。运行时在登记时生成 ID，接入时写进项目数据库。
  - 名称默认取仓库目录名。
  - 新项目的数据目录是 host 目录下的 `projects/<项目 ID>`。
  - 登记中也记下仓库路径（**语义更新**，用户确认的方案，2026-10-10）。它在登记时写入，之后不变。项目数据库中的记录是权威；登记中的这一份只用于下面的查重，以及项目打不开时在 GUI 中显示。依据：查重要覆盖已归档和打不开的项目，这时项目数据库没有打开，或者已经丢失。
- **同一个仓库同时只能有一个未归档的项目。** 这条规则原来的依据是两个项目会把预览写进同一个分支；预览已随 #86 退出，规则是否保留见 §11。
  - 新建项目时，如果这个仓库已有未归档的项目，运行时拒绝。如果只有已归档的项目，GUI 提示可以取消它的归档；用户也可以照样新建。
  - 取消归档时，如果这个仓库已有别的未归档项目，运行时拒绝。
  - 一个项目的数据目录丢失后，用户把它归档，再为这个仓库新建项目。
  - 已归档的项目不占用仓库（**语义更新**，用户确认，2026-10-10）。依据：否则数据目录丢失的项目无法取消归档，这个仓库就再也不能接入。
- **启动时**，后端读取登记，打开每个状态为"运行"的项目：取得数据目录的锁、迁移、对账（§3.3），然后开始调度。项目之间互不等待。
- **打不开的项目只影响自己。** 数据目录丢失、迁移失败、锁被占用，或项目数据库由更新版本的 Lobotomy 写过时，后端把这个项目记为出错，GUI 显示原因，其他项目照常运行。出错只记在后端进程中，不写入登记。用户处理后，选择"重试打开"。
- **数据库比后端新时不使用。** 数据库的迁移编号大于后端知道的编号时，后端不打开它，也不改动它：后端不知道更新的表结构表示什么。项目数据库属于这种情况时，按上一条，这个项目打不开；`host.db` 属于这种情况时，后端不启动。
- GUI 的请求与推送、MCP 的地址都带项目 ID（frontend.md §3，harness-adapter.md §2）。
- 同一额度域同时最多一次检查（§8.4）：所有项目在同一个进程中，进程内的保证覆盖全部项目。

### 10.4 新建与归档

**新建项目**：用户在 GUI 中选择仓库，后端运行中完成，不重启。

1. 运行时确认这个仓库没有未归档的项目（§10.3）。
2. 运行时写入登记，状态为"接入中"。
3. 运行时建立数据目录，按接入项目的规则接入（§9.2）。
4. 运行时把状态改为"运行"，打开项目实例。

接入被拒或出错时，运行时删除数据目录和登记，返回原因。后端在接入中途退出时，下次启动时清扫状态为"接入中"的登记和它的数据目录（§6）。

**归档**对这一个项目做正常停止，与退出 Lobotomy 时相同（frontend.md §1）：

1. 运行时停止这个项目的调度。
2. 运行时中断这个项目正在运行的 turn，等 CLI 退出。超过正常停止的等待时间（30 秒）时，运行时强制结束 CLI 所属的进程组（Linux）或 Job Object（Windows），确认其中的进程已退出。Linux 的进程组范围见 harness-adapter.md §1.8。
3. 运行时关闭项目实例，释放数据目录的锁。数据全部保留。

- 取消归档后，被中断的 role 等用户选择"继续"。
- 归档不要求项目没有未结束的 turn（**语义更新**，用户确认，2026-10-10）。依据：有排队任务的项目会一个 turn 接一个 turn 地运行，用户很难等到空档。
- 出错的项目也可以归档。
- 取消归档时，运行时重新打开项目实例，与启动时相同。这个仓库已有别的未归档项目时，运行时拒绝（§10.3）。
- GUI 不提供删除项目数据目录的操作。

### 10.5 跨项目

- **不设跨项目的并发上限**（用户确认，2026-10-10）。各项目的 role 各自运行。额度域是实际的限制：一个项目中 Claude 的 turn 额度被拒时，所有项目中使用 Claude 的 role 都不再启动新 turn（§8.3）。真实使用中出现问题再加上限。
- **"等你决定"全局汇总**（用户确认，2026-10-10）。托盘和窗口标题的条数是所有项目之和。进入一个项目后，只显示这个项目的（frontend.md §2）。
  - 分组方式：**语义更新**（用户确认，2026-10-12，[ui-ux-plan.md](ui-ux-plan.md) §7 第 2 条）。「全部」与项目中的"等你决定"都按类型分组，每张卡片标出项目。界面改进专项的 P3 实现，在那之前仍按项目分组。
- **额度受阻在全局汇总中只算一条**，归在"本机"一组，不属于任何项目。进入一个项目后，用到这个额度域的项目照常显示它。依据：额度域由所有项目共享（§8），按项目各算一条会重复计数。托盘和窗口标题的条数因此是各项目之和，加上"本机"与 Angela 的条目（frontend.md §7.5）。

### 10.6 Angela 的位置

- **Manager 全局只有一个**（**语义更新**，[#23](https://github.com/vorton-lang/Lobotomy/issues/23)，用户确认，2026-10-09）。Angela 属于用户，放在 host，跨项目工作，按需载入项目的上下文。
- **数据位置**（用户确认，2026-10-10）：
  - Angela 的 turn、对话和收件箱存在 host 目录下她自己的数据库中，复用项目数据库的表结构与命令层。
  - 她的工具都带项目 ID。
- 她的数据目录是 host 目录下的 `angela/`。数据库 `lobotomy.db` 用项目数据库的迁移，库中只有她一个 role（类型 manager，默认 Claude）。
- 后端打不开她时，项目照常运行，GUI 显示原因（roles-and-tasks.md §1.4）。
- 她的 turn 只在收件箱有消息时登记，与项目的 role 一样受额度域约束。
- **记录按作用域存放**（**语义更新**，用户确认，2026-10-11）。用户范围的记录存在 Angela 的数据库中。项目范围与任务范围的记录存在所属项目的数据库中。依据：项目的数据目录应当自包含（见下面的跨库操作第 1 条）。项目归档、打不开或数据目录丢失时，只影响这个项目自己的记录。
- **工作目录与读取代码**（用户确认，2026-10-11）：
  - Angela 的工作目录是她数据目录中的空目录 `work/`。
  - 她按绝对路径读各项目的仓库，与用户看到的是同一份。
  - 她的指令写明：仓库只用来展示，不修改。运行时不另加只读沙箱，也不去掉写文件的工具。依据：role 默认在 bypass 模式下运行（harness-adapter.md §1.9），指令写明后，模型一般会遵循。万一误写，运行时不会发现（#86 之后没有预览前的检查）。
- **MCP 地址**（用户确认，2026-10-11）：Angela 的 MCP 地址在 host 层，不带项目 ID，由 token 识别她的 turn。工具参数带项目 ID（harness-adapter.md §2）。
- **读取工具**：`list_projects`、`read_project`、`read_task`、`read_events`，按下面的"读取带边界"返回。`read_diff` 随私有存储退出（#86）。
- **她的输入**：每条输入开头写明用户的本地时间。后端运行在用户的机器上，用的是本机时区。指令把它当作弱信号（roadmap.md M4）。
- **复制进项目的内容**（跨库操作第 1 条）：她引用的用户原话复制进项目数据库的 `quote` 表，每条记下她数据库中的消息 ID 和说话时间，属于一个任务或一条消息。用户当时在回复的对象，以同样的方式复制进 `forward_context` 表（manager-actions.md §1.1）。
- **回复中的引用**由后端按 ID 读出：`[[quote:…]]` 读她数据库中用户本人的消息；`[[att:…]]` 在打开的项目中查找任务或汇报，并给出当前状态。在打开的项目中都查不到时，结果写明哪些项目读不到。

**读取带边界**（用户确认，2026-10-11，[#50](https://github.com/vorton-lang/Lobotomy/issues/50)）。Angela 读取任务、成果、记录和事件时，运行时在结果中写明：

- 每个项目读到哪个事件序号为止；
- 哪些项目没有读到，以及原因：已归档或打不开（§10.3）；
- 每条结果是否仍然有效：
  - 记录是否已被 `supersedes` 取代或已失效；
  - 全文是否已回收（§7.5）。回收未实现，现在不会出现这种情况。

读取结果因此区分三种情况：在读到的项目中查不到，是"没有"；没有读到的项目，是"不可用"；已作废、被取代或已回收的内容，是"已过期"。现在只提供结构化读取，不提供全文检索或语义检索，所以不会出现检索漏查的情况。以后加入检索时，需要再区分"未查到"。

依据：Angela 恢复工作时以当前状态为准（#50）。读取结果不写边界时，她可能把没有读到说成没有，或把旧结果当作当前事实。

**跨库操作**（用户确认，2026-10-11）。Angela 的操作涉及两个 SQLite 文件：她自己的数据库，以及她操作的项目的数据库。SQLite 的外键不能跨文件，一个事务也不能跨两个数据库提交。

1. **跨库引用复制原文，并记下来源 ID。** 例如，Angela 转发的用户原话存在她的数据库中。运行时把原文复制进项目的数据库，与来源 ID 一起保存。不建跨库的外键，也不跨库联表查询。ID 由类型前缀加 ULID 组成，跨库也不会重复（§7.7）。依据：这样项目的数据目录自包含，项目丢失或归档不影响 Angela 的数据库，反过来也一样。GitHub 附件的快照（manager-actions.md §5.3）是同样的做法。
2. **Angela 在项目数据库中有自己的调用者身份：新增一种调用者 `manager`**，带她在自己数据库中的 turn ID。不复用 role 的调用者（`Caller::Role`）。
   - 依据：role 的调用者带本库中的 turn ID，role 的命令在本库中检查 turn 是否结束。Angela 的 turn 在她自己的数据库中，项目数据库查不到。
   - host 层的 MCP 入口先在 Angela 的数据库中确认她的 turn 没有结束，再以 `manager` 身份在项目数据库中执行命令。
   - 用户的控制命令按调用者分为三类（roles-and-tasks.md §4）：
     - 用户或 Manager：验收、退回、放弃、暂停与恢复。
     - 只限 Manager：`assign`、`send_to_role`。用户在 GUI 中建任务、发消息，走用户自己的命令。
     - 只限用户：其余的用户命令，例如建任务、修改完成条件、重开、调整队列、设置。
   - 暂停记下由谁设置。Manager 恢复用户设的暂停时被拒绝；Manager 暂停一个用户已暂停的任务，它仍是用户的暂停。
   - 执行者还没收到的用户消息，Manager 验收时不能放弃，只有用户能放弃（§4.2）。
   - 幂等键仍按调用者划分（§9.1）。
3. **事件记下发起者。** 事件日志为每个事件记下发起者：用户、运行时、role 或 Angela。做法：每个事件记下写入它的命令记录，读出事件时一并给出调用者：用户、运行时、role 或 `manager`（§7.6）。依据：用户直接操作项目之后，Angela 要能分清哪些变化是用户做的，哪些是运行时做的（[#23](https://github.com/vorton-lang/Lobotomy/issues/23) §3）。
4. **Angela 按项目记下读到的事件位置。** 她的数据库中，每个项目存一个事件游标（`project_cursor` 表）。运行时把变化放进她的收件箱时，在同一个事务中移动游标（第 5 条）。项目归档或打不开时，游标停在原处；项目恢复后，Angela 从游标处继续读。前提是事件不被回收：现在运行时不删除事件。以后要回收事件时，需要考虑这些游标。
5. **每条命令只写一个数据库，按作用域选择。**
   - 建任务、发消息、验收等项目命令只写项目数据库；引用的用户原话按第 1 条复制进去。
   - 用户范围的记录只写 Angela 的数据库；项目范围与任务范围的记录只写项目数据库。
   - 运行时把项目的事件投递进 Angela 的收件箱时，收件箱与游标只写 Angela 的数据库。
   - 依据：这样不需要跨库事务，也不需要中途失败后的跨库对账。按 2026-10-11 时 Manager 的工具逐个核对过，没有必须同时写两个数据库的操作。以后确实出现时，沿用 §5 的"意图 → 执行 → 回执"：在发起方的数据库中与业务变化一起写入意图，在另一个数据库中以意图 ID 为幂等键执行，回执写回发起方。

### 10.7 旧数据

升级后第一次启动时，如果 host 目录的 `gui.json` 指向一个已接入的项目，后端把它登记为第一个项目，数据目录不动。

问题记录（§3.5）的迁移用既有 `question.asked`、`task.blocked_changed` 和 `message.queued` 的事件序号恢复每个开放问题的边界，不使用历史时间戳。缺少提问事件时，已有消息全部视作上下文，问题保留，等待新回复。历史记录不完整时，不能宣称已证明旧消息与问题的关联。
